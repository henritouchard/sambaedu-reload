## Détail des problèmes

### #1 — État incohérent `batchRunning=true` + `currentBatchTaskIds=[]`

**Sévérité** : 🟠 Important
**Fichier(s)** : `resources/views/pages/parc/groups/[id]/index.blade.php:237-272`

**Constat initial (review sonnet)** :
Si le service retourne `success_count > 0` mais qu'aucun `task_id` n'est présent dans les résultats (cas des mocks des tests originaux qui retournent `code=201` sans `task_id`), alors `batchRunning=true` avec `currentBatchTaskIds=[]`. Le premier tick `pollGroupReadiness` sort immédiatement (guard `empty($currentBatchTaskIds)`) et appelle `stopBatchPolling()` — le batch se termine instantanément sans poller. État transitoire cassé silencieux.

**Avis Opus** (pertinence 2) :
Confirmé. Le service réel renvoie toujours `task_id` quand `success=true`, donc le bug ne peut se manifester qu'avec des mocks incohérents OU si le contrat du service dérive. La solution sonnet (`if (empty($dispatchedTaskIds))`) peut masquer un vrai pb côté service — il faut **garder le flip conditionné ET logger une erreur serveur** si `$dispatched > 0` mais `$dispatchedTaskIds` vide.

**Solutions possibles** :
1. Early return + log d'erreur + toast si `$dispatched > 0 && empty($dispatchedTaskIds)` (protection contrat)
2. Réparer les mocks test (voir problème #5) — adresse la cause racine des faux positifs

**Action** : corrigé automatiquement (approche 1+2 combinée).

### #8 — Polling pinge tasks `queued`/`dispatched` (blocage série)

**Sévérité** : 🟡→🟠 (Important en combo avec #12)
**Fichier(s)** : `resources/views/pages/parc/groups/[id]/index.blade.php:431-446`

**Constat initial** :
Le foreach filtre sur `isTerminal()` mais pas `STATUS_RUNNING`. Sur un batch de 50 machines en `queued` (worker pas démarré), le premier tick exécute 50 pings synchrones avant que les commandes shell aient été envoyées.

**Avis Opus** (pertinence 2) :
Plus critique que sonnet l'indique. `ping()` est serial et bloquant (~1.4s worst-case par machine offline). 50 machines offline × 1.4s = **70s bloqués** sur une requête Livewire poll, dépassant l'intervalle `wire:poll.3s` et saturant PHP-FPM.

**Solutions possibles** :
1. Restreindre ping aux tasks `STATUS_RUNNING` uniquement (queued/dispatched → skip le tick)
2. Documenter l'exigence worker async (`php artisan queue:work`) en header du composant
3. [Futur] Migration vers ping parallèle (`Concurrency::run` Laravel 11)

**Action** : corrigé automatiquement (1 + 2).
