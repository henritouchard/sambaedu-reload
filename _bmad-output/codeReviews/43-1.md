## Détail des problèmes

### #1 — Anti-thrash manquant sur le geste le plus destructeur

**Sévérité** : 🟠
**Fichier(s)** : `agent/shared/companion.go`, `agent/windows/refresh_windows.go`

**Constat (review opus)** :
`explorer_restart` partait à chaque passe où l'item porteur du hint change effectivement. Politique drift
STRICT → une force externe réécrivant la clé entre deux ticks (GPO legacy, appli tierce) aurait provoqué un
kill+relaunch d'explorer.exe toutes les 30-60 s : session utilisateur cassée en boucle. Le gate `changed`
ne protège pas de ce cas (le drift est réel à chaque passe).

**Solutions possibles** :
1. Throttle runtime par instance (intervalle minimal, dégradation vers `policy_broadcast` + warning).
2. Déléguer à 43.2 (choix du hint par capacité) avec consignation explicite du risque.

**Action** : corrigé automatiquement (solution 1) — `explorerRestartMinInterval` = 10 min, timestamp posé à la
tentative (même en échec), horloge injectable `c.now()` existante réutilisée, jamais persisté (le thrash visé
est intra-vie du compagnon). Premier restart jamais throttlé ; `shell_notify`/`policy_broadcast` jamais throttlés.

### #2 — Couverture companion du geste `policy_broadcast`

**Sévérité** : 🟡
**Fichier(s)** : `agent/shared/companion_test.go`

**Constat (review opus)** :

**Action** : corrigé automatiquement — scénarios succès (séquence = `[policy_broadcast]` exactement) et échec
(passe/rapport intacts, warning loggé).

### #3 — Log de hint inconnu dupliqué

**Sévérité** : 🟡
**Fichier(s)** : `agent/shared/handler_registry.go`, `agent/shared/handler_registry_list.go`

**Constat (review opus)** :
`desiredSpecs`/`desiredListSpecs` sont invoquées deux fois par passe (Test puis Apply) → 2 lignes de debug
identiques par item et par passe pour un hint inconnu.

**Action** : corrigé automatiquement — paramètre `logHints` (Test→true, Apply→false), valide car Apply n'est
jamais invoqué sans Test dans la même passe (dispatch engine §5). Tests « logged once per pass » ajoutés
(registry + registry_list).

### #4 — Course de la garde anti-double-lancement d'explorer

**Sévérité** : 🟡
**Fichier(s)** : `agent/windows/refresh_windows.go`

**Constat (review opus)** :
Si Windows relance le shell APRÈS la borne de poll de 3 s (poste lent), la re-vérification finale voyait 0
explorer et lançait un 2ᵉ explorer → fenêtre parasite (piège #3 de la story).

**Action** : corrigé automatiquement — délai de grâce `explorerRelaunchGrace` (1 s) + ultime re-check
`explorerPidsInSession` juste avant `exec.Command` ; course résiduelle inhérente (non testable hôte)
documentée dans le scénario runbook 43.1.3 avec l'hypothèse « relance rapide par Windows » explicitée.
