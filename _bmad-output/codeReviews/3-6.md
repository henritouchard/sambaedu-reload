## Détail des problèmes prioritaires

### #6 — Regex iso-legacy dupliquée 3× 🟠

**Fichier(s)** : `resources/views/pages/admin/ipxe/iso-windows/index.blade.php:89,168`, `app/Ipxe/Iso/Services/WindowsIsoUrlValidator.php`

**Constat sonnet** : La regex Livewire `rules()` accepte `.iso` générique alors que le service filtre Win10/11.

**Avis Opus (pertinence 2)** : Vrai problème + 3e duplication détectée dans `submitDownload()` (re-vérifie Win(10|11) regex avant ouverture modale). Triple source de vérité = drift garanti à la première modification.

**Solution** : extraire `WindowsIsoUrlValidator::ISO_NAME_REGEX` en **constante publique** et la référencer depuis le composant Livewire. Supprimer le re-check dans `submitDownload()`. Tightening `rules()` Livewire pour matcher la regex service.

**Action** : auto-fix sous Q5.

### #7 — Annulation en phase extracting non détectée 🟠

**Fichier(s)** : `app/Ipxe/Iso/Jobs/DownloadWindowsIsoJob.php:155-191`, `resources/views/pages/admin/ipxe/iso-windows/index.blade.php:467-474`

**Constat sonnet** : UI laisse cliquer "Annuler" en phase `extracting`, mais l'extraction continue blockingly.

**Avis Opus (pertinence 2)** : Le Job détecte le cancel entre curl et extract (refresh ligne 156) mais **pas** entre extract et success. Si annulé pendant extract, status passe `extracting → success` sans vérification. Le UI affiche un warning « L'annulation n'interrompt PAS le process en cours » mais l'écrasement du status `cancelled` par `success` est silencieux.

**Solutions possibles** :
- **A** : désactiver le bouton Annuler dès `status === extracting`
- **B** : garder le bouton visible mais ajouter un 2e `$download->refresh()` AVANT la transition vers Success ; si `cancelled` → ne pas écraser, juste log + return

**Action** : décision Q3 attendue.

### #8 — cascadeOnDelete users efface audit 🟠

**Fichier(s)** : `database/migrations/2026_05_21_120000_create_windows_iso_downloads_table.php:48`

**Constat sonnet** : Cascade supprime tout l'historique si user supprimé.

**Avis Opus (pertinence 2)** : En milieu scolaire, traçabilité des opérations serveur (qui a remplacé quelle ISO Windows) est importante pour audit. Un admin compromis pourrait initier des downloads malicieux puis supprimer son compte.

**Solution** : remplacer `->cascadeOnDelete()` par `->nullOnDelete()` et autoriser `initiated_by_user_id` nullable. Adapter modèle + serializer (`initiatedBy` déjà null-safe dans `serializeDownload`).

**Action** : décision Q2 attendue.

### #14 — Pas de lockForUpdate sur transitions 🟠

**Fichier(s)** : `app/Ipxe/Iso/Jobs/DownloadWindowsIsoJob.php:155-191`

**Constat sonnet** : `$download->refresh()` puis `$download->update(['status' => Extracting])` non transactionnel. Race possible avec `cancelDownload()` parallèle.

**Avis Opus (pertinence 2)** : Race **réelle** sur Postgres en concurrence write. Postgres UPDATE atomique au niveau row mais pas au niveau logique. Si admin clique Annuler exactement entre refresh et update, status `cancelled` est écrasé par `extracting`.

**Solution** : envelopper transitions dans `DB::transaction(fn() => { lockForUpdate + status check })`. Idem entre extract et success (cf #7).

**Action** : auto-fix sous Q5.

### Opus-A — Cleanup ISO partiel après échec curl absent 🟠

**Fichier(s)** : `app/Ipxe/Iso/Jobs/DownloadWindowsIsoJob.php:149-153` (`markFailed`)

**Avis Opus (pertinence 3 — TRÈS PERTINENT)** : Si curl échoue à mi-téléchargement, le fichier `.iso` partiel (plusieurs Go) reste sur `/var/sambaedu/unattended/install/os/iso/`. Pas de cleanup. 5 retries = ~30Go perdus sur VM 100Go.

**Solution** : dans `markFailed()`, best-effort `if (file_exists($isoPath)) { @unlink($isoPath); }`. Logger `ipxe.iso.cleanup.partial_removed`.

**Action** : auto-fix sous Q5.

### Opus-C — Job::failed() lock leak si row supprimée 🟡

**Fichier(s)** : `app/Ipxe/Iso/Jobs/DownloadWindowsIsoJob.php:228-249`

**Avis Opus (pertinence 2)** : `failed()` handler return **sans** release du lock si row null ou terminal. Edge case (admin clean DB manuellement) mais bloquant 7200s.

**Solution** : déplacer `$this->releaseLock(...)` AVANT les guards `if`.

**Action** : auto-fix sous Q5.

### Opus-E — Pas de DB::transaction() autour create+dispatch 🟠

**Fichier(s)** : `app/Ipxe/Iso/Services/WindowsIsoDownloadOrchestrator.php:68-92`

**Avis Opus (pertinence 2)** : Si dispatch réussit mais worker queue down (T0.5 manquant), le lock reste posé 7200s. Le `try/catch` ligne 93-101 release seulement sur exception immédiate, pas sur worker down.

**Solution** : envelopper dans `DB::transaction()`. Ajouter test `it_releases_lock_when_dispatch_fails`. Documenter dans D15 que worker queue down → row pending indéfini + cleanup manuel UI (cancel).

**Action** : auto-fix sous Q5.
