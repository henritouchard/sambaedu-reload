### #1 — `password_is_admin` migré vers `UserAdmin` : escalade de privilèges

**Sévérité** : 🔴 Critique (sécurité — escalade de droits)
**Fichier(s)** :
- `app/Services/Permissions/RightsMigrationService.php:71` (constante `SEEDED_PROFILE_TO_ROLE`)
- `tests/Feature/Integration/CalculateRightsRoundTripTest.php:120`

**Constat initial (review)** :
La matrice §5.3 est explicite :

> `password_is_admin (0x01)` → *(Délégation ciblée `user.password.init`, pas un rôle)*
> `PermissionService::grantDelegation($user, 'user.password.init')` plutôt qu'un rôle dédié

Or `SEEDED_PROFILE_TO_ROLE` mappe :
```php
'password_is_admin'  => SambaRole::UserAdmin,      // 0x01 — mappé UserAdmin (fallback seedé)
```

Le rôle `UserAdmin` porte 8 permissions (bitmask `0xFF`) : `user.password.init` + `user.read` + `user.modify` + `user.create.temp` + `user.assign.right` + `user.delegate` + `share.view` + `share.refresh`. Un utilisateur qui n'avait historiquement que le droit de réinitialiser les mots de passe (`0x01`) reçoit 7 droits supplémentaires qu'il n'avait jamais eus, dont `user.assign.right` (attribution de droits à d'autres users) et `user.delegate`.

Le test `CalculateRightsRoundTripTest::round_trip_seeded_profile_produces_consistent_bitmask` ne détecte pas ce problème car il utilise un **test de sous-ensemble** (`$expectedBits & $spatieSourceBitmask === $expectedBits`) : `0x01 & 0xFF === 0x01` est vrai, donc le test passe même si le bitmask Spatie retourné est `0xFF` au lieu de `0x01`.

**Avis Opus** : **Pertinence 3/3 — critique sécurité confirmée à 100 %.**

Vérifications effectuées :
1. **Matrice §5.3 (ligne 168)** : « `password_is_admin` (0x01) → *(Délégation ciblée)* `PermissionService::grantDelegation($user, 'user.password.init')` plutôt qu'un rôle dédié ». La prescription produit est sans ambiguïté.
2. **Matrice §4.1 (ligne 102)** : `password_is_admin` est seedé avec `SE_USER_PASSWORD_INIT` = `0x01` (un seul bit).
3. **Code legacy** (`sambaedu/includes/ldap.inc.php:742`) : confirmation directe — `groupadd($config, "password_is_admin", ..., SE_USER_PASSWORD_INIT)`. Le bitmask réel est bien 0x01, **pas** 0xFF.
4. **Code review** (`RightsMigrationService.php:71`) : `'password_is_admin' => SambaRole::UserAdmin` — **mapping erroné**. UserAdmin embarque 8 permissions dont `user.assign.right` (capacité à attribuer des droits à d'autres users) et `user.delegate`. Un user qui n'avait que le droit de réinitialiser les mots de passe se retrouve avec la pleine gestion annuaire.
5. **Test round-trip** (`CalculateRightsRoundTripTest.php:120`) : le data provider mappe explicitement `'password_is_admin' => SambaRole::UserAdmin` et l'assertion subset (ligne 162-171) `$expectedBits === $expectedBits & $spatieSourceBitmask` est satisfaite tautologiquement quand `expectedBits ⊂ spatieSourceBitmask`. Le test est complice du bug.

**Nuance sur la solution Sonnet (1)** : `permissionService->grantDelegation($user, 'user.password.init', null)` **ne compile pas** — la signature de `grantDelegation` (cf. `PermissionService.php:124-130`) exige `WorkstationGroup $group` (non-nullable typehint). Pour réaliser une délégation **non scopée** (globale), deux options techniquement valides :
- (a) `$user->givePermissionTo('user.password.init')` — permission Spatie directe, sans rôle. Simple, mais pas tracée dans `delegation_history`.
- (b) Étendre `grantDelegation` pour accepter `?WorkstationGroup` (nouveau scope global, cohérent avec hiérarchie matrice §7 « exclusion scopée > global > délégation positive scopée »). Plus invasif mais aligné sur le modèle.

**Solution recommandée** : (a) `$user->givePermissionTo('user.password.init')` en attendant décision de Henri. C'est le minimum de surface de changement et reste fidèle à la matrice (la matrice cite `grantDelegation` mais explicitement « pas un rôle dédié » — donc la permission directe respecte l'esprit).

**Verdict tranché** : **bloquant non-négociable**. Cette escalade affecte 32 occurrences de `SE_USER_PASSWORD_INIT` dans le legacy (matrice §6 ligne 186), donc tout user historiquement membre du groupe `password_is_admin` (typiquement un agent administratif limité) reçoit après migration `user.assign.right` + `user.delegate` + `user.modify` + `user.create.temp` + `share.view` + `share.refresh`. Pour un SER multi-tenant, c'est inacceptable.

**Action** : décision Henri requise (question #1). Recommandation Opus = solution (a) avec correctif test round-trip en assertion d'égalité stricte (`assertSame(0x01, $bitmask & 0xFF)`) pour `password_is_admin`.

**Correction appliquée** (2026-04-27, décision Henri 2026-04-25 — solution (a)) :

- `password_is_admin` retiré de la constante `SEEDED_PROFILE_TO_ROLE` dans `RightsMigrationService`. Nouvelle constante `SEEDED_PROFILE_TO_DIRECT_PERMISSION = ['password_is_admin' => 'user.password.init']` qui pilote un nouveau cas spécial dans `migrateRightsGroupAssignments()`.
- Nouvelle méthode privée `migrateProfileAsDirectPermission(cn, permissionName, ...)` qui pose la permission directe via `$user->givePermissionTo($permissionName)` (idempotent — pas de doublon dans `model_has_permissions`). Aucun rôle Spatie n'est attribué.
- Test round-trip `CalculateRightsRoundTripTest::round_trip_seeded_profile_produces_consistent_bitmask` désormais **désképé** pour `password_is_admin` (le `markTestSkipped` est retiré, branche conditionnelle `$expectsDirectPermissionInsteadOfRole` qui vérifie `roles()->count() === 0` ET `hasDirectPermission('user.password.init')`).
- Nouveaux tests dédiés (`tests/Unit/Services/Permissions/RightsMigrationServiceTest`) : `it_grants_direct_user_password_init_for_password_is_admin_without_role_escalation` (couvre l'absence d'escalade UserAdmin/UserAssignRight/UserDelegate) + `password_is_admin_migration_is_idempotent_across_multiple_runs`.

### #2 — Parse CN délégation cassé pour parcs avec underscore dans le nom

**Sévérité** : 🟠 Important (perte silencieuse de délégations en production)
**Fichier(s)** :
- `app/Services/Permissions/RightsMigrationService.php:350-361`

**Constat initial (review)** :
Le parsing du CN utilise `strrpos($body, '_')` pour séparer `<right>` de `<parc>` :

```php
$lastSep = strrpos($body, '_');
$right = substr($body, 0, $lastSep);
$parc  = substr($body, $lastSep + 1);
```

Le commentaire dans la story mentionne comme edge case :
> "Délégations scopées : le parsing du format `<right>_<parc>` (ou `no_<right>_<parc>`) supporte-t-il les parcs avec underscore dans leur nom ? (edge case : `computer.control_salle_info_bat_A`)"

Pour `cn = 'computer.control_salle_info_bat_A'` :
- `body = 'computer.control_salle_info_bat_A'`
- `strrpos` → dernier `_` avant `A`
- `right = 'computer.control_salle_info_bat'` ← **invalide**
- `parc = 'A'` ← **invalide**

Résultat : `Permission::findByName('computer.control_salle_info_bat')` retourne `null` → rapporté comme `permission_not_found` → délégation silencieusement ignorée. Aucune erreur bloquante, mais des délégations légitimes sont perdues en production sans alerte claire.

Le problème est algorithmique : le format `<right>_<parc>` est ambigu si `<parc>` contient des `_`. Le format legacy (`sambaedu/includes/ldap.inc.php:4407-4410`) ne documente pas les contraintes de nommage des parcs.

**Avis Opus** : **Pertinence 2/3 — réel, mais éclipsé par le problème #10 plus structurel.**

Vérifications :
- Le code (`RightsMigrationService.php:350-361`) utilise bien `strrpos($body, '_')` après stripping du préfixe `no_`. Le bug de parsing pour parcs à underscore est confirmé.
- **Mais** : le problème #10 (ci-dessous) montre que le format réel legacy n'est PAS `computer.elevate_<parc>` mais `manage_<parc>` / `view_<parc>` / `<level_legacy>_<parc>`. Donc le parsing actuel est de toute façon inopérant en prod indépendamment de l'underscore dans le nom du parc.
- Si le format de migration est révisé pour matcher le legacy réel, l'ambiguïté underscore subsiste.

**Solution Sonnet 1 (itérer SambaPermission::cases())** : ne fonctionne pas pour le legacy réel — les permissions Spatie utilisent des `.`, le legacy stocke des noms type `manage`, `view`, `manage_install`. La solution correcte est plutôt de **valider le suffixe `<parc>` contre la table `workstation_groups`** : pour chaque position de `_` dans le body, tester si la suffix-string post-`_` correspond à un `WorkstationGroup` existant en DB. Le premier match (en partant du suffixe le plus long) est pris. C'est O(n × m) avec n = positions de `_` et m = lookup DB, mais peut être optimisé en chargeant la liste des parcs en mémoire.

**Action** : à corriger conjointement avec #10. La solution Sonnet 1 est inadaptée au format legacy réel.

**Solutions possibles** :
1. **(Recommandée)** Parser en cherchant d'abord un préfixe valide de permission (les noms de permissions Spatie utilisent des `.` jamais des `_`) : itérer les permissions connues (`SambaPermission::cases()`) et chercher si `$body` commence par `$perm->value . '_'`. Si un match unique trouvé → split propre. Complexité O(n) sur le nombre de permissions (19 max).
2. Documenter le format comme "parcs sans underscore" et logger un warning explicite si `Permission::findByName` échoue en suggérant un problème de format.
3. Interroger les WorkstationGroups en DB pour valider le parc en premier : essayer de matcher `$parc = substr($body, firstDotPos+1...)` progressivement (risqué si le format change).

**Action** : décision Henri requise (question #2 ci-dessus).

**Correction appliquée** (2026-04-27, conjointement avec #10) : nouveau parser via regex strict `/^(no_)?(manage|view|rdp)_(.+)$/` dans `RightsMigrationService::parseLegacyDelegationCn()`. Le 3ᵉ groupe capture (greedy) tout ce qui suit `<level>_`, donc un parc nommé `salle_info_bat_A` est correctement extrait en entier. Le regex contraint simultanément le préfixe `no_` optionnel et la liste fermée de levels legacy `{manage,view,rdp}`, ce qui élimine d'office les CN au format Spatie hypothétique (ils tombent en `delegation_parse_error` avec log warning explicite — review #12). Test dédié `it_parses_parc_name_with_underscores_correctly` ajouté.

### #3 — Test round-trip `password_is_admin` masque le bug d'escalade

**Sévérité** : 🟠 Important (test green alors que comportement incorrect)
**Fichier(s)** :
- `tests/Feature/Integration/CalculateRightsRoundTripTest.php:125-172`

**Constat initial (review)** :
L'assertion du data provider `seededProfilesProvider` utilise un **check de sous-ensemble** :

```php
$this->assertSame(
    $expectedBits,
    $expectedBits & $spatieSourceBitmask,  // subset check, pas equality!
    ...
);
```

Pour `password_is_admin` : `$expectedBits = 0x01`, `$spatieSourceBitmask = 0xFF` (UserAdmin). L'assertion vérifie `0x01 === (0x01 & 0xFF) === 0x01` → **passe**. Mais le bitmask réel `0xFF` contient 7 droits en plus qui ne sont jamais vérifiés.

**Avis Opus** : **Pertinence 2/3 — confirmé. Le test est complice du bug #1.**

Vérification : ligne 162-171 de `CalculateRightsRoundTripTest.php`, l'assertion est bien `$expectedBits === $expectedBits & $spatieSourceBitmask`. Pour `password_is_admin`, `expectedBits = 0x01` et `spatieSourceBitmask` après mapping `UserAdmin` = `0xFF` filtré ComputerView = `0xFF` (pas de bit ComputerView dans 0xFF). Donc `0x01 === 0x01 & 0xFF === 0x01` → green. Le bug est masqué.

**Nuance** : la solution dépend de #1. Si Henri choisit de garder l'élévation `password_is_admin → UserAdmin`, alors le test reflète une décision produit et n'est plus un bug. Sinon, le test doit ajouter une assertion d'égalité stricte sur les bits attendus pour les profils mono-droit. Solution Sonnet 1 (`assertSame(0, $bitmask & ~0x01)`) est valide.

**Solution Opus complémentaire** : ajouter une 4e colonne au data provider `seededProfilesProvider` pour distinguer "test subset" (ComputerAdmin où ServerAdmin manque côté Spatie) vs "test equality" (UserAdmin, ReferentNumerique). Cela rend explicite la sémantique attendue par profil.

**Action** : correction conditionnelle à #1.

**Solutions possibles** :
1. Ajouter une assertion de borne supérieure pour `password_is_admin` : `assertSame(0, ($spatieSourceBitmask & ~0x01), "Aucun bit supplémentaire ne doit être présent")`.
2. Une fois #1 corrigé (délégation ciblée), réécrire ce test : `password_is_admin` doit donner un bitmask `0x01` en scope, `0x00` sans scope.
3. Séparer les cas data-provider : les profils où le bitmask Spatie peut être supérieur au legacy (ComputerAdmin, SuperAdmin), vs les profils où il doit être identique (UserAdmin, ReferentNumerique) vs les profils délégations (password_is_admin).

**Action** : correction conditionnelle à la résolution de #1.

**Correction appliquée** : data provider `seededProfilesProvider` enrichi d'une 4e colonne `assertionMode` (`equality` | `subset`). Tous les profils sont en `equality` SAUF `computer_is_admin` qui reste en `subset` (Spatie embarque `WpkgAssign 0x1000` absent du legacy 0xEF00, modélisation intentionnelle matrice §5.2). Le test `round_trip_seeded_profile_produces_consistent_bitmask` :
- En mode `equality` : assertion stricte `assertSame($expectedBits, $actualBits)` après strip ComputerView + ServerAdmin.
- En mode `subset` : conserve l'ancienne assertion subset `$expectedBits & $spatieSourceBitmask`.

### #4 — Heuristique DN parc fragile : faux positifs de reporting si OU non standard

**Sévérité** : 🟠 Important (migration incomplète sans indication claire)
**Fichier(s)** :
- `app/Services/Permissions/RightsMigrationService.php:393-410`

**Constat initial (review)** :
Quand `resolveUserFromDn($memberDn)` retourne `null` pour un DN membre, le code tente de détecter si c'est le DN du parc (à ignorer) ou un user inconnu (à rapporter). Deux heuristiques :

```php
// Heuristique 1 : contient le nom du parc ET pas de 'cn='
if (stripos($memberStr, $parc) !== false && stripos($memberStr, 'cn=') === false) {
    continue;
}
// Heuristique 2 : OU = computers ou parcs
if (preg_match('/ou=computers/i', $memberStr) === 1 || preg_match('/ou=parcs/i', $memberStr) === 1) {
    continue;
}
```

**Problème heuristique 1** : un DN de parc standard en AD est `CN=salle-a12,OU=Parcs,DC=test,DC=local`. Ce DN **contient** `cn=` → la condition `&& stripos($memberStr, 'cn=') === false` est **fausse** → l'heuristique 1 ne filtre pas le DN de parc et tombe sur l'heuristique 2.

**Problème heuristique 2** : si les parcs sont organisés dans une OU custom (ex. `OU=Groupes`, `OU=Salles`) au lieu de `OU=Parcs` ou `OU=Computers` → l'heuristique 2 échoue → le DN du parc est rapporté comme `user_not_found` (faux positif dans le rapport). La migration continue sans crash mais le rapport est pollué.

Le test couvre uniquement `OU=Parcs,DC=test` ce qui fait passer l'heuristique 2 sans tester le cas `OU=Groupes`.

**Avis Opus** : **Pertinence 2/3 — confirmé sur les deux problèmes.**

Vérification heuristique 1 : pour `CN=salle-a12,OU=Parcs,DC=test,DC=local`, `stripos($memberStr, 'cn=')` retourne `0` (position 0). En PHP, `0 === false` est `false`, donc la condition `&& stripos(...) === false` est fausse → l'heuristique 1 est effectivement court-circuitée. Sonnet a raison.

Vérification heuristique 2 : on tombe alors sur `preg_match('/ou=computers|ou=parcs/i')`. Pour les fixtures de test (`OU=Parcs`), match. Pour un AD prod avec `OU=Salles` ou `OU=Groupes,OU=Etablissement` (cas SER multi-tenant), pas de match → faux positif `user_not_found`. La pollution du rapport peut masquer de vrais users introuvables si volume élevé.

**Solution Opus** : exploiter `WorkstationGroup::findByAdDn($memberDn)` (méthode existante ligne 503 du modèle) — pattern Laravel idiomatique. Si le DN matche un parc Eloquent → ignorer silencieusement. Sinon → reporter `user_not_found`. Cela élimine les heuristiques fragiles et profite de la source de vérité DB.

**Mitigation alternative** : le code actuel ne crashe pas, juste pollue le rapport. Risque opérationnel limité — un opérateur attentif voit que c'est le DN du parc et l'ignore. Mais en run automatisé (cron post-installation), la métrique `cas_non_mappables` n'a pas de sens.

**Action** : refactor recommandé via `findByAdDn`. À corriger en même temps que #2.

**Solutions possibles** :
1. **(Recommandée)** Approche par résolution inverse : si `resolveUserFromDn` retourne `null`, essayer de résoudre comme `WorkstationGroup` via le même DN (chercher `WorkstationGroup::where('dn', $memberDn)` ou par CN extrait). Si match → ignorer silencieusement. Si non-match → rapporter.
2. Logger les DNs filtrés par heuristique à niveau `debug` pour permettre un audit post-migration sans bloquer le flux.
3. Documenter la limitation dans le runbook QA (5.4) : "Si des DNs de parcs sont reportés comme `user_not_found`, vérifier que l'OU des parcs en LDAP correspond à `ou=computers` ou `ou=parcs`."

**Action** : à discuter avec Henri (acceptable en l'état si la VM target a des parcs dans `ou=Parcs` ou `ou=Computers`).

**Correction appliquée** (2026-04-27, décision Henri 2026-04-25) : les heuristiques `stripos`/`preg_match('ou=...')` sont remplacées par une nouvelle méthode privée `RightsMigrationService::isKnownWorkstationGroupDn(string $dn, WorkstationGroup $currentGroup): bool` qui combine deux stratégies :
1. Match cheap par CN extraction (`/^cn=([^,]+)/i` puis `strcasecmp` sur le `name` du parc en cours de traitement).
2. Lookup DB sur la colonne `ad_dn` via `WorkstationGroup::findByAdDn()` — encapsulé dans un `try/catch` car le schéma de test (`tests/Traits/CreatesPermissionSchema.php`) n'a pas la colonne `ad_dn`.

Aucun parc DN n'est plus rapporté `unmappable user_not_found` quand la résolution est correcte. Test `it_creates_positive_delegation_from_legacy_manage_cn` valide le filtrage du parc DN au format `CN=salle-a12,OU=Parcs,DC=test,DC=local` (`assertEmpty($report['unmappable'])`).

### #5 — Absence de transaction DB globale sur `migrate()` : rollback impossible

**Sévérité** : 🟠 Important (intégrité des données en cas d'interruption)
**Fichier(s)** :
- `app/Services/Permissions/RightsMigrationService.php:97-127` (méthode `migrate`)
- `app/Console/Commands/MigrateRightsToSpatieCommand.php:62-72`

**Constat initial (review)** :
La méthode `migrate()` exécute jusqu'à plusieurs milliers d'assignations `assignRole` + `grantDelegation` sans transaction DB englobante. Si la commande est interrompue en cours de migration (signal SIGTERM, timeout PHP, exception DB mid-run), l'état Spatie est **partiellement migré** :
- Certains users auront leurs rôles, d'autres non.
- La clé unique `Delegation` protège contre les doublons lors d'un re-run, mais `model_has_roles` peut avoir des entrées partielles sans constraint de re-run (Spatie v6 `assignRole` est additif, pas idempotent d'une session à l'autre si on ajoute des groupes LDAP après coup).

Dans un contexte one-shot en production, un re-run complet récupère la situation (idempotence), mais :
1. Le rapport du 1er run tronqué est incomplet et trompeur.
2. Le fichier log est persisté via rename atomique **après** le retour de `migrate()` — s'il y a une exception non catchée, aucun log n'est persisté.

**Avis Opus** : **Pertinence 1/3 — réel mais marginal pour une commande one-shot idempotente.**

Vérification :
- `migrate()` n'a effectivement aucune `DB::transaction()` enveloppante.
- Le `try/catch` global est dans `MigrateRightsToSpatieCommand::handle()` (ligne 62-72), il catche `Throwable` mais retourne `FAILURE` sans appeler `persistReportLog()`. Donc le rapport est perdu en cas d'exception.

**Nuance Opus** : l'option 1 (transaction DB) est **risquée** en pratique :
- `assignRole` Spatie déclenche des observers, des cache invalidations (`PermissionRegistrar::forgetCachedPermissions`), et potentiellement des jobs queue (`SyncGpoJob`). Une transaction longue qui rollback peut laisser le cache Spatie incohérent et les jobs déjà dispatchés non-rollbackable.
- Pour des milliers d'assignations, une transaction unique tient les locks longtemps.
- Spatie v6 gère ses propres transactions internes via Eloquent observers — risque de transaction imbriquée subtile.

**Recommandation Opus** : retenir uniquement la solution Sonnet 2 (déplacer `persistReportLog($report)` dans un bloc `finally` côté commande), trivial et sans effet de bord. Pas de transaction globale. Documenter dans le runbook que la commande est idempotente et qu'un re-run récupère.

**Action** : correction quick-win recommandée (try/finally autour de `persistReportLog`). Pas de transaction.

**Solutions possibles** :
1. Envelopper `migrateRightsGroupAssignments()` et `migrateScopedDelegations()` dans `DB::transaction(...)`. Si exception mid-run → rollback complet → état cohérent → re-runnable. Attention : peut entrer en conflit avec les transactions de `updateOrCreate` imbriquées dans Spatie.
2. **(Alternative légère)** Persister le rapport partiel même en cas d'exception dans la commande : déplacer `$this->persistReportLog($report)` dans un bloc `finally`.
3. Documenter la limitation dans le runbook QA 5.2 : "En cas d'interruption, re-lancer la commande (idempotente)."

**Action** : l'option 2 (persist dans `finally`) est minimale et ne bloque pas la story. L'option 1 (transaction) est plus robuste mais nécessite validation de compatibilité Spatie.

**Correction appliquée** : `app/Console/Commands/MigrateRightsToSpatieCommand.php::handle()` refactoré en pattern `try/finally` (option 2) — pas de `DB::transaction` englobante (les observers Spatie / cache permissions / jobs queue dispatchés rendent la transaction risquée). Concrètement :
- Un rapport partiel par défaut est initialisé en début de `handle()` (avec un warning « Migration interrompue — rapport partiel »).
- Le bloc `try { migrate ; renderReport }` est suivi d'un `catch (Throwable)` qui logge l'exception, ajoute un warning au rapport et passe l'exit code à `FAILURE`.
- Un bloc `finally` appelle systématiquement `persistReportLog($report)` en mode run effectif (pas en dry-run), garantissant qu'on dispose d'une trace diagnostiquable même si la migration explose mid-run.
- Le service `RightsMigrationService` n'utilisait pas de `DB::transaction` : aucune modification nécessaire côté service.
