## Détail des problèmes

### #M6 — Edit-form efface silencieusement les professeurs principaux

**Sévérité** : 🔴 Critique
**Fichier(s)** : `app/Services/UserGroupService.php:138-175` ; déclencheurs `resources/views/pages/users/groups/[id]/index.blade.php:88,143`

**Constat (finding manqué par sonnet, confirmé par opus puis vérifié dans le code)** :
`syncRoleAwareAdGroupMembers` synchronise TOUJOURS la 3ᵉ cible `PP_<base>` (l.919). `removeMember()` et `save()` de l'edit-form appellent `updateGroup` avec `user_ids` mais **sans** la clé `head_teacher_ids`. L'ancien code posait alors `$headTeacherUserIds = []` → `PP_<base>` vidé en AD → le read-back `syncFromAd` relit un `PP_` vide → efface le pivot `is_head_teacher`. **Résultat : toute édition de membres d'une classe (même sans rapport avec les PP) supprime tous ses professeurs principaux, sans erreur ni avertissement.** Feature auto-destructrice en exploitation normale.

**Avis Opus** : 3/3. Vérifié de bout en bout (l.919 PP toujours écrit ; appelants edit-form sans `head_teacher_ids` ; chemin read-back l.150-152). Régression silencieuse réelle.

**Correctif appliqué** : distinction **clé absente** vs **`[]` explicite**. Quand `head_teacher_ids` est absent du payload, `$headTeacherUserIds` est dérivé du pivot existant (`$group->users()->wherePivot('is_head_teacher', true)->pluck('users.id')`) → les PP existants sont préservés. Un `[]` explicite (la section UI qui retire tous les PP) reste un effacement volontaire. L'intersection avec `$selectedUserIds` (l.914-918) garantit qu'un PP retiré des membres est bien retiré de `PP_`.

**Action** : ✅ Corrigé automatiquement + test de régression `it_preserves_head_teachers_when_updateGroup_omits_head_teacher_ids`.
