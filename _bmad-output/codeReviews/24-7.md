## Détail des problèmes

### #1 — `forceSyncGroup`/`forceSyncWorkstation` sans Gate

**Sévérité** : 🟠
**Fichier(s)** : `resources/views/pages/parc/groups/[id]/index.blade.php`, `machines/[id]/index.blade.php`, les 2 partials conformité

**Constat (review fable)** : les deux pages sont derrière `can:viewAny-workstationGroup` (lecture).
Toutes les mutations voisines de la page groupe sont gatées `computer.control` ; les actions force-sync
n'avaient aucun check → tout utilisateur voyant la page pouvait forcer la resynchro.

**Évaluation orchestrateur** : Pertinence 3 — vérifié dans le code (aucun `Gate::` dans les 2 méthodes,
pattern `Gate::allows('computer.control') + toastAccessDenied()` partout ailleurs sur la page groupe).

**Action** : corrigé automatiquement — guard serveur `computer.control` dans les 2 actions + boutons
masqués `@can('computer.control')` côté Blade + test du chemin refusé
(`test_force_sync_denied_without_computer_control`). Permission dédiée = Q1.

### #2 — Incohérence filtre SQL vs badge/compteurs sur les muets

**Sévérité** : 🟠
**Fichier(s)** : `app/Repositories/WorkstationGroupRepository.php` (`applyConformityFilter`)

**Constat (review fable)** : badge et compteurs appliquent le priming « muet » (un poste muet avec drift
est classé `silent`), mais les branches `exceptions` et `drifted_allowed` du filtre SQL n'excluaient pas
les muets (seul `compliant` le faisait) → compteur « En écart » = 3, filtre « En écart » = 4 lignes.

**Évaluation orchestrateur** : Pertinence 3 — confirmé en lisant les deux implémentations ; la Completion
Note du dev prétendait l'alignement, faux pour ces deux branches.

**Action** : corrigé automatiquement — clause `notSilent` factorisée appliquée aux 3 branches de statut +
docblock aligné + test `test_silent_workstation_with_drift_stays_out_of_exceptions_filter`
(filtre + compteurs cohérents).
