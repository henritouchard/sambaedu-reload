## Détail des problèmes

### #3 — `handleJoin` ret=0/1 perd `role`/`ou` → poste joint dans le mauvais OU AD

**Sévérité** : 🔴 (sonnet l'avait classé 🟠, opus relève à pertinence 3/3 = bug terrain)
**Fichier(s)** : `app/Ipxe/Http/Controllers/IpxeWindowsActionController.php:255-284` + `app/Ipxe/Services/WindowsPostInstallTracker.php:272-285` (recordJoinInitiated) + `resources/views/ipxe/windows/cmd/join.blade.php:21,39,54`

**Constat initial (sonnet)** :
`handleJoin` ret=0/1 invoque `buildJoin($ws, $role, $ou)` où `$role`/`$ou` viennent de la requête HTTP courante. Le template `join.blade.php` ne re-envoie PAS `role`/`ou` dans les curls internes ret=0/1/2 → au 2e POST depuis le poste, `$role=''`, `$ou=''` → `Add-Computer -OUPath ''`.

**Avis Opus** : pertinence 3/3. Bug terrain confirmé après lecture directe. Régression silencieuse : install passe (200 OK), poste prend le domaine, mais joint dans `CN=Computers` au lieu de `OU=salle1,…` → GPOs ne s'appliquent pas, l'admin ne le remarque que plus tard. Le legacy résolvait `role`/`ou` depuis APCu serveur-side (`get_action_value($uuid, 'role')`). SE5 a une colonne JSONB `programmed_action` dédiée à exactement cet usage (D7).

**Solutions possibles** :
1. **(retenue)** Persister `role`+`ou` dans `programmed_action` à `recordJoinInitiated`, lire depuis DB dans `handleJoin` ret=0/1 (pattern `handleRenomme` qui fait déjà `paOf($ws)['role']`).
2. Modifier `join.blade.php` pour re-envoyer `role`/`ou` dans le curl `-F` (divergence template vs legacy plus visible, fragile si poste tronque les params).

**Action** : Corrigé automatiquement via solution 1 (convergence sonnet + opus, pattern déjà établi par handleRenomme).
