## Détail des problèmes

### P1 — AC#1 habilitation non livrée pour le délégué positif-seul

**Sévérité** : 🟠 — **Pertinence Opus** : 3/3
**Fichier(s)** : `capabilities-tab.blade.php` (`authorizeUpstream`), `app/Policies/CapabilityPolicy.php` (`modify`), `tests/Feature/Livewire/Parc/CapabilitiesTabCustomizeScopingTest.php`

**Constat initial (review sonnet)** : un délégué disposant d'une délégation positive `app.customize` scopée sur le parc A (SANS droit global) passe `guardCustomize()` (gate scopé → délégation positive → autorisé, mount OK) MAIS est bloqué dès `openAdd`/`openEdit`/`saveOverride`/`removeOverride` par `authorizeUpstream` → `Gate::authorize('modify-capability')` → `CapabilityPolicy::modify` qui exige `hasPermission($user,'app.customize')` **GLOBAL**. Le test AC#1 n'asserte que `assertStatus(200)` au mount, pas les mutations. Le write-through n'est prouvé qu'avec l'acteur M4 (droit global + exclusion négative).

**Avis Opus** : confirmé (chaîne vérifiée jusqu'à `ChecksPermissions::hasPermission` = `$user->can()` global Spatie, jamais scopé). **Mais point décisif** : le correctif **sécurité M4 est complet** (négative honorée, tampering bloqué, 0 écriture/trace hors-périmètre), et 29.6 **ne régresse rien** — avant 29.6, `guardCustomize` était déjà global donc le délégué positif-seul était déjà bloqué (au mount) ; 29.6 déplace seulement le blocage du mount vers `authorizeUpstream`. AC#1 promettait une habilitation **qui n'a jamais existé** et qui exige de scoper AUSSI `modify-capability`. Or **`modify-capability` est DUAL-PURPOSE** : consommé par `capabilities-tab` (override par-parc, à scoper) ET par `parc-defaults/registry-tab` (défaut diffusé Broadcast = réglage global, à garder global). Le scoper ici empièterait sur 29.2 et risquerait une régression de la surface défaut global.

**Action** : ⏳ **Reporté** — suivi `29-8` créé (scoper le plancher de `modify-capability` par surface). AC#1 **annoté** dans le fichier story (sécurité M4 satisfaite / habilitation du délégué positif reportée). Aucun changement de code dans 29.6 (frontière 29.2 respectée).

### P3 — Double requête WorkstationGroup

### P4 — Toast trompeur

**Sévérité** : 🟡 — **Pertinence Opus** : 2/3 (sous-évalué par sonnet)
**Fichier(s)** : `capabilities-tab.blade.php` (`authorizeUpstream`)

**Constat** : le `catch (AuthorizationException)` affichait toujours « verrouillée par un contrat amont », alors que `modify-capability` échoue pour DEUX causes (verrou amont OU droit manquant). **Opus** : ce n'est pas purement « pré-existant 29.2 » — 29.6 rend le toast trompeur **nouvellement atteignable** (guard scopé qui laisse passer un délégué sans droit global), et la **surface sœur `registry-tab.blade.php:224-234` a DÉJÀ le correctif** (« [P1a review] »). **Action** : ✅ **Corrigé** — désambiguïsation portée dans `capabilities-tab::authorizeUpstream` : si `isCapabilityLocked` → message amont ; sinon « Vous n'avez pas le droit de modifier cette capacité. » (calqué sur `registry-tab`).
