## Détail des problèmes

### P-1 — Injection shell distante via env vars SSH

**Sévérité** : 🟠 — **Pertinence Opus : 2**
**Fichier(s)** : `tests/e2e/global-setup.ts:49`

**Constat initial (review)** :
`const remoteCommand = \`cd ${projectPath} && ${artisan} e2e:reset\`` — `E2E_PROJECT_PATH`/`E2E_ARTISAN` non sanitisées sont interprétées par le `sh -c` du sshd distant. `execFileSync` protège du shell local uniquement.

**Avis Opus** :
Réel mais faible risque : ces vars sont fournies par henri sur son propre poste (surface self-inflicted). Single-quoting = bonne pratique peu coûteuse.

**Solutions possibles** :
1. Single-quoter les segments interpolés (`'${projectPath.replace(/'/g, "'\\''")}'`).
2. Statu quo documenté.

**Action** : correction automatique (défense en profondeur triviale).

### P-2 — Config cache hardcodé dans le garde-fou destructif

**Sévérité** : 🟠 — **Pertinence Opus : 3 (le plus important du lot)**
**Fichier(s)** : `app/Console/Commands/Concerns/GuardsE2eDatabase.php:71,89` (hérité de `DbSeedCommand`)

**Constat initial (review)** :
Le garde-fou lit en dur `bootstrap/cache/config.php` ; `APP_CONFIG_CACHE` (déjà utilisé par `phpunit.xml` → `config-testing.php`) est ignoré → le garde-fou peut inspecter une autre config que celle que l'app utilise réellement.

**Avis Opus** :
Confirmé, noté 3 : seul vecteur de contournement réaliste du garde-fou (valider sur une config, dropper sur une autre). Même biais que `DbSeedCommand`, mais l'enjeu est plus élevé sur un chemin destructif. N-4 en est l'angle mort côté tests (`Config::set` ignorés si un cache fichier existe).

**Solutions possibles** :
1. `app()->getCachedConfigPath()` dans `GuardsE2eDatabase` + `DbSeedCommand` (cohérence) — N-4 corrigé par construction.
2. Documenter la limitation dans le code du garde-fou.

**Action** : en attente de décision utilisateur (question 1).

### P-3 / P-9 / N-1 — Sessions résiduelles sur la template Postgres

**Sévérité** : 🟠 — **Pertinence Opus : P-3=2, P-9=1, N-1=3 (trouvé par Opus)**
**Fichier(s)** : `app/Console/Commands/E2eResetCommand.php:67`, `app/Console/Commands/Concerns/UsesMaintenanceConnection.php:88-95`, `app/Console/Commands/E2eBuildTemplateCommand.php:105-126`

**Constat initial (review)** :
`CREATE DATABASE … TEMPLATE` échoue si une session est ouverte sur la template ; le reset ne terminate que la cible, jamais la template.

**Avis Opus** :
Unifie P-3 + P-9 + N-1 : le scénario concret est le **premier reset juste après un build-template** (connexions migrate/seed sur la template pas forcément fermées côté serveur). `DB::purge` ne ferme que les connexions du process PHP courant. Correction à plus forte valeur du lot. Ajouter aussi un scénario QA 2.4 « reset juste après build-template ».

**Solutions possibles** :
1. Extraire `terminateSessions(string $database)` du trait et l'appeler sur la template avant `createFromTemplate` dans `e2e:reset`.

**Action** : correction automatique.
