## Détail des problèmes corrigés automatiquement

### #2 — Templates enrollment ne propagent pas username/password

**Sévérité** : 🔴 Critique — **Pertinence Opus : 3**
**Fichier(s)** : `resources/views/ipxe/enrollment/{name,room,parc-add,parc-remove,byod}.blade.php`

**Constat** : Aucun des 5 templates enrollment ne re-déclare `param username ${username}` et `param password ${password:base64}` dans son bloc `params`. Le 1er hit (chain depuis `admin.blade.php`) passe la garde car les params sont fournis par l'appelant. Mais le 2ème hit (après `read name` → `chain ##params` local) re-construit les params sans creds → `MissingCredentials` → `auth_failed` → enrollment **complètement cassé** en flow multi-étapes.

**Avis Opus** : Confirmé empiriquement par grep. iPXE conserve `${username}`/`${password}` en mémoire après `:login` (settings store persistant cross-chain). La correction est triviale : ajouter les deux lignes dans chaque bloc `params`.

**Solution appliquée** : ajout `param username ${username}` + `param password ${password:base64}` dans les 5 templates enrollment.

### #3 — Fallback `decodePassword` raw défectueux

**Sévérité** : 🟠 Important — **Pertinence Opus : 2**
**Fichier(s)** : `app/Ipxe/Services/IpxeAuthService.php:161-170`

**Constat** : `base64_decode($value, true)` ne retourne `false` que pour les caractères hors alphabet b64. Un password comme `mypassword` (composé uniquement de [a-z]) est décodé en binaire aléatoire sans déclencher le fallback raw → bind LDAP échoue silencieusement avec garbage.

**Avis Opus** : Confirmé. Firmware iPXE standard envoie toujours base64 (cf. `known.blade.php`), donc bug latent. Durcissement = valider la chaîne via regex `^[A-Za-z0-9+/]+={0,2}$` ET `strlen % 4 === 0` AVANT de décider décodage vs raw.

**Solution appliquée** : guard regex sur format b64 strict avant `base64_decode`. Sinon retourne raw.

### #5 — bypassIpxeAuth masque retrait de `guard()`

**Sévérité** : 🟠 Important — **Pertinence Opus : 2**
**Fichier(s)** : `tests/Support/IpxeAuthTestHelper.php` + `tests/Feature/Ipxe/IpxeAdminAuthTest.php`

**Constat** : Le helper court-circuite `IpxeAuthService::authorize()`. Si un dev retire `$this->guard()` d'un handler, aucun test existant ne casse.

**Solution appliquée** : `IpxeAdminAuthTest` ajoute un test paramétré qui vérifie via spy que `validateAdCredentials()` est invoqué exactement 1× pour chaque endpoint protégé.

### #10 — Test `allow` sans assertion positive

**Sévérité** : 🟡 Mineur — **Pertinence Opus : 2**
**Fichier(s)** : `tests/Feature/Ipxe/IpxeAdminAuthTest.php:204-221`

**Solution appliquée** : ajout d'un dictionnaire `[path => substring_attendu]` et assertion positive minimale par endpoint dans le test `it_allows_authenticated_user_with_permission`.

### #14 — Case sensitivity AD vs Postgres

**Sévérité** : 🟠 Important — **Pertinence Opus : 2**
**Fichier(s)** : `app/Models/User.php::findByLogin()` (à vérifier)

**Action appliquée** : audit de l'implémentation `User::findByLogin`. Si case-sensitive, basculer en `whereRaw('LOWER(login) = ?', [strtolower($login)])` ou équivalent ILIKE.

## Détail des problèmes non corrigés / différés

Le password n'apparaît pas dans la string formatée. Le `reason=ldap_exception` n'est PAS exposé au client iPXE, c'est un log serveur destiné au SIEM.

### #11 — Non-issue

Le handshake admin sans mac/uuid est attendu (premier hit firmware iPXE).
