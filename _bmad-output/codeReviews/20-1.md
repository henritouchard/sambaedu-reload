## Détail des problèmes

### #1 — Révocation `is_active=false` réarmée par un fresh login

**Sévérité** : 🟠 — **Pertinence Opus** : 3 (CONFIRMÉ)
**Fichier(s)** : `app/Auth/Federated/Http/FederatedLoginController.php` (`upsertIdentity()` ~L145-153, `provisionUser()` ~L183)

**Constat initial (review)** : `upsertIdentity()` appelle `restore()` sur une identité soft-deletée et remet `is_active=true` à chaque login. Un admin qui désactive un externe voit la désactivation annulée dès qu'un JWT valide est re-présenté. Le guard D-5 protège les sessions existantes mais pas un fresh login.

**Avis Opus** : Confirmé ligne par ligne (`if ($identity->trashed()) restore()` puis `is_active=true` inconditionnel ; idem `provisionUser`). C'est la **seule** voie de révocation locale et elle est silencieusement réarmée. Atténuation : la révocation fédérée vient normalement de l'IdP. Mais le report est ici **tacite** (commentaire « sémantique avancée = 20.2 »).

**Solutions possibles** :
1. (Opus) Refuser le login (403) si `is_active=false` et non soft-deletée ; réactivation = action admin (20.3).
2. Acter explicitement le report en 20.2 (décision user documentée).

**Action** : ✅ **Corrigé (Q1 → option 1, élargie au soft-delete)**. `upsertIdentity()` : si l'identité existe et `trashed() || !is_active` → `HttpException(403)`, sans `restore()` ni `is_active=true` réarmé. Log `federated.login.identity_revoked`. Tests Feature `deactivated_identity_is_refused_on_fresh_login` + `soft_deleted_identity_is_refused_on_fresh_login`.

### #2 — `kid` exigé dans le payload (non-standard JOSE)

**Sévérité** : 🟠 → ramenée à un point de **contrat/interop** — **Pertinence Opus** : 2
**Fichier(s)** : `app/Auth/Federated/Jwt/FederatedJwtVerifier.php` (~L104-118)

**Constat initial** : `kid` est lu du payload et requis, alors que `kid` est un paramètre d'en-tête JOSE. Un IdP standard (kid en header seul) serait rejeté.

**Avis Opus** : Confirmé, MAIS la sélection de clé se fait déjà sur le **header** via firebase/php-jwt (sain). La lecture du payload est redondante. C'est une **convention projet assumée**, identique à `WorkstationJwtVerifier` (iso V1). Pas une faille de sécurité (sélection de clé header-based). L'IdP est ici controlHub (contrat maîtrisé).

**Action** : ✅ **Documenté** comme contrat (kid attendu aussi dans le payload, cohérent avec le tier workstation). À reporter dans la doc de contrat 20.5. Pas de modif de code (préserve l'iso-V1).

### #3 — `aud` array sans match → mauvais code d'erreur

**Sévérité** : 🟡 — **Pertinence Opus** : 1 (CONFIRMÉ, impact observabilité uniquement)
**Fichier(s)** : `app/Auth/Federated/Jwt/FederatedJwtVerifier.php` (`audClaim()`)

**Constat initial** : `aud` array sans correspondance retourne `''` → interprété comme claim manquant → `missing_claim('aud')` au lieu de `aud_mismatch`. Les deux rejettent (401), seul le code loggé diffère.

**Avis Opus** : Confirmé, aucun impact sécu/fonctionnel, purement log. Correction triviale.

**Action** : ✅ **Corrigé** — distinction « aud absent » vs « aud présent sans match » ; le second lève `aud_mismatch`. Test ajouté.

### #4 — Fallback `Authorization: Bearer` (déviation D-3)

**Sévérité** : 🟠 → contrat — **Pertinence Opus** : 2
**Fichier(s)** : `app/Auth/Federated/Http/FederatedLoginController.php` (`extractToken()`)

**Constat initial** : `extractToken()` accepte un Bearer en plus du POST. D-3 dit POST binding uniquement.

**Avis Opus** : Le header Bearer ne réintroduit PAS la fuite que D-3 visait (query string/Referer). C'est une déviation de contrat, pas une faille. Le path n'est pas tranché.

**Action** : ✅ **Corrigé par retrait** du fallback Bearer (colle à D-3 strict). Token absent → 400. **À confirmer (Q3)** : si Henri veut le Bearer pour les intégrations, le réintroduire via une décision D-10 documentée.

### #6 — `login` loggé dans le guard (viol. partielle AC16)

**Sévérité** : 🟡 — **Pertinence Opus** : 2
**Fichier(s)** : `app/Http/Middleware/Auth/SambaEduAuthGuard.php` (`handleFederatedSession()`)

**Constat initial** : le warning `federated.session.user_missing` logge `'login' => $login` (= `ext:<sub>`), alors qu'AC16 limite à `sub/jti/iss/role`.

**Avis Opus** : Confirmé, violation littérale d'AC16. Impact réel faible (`ext:<sub>` ≠ PII nominative), mais AC explicite.

**Action** : ✅ **Corrigé** — log du `sub` extrait (sans préfixe `ext:`) au lieu du champ `login`.

### #7 — Formule `ttlFor()` toujours = `$configured`

**Sévérité** : 🟡 — **Pertinence Opus** : 1 (pas un bug)
**Fichier(s)** : `app/Auth/Federated/Jwt/FederatedJwtReplayChecker.php`

**Constat initial** : `max(0, min($configured, max($remaining,0)+$configured))` vaut toujours `$configured`. Formule trompeuse.

**Avis Opus** : Confirmé. Seul effet : légère sur-rétention cache (la couche DB borne via `expires_at`). Pas d'impact correctness.

**Action** : ✅ **Corrigé** — formule simplifiée à `min($configured, max($remaining, 0))` (TTL borné au temps restant du jeton) + commentaire honnête.

### M1 — `jti` consommé AVANT le provisioning (manqué par la review 1)

**Sévérité** : 🟠 — **Pertinence Opus** : 3
**Fichier(s)** : `app/Auth/Federated/Http/FederatedLoginController.php` (verify L~58 avant `DB::transaction` L~80), `app/Auth/Federated/Jwt/FederatedJwtVerifier.php` (`consumeOnce` L~158)

**Constat** : `verify()` consomme le `jti` avant la transaction de provisioning. Si le provisioning échoue, le `jti` est brûlé → retry légitime avec le même JWT rejeté `replayed` jusqu'à réémission IdP. Aggravé par le fail-closed du checker.

**Solutions possibles** :
1. Déplacer la consommation `jti` dans la transaction de provisioning (rollback du jti si échec).
2. Consommer le `jti` en tout dernier (après `Auth::login`).
3. Laisser (risque faible : provisioning casse rarement ; TTL court).

**Action** : ✅ **Corrigé (Q2 → option 1)**. `FederatedJwtVerifier` ne consomme plus le `jti` (pur validateur — constructeur sans `FederatedJwtReplayChecker`). Le controller appelle `consumeOnce()` **en dernier dans `DB::transaction`**, après `upsertIdentity`/`provisionUser`/`applyRole` : un échec amont (403 révoqué, panne DB) rollback ET ne brûle pas le `jti`. Tests : `verifier_does_not_consume_jti`, `replay_checker_consumes_jti_once_then_rejects` (unit), `replayed_token_is_rejected_on_second_post` (feature, inchangé). ⚠️ Note résiduelle assumée : le cache `add()` n'est pas transactionnel — sur le chemin *gagnant* (consume réussi) cache+DB sont commités ensemble ; sur un rollback le `jti` n'a jamais été ajouté (consumeOnce n'add qu'en cas de succès), donc pas d'incohérence.

### M2 — `external_identity_id` du marqueur de session non utilisé

**Sévérité** : 🟡 — **Pertinence Opus** : 1 (pas de faille)
**Fichier(s)** : `app/Http/Middleware/Auth/SambaEduAuthGuard.php`

**Constat** : `FederatedSession::mark()` mémorise `external_identity_id` mais le guard ne s'en sert pas pour valider (recharge le User par `login`+`source='federated'`). Pas de confusion LDAP/fédéré exploitable (branche gardée par `source='federated'`, un user LDAP a `source='ad'`).

**Action** : ✅ **Documenté** — le marqueur est un booléen de routage de session, pas un mécanisme de validation. Pas de modif.
