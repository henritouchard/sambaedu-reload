## Détail des problèmes

### #1 — AC#5 (`$versionChanged=true`) jamais exercé par les tests

**Sévérité** : 🟠 — **Pertinence Opus : 2**
**Fichier(s)** : `tests/Feature/ControlHub/ControlHubContractSchemaVersionTest.php`

**Constat initial (review sonnet)** : `test_version_change_is_mutation` fait un `return` précoce dès que `SUPPORTED_VERSIONS` ne contient qu'une version (toujours vrai en 33.1). La branche `$versionChanged = true` (service ligne 170-171) — cœur de NFR4 × AC#5 — n'a aucune assertion d'exécution ; une régression y serait invisible.

**Avis Opus** : exact. **Nuance décisive manquée par la 1ʳᵉ review** : la branche est testable **sans** inventer de 2ᵉ version — il suffit de pré-seeder un contrat actif avec `schema_version=null` puis de ré-ingérer un contenu identique (`null !== '1.0'` ⇒ `versionChanged=true`). « Couvert par construction » était donc un argument faible. Meilleur rapport valeur/coût de la review.

**Action** : ✅ **Corrigé automatiquement** — ajout de `test_version_change_from_legacy_null_is_mutation` : ingestion → rétrogradation silencieuse de `schema_version` à NULL (mass-update, sans bump `updated_at`) → ré-ingestion identique → assert `mutated=true` + event 1× + `schema_version='1.0'`. Couvre AC#5 **et** transforme #2 en cas positif testé.

### #2 — Event « spurieux » sur contrat legacy (`null` → courante)

**Sévérité** : 🟠 — **Pertinence Opus : 1**
**Fichier(s)** : `ControlHubContractIngestionService.php:170`

**Constat initial (review sonnet)** : un contrat 28.2 préexistant (`schema_version=null` après migration additive) ré-ingéré à l'identique déclenche `versionChanged=true` ⇒ mutation + event, alors que le contenu du payload est inchangé.

**Avis Opus** : mécaniquement exact mais **pas un défaut**. L'état change réellement (le contrat acquiert sa version), une seule fois, et c'est documenté dans la migration. Aucun listener en 33.1 ; en aval (28.3), la version d'échange est serveur-only (invisible du StateCompiler/agent ⇒ recompilation no-op). Qualifier l'event de « spurieux » est inexact : il signale une vraie transition.

**Action** : ✅ Clarifié — comportement **légitime**, désormais **couvert par un test positif** (cf. #1). Confirmation utilisateur demandée (Question #2). Aucun changement de code recommandé.

### #3 — Version non supportée repliée silencieusement, sans observabilité

**Sévérité** : 🟠 — **Pertinence Opus : 2**
**Fichier(s)** : `ControlHubContractSchema.php` (`negotiate()`, branche de repli)

**Constat initial (review sonnet)** : `negotiate('99.0')` retourne silencieusement `'1.0'` ; le DTO et les logs affichent `'1.0'`. La version déclarée par l'autorité n'est tracée nulle part → en cas de bug d'émission côté controlHub, aucun signal entre 33.1 et 33.2.

**Avis Opus** : exact. `'99.0'` n'est **ni** conforme **ni** absent — ce n'est pas le « chemin heureux » que 33.1 prétend couvrir, c'est un cas non-heureux traité par un repli trompeur. **Angle supplémentaire (opus)** : le cast tolérant (`is_string||is_int`) transforme aussi un `bool/array/float` en `null` (« absent »), et un `int 1` en `"1"` non supporté → repli silencieux. Double angle mort d'observabilité. Un `Log::warning` non bloquant améliorerait l'observabilité **sans** empiéter sur le rejet de 33.2. **Zone grise de périmètre** ⇒ décision utilisateur.

**Solutions possibles** :
1. Ajouter un `Log::warning('version non supportée, repli courant — seam 33.2', ['declared' => ..., 'fallback' => CURRENT_VERSION])` dans la branche de repli de `negotiate()` (et idéalement aussi quand le cast écarte un type inattendu).
2. Tout déléguer à 33.2 (qui rejettera et tracera de toute façon).

**Action** : ✅ **Corrigé** (décision Henri 2026-06-30 = option 1) — `Log::warning` non bloquant ajouté dans la branche de repli de `negotiate()` (déclarée, repli, versions supportées). Le rejet reste 33.2. Test `test_unsupported_version_falls_back_to_current_and_is_logged`.
