## Questions en attente

> Questions de design relevées par la review. Tranchées par défaut dans le sens
> le plus conforme à l'intention de la story (AC5 / piège 6) ; à confirmer.

1. **Re-cibler un poste DÉJÀ rapproché via la modale de sélection de cible** — autorisé ou interdit ?
   La review (P2) a montré qu'un admin pouvait, via `/livewire/update`, écraser un rapprochement existant en re-ciblant. **Décision appliquée par défaut : interdit** (cohérent avec AC5 « approbation d'un poste INCONNU » et le piège 6 anti-usurpation). Le flux pour corriger un mauvais rapprochement reste « Rejeter puis re-soumettre ». _Si tu veux au contraire permettre la correction d'un rapprochement automatique erroné depuis cette modale, dis-le : il faudra retirer la garde et la documenter/tester._

2. ~~**Multi-comptage des postes appartenant à plusieurs rings**~~ — **TRANCHÉ & CORRIGÉ (post-review, Henri 2026-06-13)**. La multi-appartenance est en fait **fréquente** (un poste ∈ 1 groupe physique + 1-2 logiques, pivot global 4.11), donc pas marginale : le multi-comptage produisait des **faux « en retard »** (un poste compté dans un ring qui ne sert pas sa version). Correctif : chaque poste est attribué au **ring effectif** = le plus récemment ciblé parmi ses groupes (récence FR4, iso `ReleaseManifestService::resolveRingRelease`), comptage **unique**. Résolu en mémoire (zéro N+1). Test : `DeploymentProgressSurfaceTest::a_multi_ring_workstation_is_counted_once_in_its_most_recently_targeted_ring`. Scénario QA 12.4 §5.

## Détail des problèmes

### #1 — Toast de succès avec version vide dans `confirmTarget()`

**Sévérité** : 🟠 — **Pertinence Opus** : 3/3
**Fichier(s)** : `resources/views/pages/parc-settings/agent/_partials/releases-rings.blade.php:120-122`

**Constat initial (review)** :
`closeTarget()` remet `$this->targetVersion = null` AVANT le `toastSuccess` qui interpole `{$this->targetVersion}`. Le message affiché est « Ring « … » ciblé sur la version  » (vide) à chaque ciblage réussi. Le pattern correct existe déjà dans `confirmPromote()` (capture `$version` avant `closePromote()`), il n'avait pas été appliqué ici.

**Avis Opus** : Confirmé, bug réel et visible à chaque ciblage. Non attrapé par les tests car `assertDispatched('toastMagic')` n'inspectait pas le message (lié à #4).

**Action** : ✅ Corrigé — capture de `$version` et `$groupName` dans des variables locales avant `closeTarget()`.

### #2 — Écrasement possible d'un rapprochement existant via la modale de cible

**Sévérité** : 🟠 — **Pertinence Opus** : 2/3
**Fichier(s)** : `resources/views/pages/parc-settings/agent/_partials/enrollment-requests.blade.php`

**Constat initial (review)** :
`openTargetSelect()` et `confirmApproveWithTarget()` ne vérifiaient pas `matched_workstation_id === null`. Via l'adressabilité `/livewire/update`, un admin pouvait appeler ces méthodes sur une demande déjà rapprochée et écraser silencieusement la cible (`approveManually` donne priorité au `$target`).

**Avis Opus** : Confirmé techniquement, mais c'est d'abord une question de design + un durcissement de cohérence (l'acteur détient déjà `computer.install`, ce n'est pas une élévation de privilège). Le composant refuse déjà l'inverse (`approve()` sur une demande non rapprochée) → l'incohérence de durcissement plaide pour la garde. La garde est conforme à AC5 (approbation d'un INCONNU) et au piège 6.

**Action** : ✅ Corrigé — garde `matched_workstation_id !== null → toastError + return` ajoutée dans `openTargetSelect()` (fail-fast à l'ouverture) ET dans `confirmApproveWithTarget()` (défense en profondeur, appel direct). Cf. question en attente #1.

### #3 — Code mort `$stable` + requête SQL dupliquée

**Sévérité** : 🟡 — **Pertinence Opus** : 3/3
**Fichier(s)** : `resources/views/pages/parc-settings/agent/_partials/deployment-progress.blade.php:29`

**Constat initial (review)** :
`$stable = AgentRelease::query()->where('is_stable', true)->value('version')` était assigné dans `rings()` mais jamais relu dans la closure → code mort + 1 requête SQL inutile par rendu.

**Avis Opus** : Confirmé et même sous-estimé : `stableVersion()` (computed) refait exactement la même requête → 2 requêtes redondantes. Supprimer la ligne morte suffit (le computed `stableVersion()` reste la source unique).

**Action** : ✅ Corrigé — ligne 29 supprimée. `stableVersion()` reste la seule requête `is_stable` de la surface.

### #4 — Test version inconnue ne discrimine pas error/success

**Sévérité** : 🟡 — **Pertinence Opus** : 3/3
**Fichier(s)** : `tests/Feature/Livewire/Agent/ReleasesRingsSurfaceTest.php:84`

**Constat initial (review)** :
`assertDispatched('toastMagic')` passe que le toast soit error ou success. Le test « version inconnue » passerait même si le code envoyait un succès.

**Avis Opus** : Confirmé. Solution syntaxiquement valide vérifiée contre le trait `WithToasts` (dispatch nommé `status`/`title`/`message`) : le callback `fn ($e, $p) => $p['status'] === 'error'` est correct en Livewire v3.

**Action** : ✅ Corrigé — le test « version inconnue » assert `status === 'error'` ; le test nominal assert `status === 'success'` ET `message` contient la version (ce qui couvre aussi la régression #1).

### #5 — Couverture Gate incomplète sur les méthodes mutantes

**Sévérité** : 🟡 — **Pertinence Opus** : 2/3
**Fichier(s)** : `tests/Feature/Livewire/Agent/ReleasesRingsSurfaceTest.php`

**Constat initial (review)** :
Un seul test de permission (`openTarget`). `confirmTarget`, `rollbackRing`, `openPromote`, `confirmPromote` non couverts en permission-denied alors qu'AC6 exige le Gate sur CHAQUE méthode mutante.

**Avis Opus** : Confirmé. Les 5 méthodes appellent bien `Gate::authorize` (vérifié), mais la couverture test asymétrique laissait passer une régression. Un test paramétré sur les 5 méthodes est l'idéal.

**Action** : ✅ Corrigé — test remplacé par un `#[DataProvider]` couvrant les 5 méthodes mutantes (`openTarget`, `confirmTarget`, `rollbackRing`, `openPromote`, `confirmPromote`).

### #6 — Scope `active()` non utilisé

**Sévérité** : 🟡 — **Pertinence Opus** : 1/3
**Fichier(s)** : `resources/views/pages/parc-settings/agent/_partials/releases-rings.blade.php:69`

**Constat initial (review)** :
`->where('is_active', true)` au lieu du scope nommé `WorkstationGroup::active()`.

**Avis Opus** : Confirmé mais cosmétique : `scopeActive` fait littéralement `where('is_active', true)`. Pure cohérence de convention, zéro impact fonctionnel (sévérité 🟡 généreuse).

**Action** : ✅ Corrigé — `->active()`.
