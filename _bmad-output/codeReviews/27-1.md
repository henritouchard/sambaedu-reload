## Détail des problèmes

### #1 — Homonyme user annule toute la convergence raccourcis 🔴

**Fichier(s)** : `agent/windows/handler_shortcuts_windows.go` (~l.222), `agent/shared/handler_shortcuts.go` (~l.211-221)

**Constat (sonnet, confirmé opus pertinence 3)** : `Matches()` retourne `(false, error)` quand un `.lnk`
utilisateur (sans marqueur de gestion) occupe le chemin exact d'un raccourci désiré. Le moteur
(`engine.go`) propage toute erreur de `Test` en `{status: error}` **pour le type entier** → un seul
homonyme utilisateur (un prof crée « Intranet » sur son bureau) annule la convergence de TOUS les
raccourcis du poste, en silence. Le commentaire décrit l'intention inverse (« laisser tel quel »).

**Solutions possibles** :
1. `Matches()` retourne `(false, nil)` pour un homonyme non géré ; `Apply`/`Test` **ignorent** ce chemin
   (ni écraser, ni supprimer, ni échouer) — comportement « jamais toucher hors périmètre » (décision n° 5).

**Action** : corrigé automatiquement (solution 1) + test #6.

### #2 — Orphelins cross-placement jamais supprimés 🔴

**Fichier(s)** : `agent/shared/handler_shortcuts.go` (~l.120-137, `managedDirs`)

**Constat (sonnet, confirmé opus pertinence 3)** : `managedDirs()` ne balaie que les dossiers présents
dans le `desired` courant. Si toutes les règles `place=desktop` disparaissent mais qu'une règle `startup`
subsiste, le dossier Bureau n'est plus listé → `.lnk` Bureau géré devient orphelin permanent. Viole AC3.

**Solutions possibles** :
1. Balayer l'**union des emplacements gérables connus** (desktop/startup/taskbar), pas seulement ceux du `desired`.
2. Persister la liste des dossiers gérés dans l'applied-state per-user.

**Action** : corrigé automatiquement (solution 1, la plus simple/robuste) + test #7.

### #3 — `IPersistFile::Save` pf vs pfPtr 🟡 (rétrogradé)

**Constat** : sonnet le notait 🟠 ; **opus pertinence 0 (faux)** — `pf := (*iPersistFile)(pfPtr)` pointe sur
la même adresse, `uintptr(unsafe.Pointer(pf)) == uintptr(pfPtr)`. Aucun risque ABI. Pure incohérence de
style entre `Load` (pfPtr) et `Save` (pf).

**Action** : harmonisé pour la lisibilité (pas un correctif fonctionnel).

### #4 — Persistance overlay mode non atomique 🟠

**Fichier(s)** : `resources/views/pages/parc-settings/overlay-messages/index.blade.php` (~l.91-104)

**Constat** : `postSignal()` crée le signal sans mode, puis `update(['mode'=>...])`. Fenêtre `mode=null`
+ perte théorique si `postSignal()→null`. **Opus pertinence 1** : inoffensif (null→strict, et la branche
null n'arrive que pour `kind=remote_control+submarine`, or ce formulaire passe `kind=notice`).

**Action** : corrigé (wrap transaction / passage du mode), faible risque.

### #5 — Identity candidate overlay rend le toggle inopérant 🔴 (relevé par opus)

**Fichier(s)** : `app/Services/Agent/Providers/OverlayStateProvider.php` (~l.134-146), `StateCompiler::aggregateMode()`

**Constat (opus pertinence 3)** : le candidat synthétique `identity` est créé sans `mode` (null → défaut
provider = `strict`). Dans l'agrégation, dès qu'un user est en session (cas nominal), l'identity force le
type `overlay` en `strict`, **annulant tout `default`** choisi par l'admin. Le toggle overlay (AC4,
« première exposition UI ») est donc inopérant en pratique.

**Solutions possibles** :
1. Exclure le candidat synthétique `identity` (sentinel `sourceId=0`) de l'agrégation du mode.
2. Lui affecter le mode dominant des signaux.

**Action** : corrigé automatiquement (solution 1) + test.

### #M1 — L'UI wallpaper ment sur le mode 🟠 (relevé par opus)

**Fichier(s)** : `resources/views/components/molecules/wallpaper-card.blade.php`, `WallpaperStateProvider::mode()`

**Constat (opus)** : `WallpaperStateProvider::mode()` = `Default`. L'UI affiche
`$wallpaper->mode?->value ?? 'strict'` → pour tout wallpaper existant (`mode` null), l'UI surligne
**« Strict »** comme actif alors que le compilateur applique réellement **`default`**. L'admin voit
l'opposé du comportement réel — exactement le « l'UI ne ment pas » que la décision n° 2 visait.

**Solution** : le défaut d'affichage doit être le défaut du provider (`default` pour wallpaper), pas `strict` en dur.

**Action** : corrigé automatiquement + test #8.

### #M2 — Collision name+place, targets différents 🟡 (relevé par opus)

**Fichier(s)** : `agent/shared/handler_shortcuts.go` (~l.100-114, `desiredSet`)

**Constat** : `desiredSet` indexe par chemin (map) ; deux items « même name+place+desktop_path » mais
targets différents s'écrasent « dernier gagne » (non déterministe). La dédup compilateur (par contenu) ne
les fusionne pas (contenus distincts). Cas de mauvaise config admin.

**Action** : documenté (commentaire + note QA) ; pas de garde lourde (garbage-in).

### #M3 — report.v1.json : hash agrégat == hash item 🟡 (relevé par opus)

**Constat** : pour un type aggregate à 1 item, le golden report porte le hash de l'item, pas
`AggregateHash(concat)`. À vérifier : si un test reconstruit le report via l'engine, divergence.

**Action** : vérifié pendant les corrections — voir Post-correctifs. Golden statique cohérent / corrigé si nécessaire.

### #M4 — `args` comparé sans EqualFold/substitution 🟡 (relevé par opus)

**Fichier(s)** : `agent/windows/handler_shortcuts_windows.go` (~l.225-227)

**Constat** : `Matches` compare `target`/`icon` via `EqualFold(substituteTokens(...))` mais `args ==
spec.Args` (sensible casse, sans substitution). Latent : si un `args` contient un token → réécriture à
chaque passe (perte d'idempotence). Aucun payload `args` n'a de token aujourd'hui.

**Action** : documenté (commentaire + note QA), latent.

## Post-correctifs & non-régressions

Corrections appliquées (2026-06-15) :

- **#1 (homonyme)** — `ShortcutOps.Matches` (Windows) retourne désormais `(false, nil)` sur un `.lnk` non géré (plus jamais d'erreur) ; ajout d'une méthode `Blocked(path)` à l'interface `ShortcutOps`. `Test`/`Apply` (shared) consultent `Blocked()` AVANT `Matches` et **ignorent** le chemin d'un homonyme user (ni écrasé, ni supprimé, ni erreur). Commentaires corrigés. Test #6 ajouté.
- **#2 (cross-placement)** — `managedDirs()` (shared) balaie désormais l'**union** des emplacements gérables connus (desktop/startup/taskbar), pas seulement le `desired` courant. Pour le desktop sans règle, probe vers le bureau STANDARD (`%USERPROFILE%\Desktop`) pour le seul nettoyage des orphelins. Test #7 ajouté.
- **#5 (identity overlay)** — le candidat synthétique `identity` porte un mode **neutre** (`StateMode::Default`), donc il ne tire plus l'agrégation du type `overlay` vers `strict`. Toggle overlay opérant. Tests ajoutés (`OverlayStateProviderTest`).
- **#M1 (UI wallpaper)** — `wallpaper-card.blade.php` : défaut d'affichage = défaut du PROVIDER (`WallpaperStateProvider::mode()` = `default`), plus `?? 'strict'` en dur. Vérifié : shortcut-form et overlay-form n'ont PAS ce bug (leur défaut provider EST `strict`). Test ajouté (`WallpaperStateProviderTest`).
- **#4 (atomicité overlay)** — create+update du mode enveloppés dans `DB::transaction` (signature `postSignal()` inchangée, moins invasif que l'étendre). 3 autres appelants non touchés.
- **#3 (style COM)** — `IPersistFile::Load` ET `Save` dérivent le `this` de `unsafe.Pointer(pf)` des deux côtés (harmonisé ; non fonctionnel — `pf`/`pfPtr` pointent la même adresse, `pfPtr` hors portée du closure de Save).
- **#M2 / #M4 (documentés)** — commentaires ajoutés dans `desiredSet` (collision name+place targets différents = mauvaise config, dernier gagne) et `Matches` Windows (`args` non token-substitué, latent).

**#M3 — verdict** : le golden `report.v1.json` est **purement statique**. `ContractV1Test::report_golden_file_has_valid_structure_and_four_statuses` ne vérifie QUE la structure (clés `type/status/hash`, 4 statuts illustrés, `detail` si `error`) — il ne reconstruit JAMAIS le report via l'engine ni ne compare le `hash` à `AggregateHash`. Aucun test Go ne lit `report.v1.json`. Le `hash` `shortcuts` du report (égal au hash de l'item, et non `AggregateHash(concat)`) est donc inoffensif → **laissé tel quel** (noté). La cohérence PHP↔Go qui compte (le `FROZEN_STATE_HASH` `c02463…`) est figée des deux côtés et reste verte.
