## Questions en attente

> Questions nécessitant une réponse de l'utilisateur avant de pouvoir avancer.

1. **Sémantique idempotence AC3.6 (= problème #3)** : l'AC dit « 0 écriture DB » lors d'un 2e run no-op, mais le code appelle `saveQuietly()` pour persister `last_seen_at` à chaque exécution. Trois options :
   - (a) Assouplir l'AC en « 0 écriture métier » et accepter que `last_seen_at` soit toujours rafraîchi (gain : simple, monitoring fiable).
   - (b) Ne pas écrire `last_seen_at` si la valeur est récente (ex : < 1 minute) — comparaison avant `saveQuietly()`.
   - (c) Regrouper les `last_seen_at` en un seul `UPDATE ... WHERE id IN (...)` hors boucle, ou ne setter qu'aux écritures réelles. **Recommandation Opus : (c)**.

2. **Renommage AC5.2 (= problème #4)** : la story tableau AC5.2 dit « Renommage : `name` MAJ, log `info` rename ». Le dev a délibérément choisi de **ne pas écraser** `name` (Eloquent reste source de vérité Eloquent → AD). **Recommandation Opus : la décision dev est cohérente avec la direction d'écriture canonique** ; il faut acter formellement et corriger le tableau AC5.2 + ajouter un log `info` rename divergent (sans écraser).

3. **Nom commande artisan** : la spec dit `sync:all-from-ad`, le code dit `sync:from-ad` (nom historique préservé). **Recommandation Opus : conserver `sync:from-ad` et corriger la spec** (faux écart, le nom historique évite de casser un éventuel runbook humain).

## Détail des problèmes

### #1 — `AppProfileObserver::disableSync()` jamais appelé pendant la passe 2

**Sévérité** : 🔴 Critique
**Fichier(s)** : `app/Jobs/SyncAllFromAdJob.php:240-261` (méthode `runPass2Apply()`)

**Constat initial (review Sonnet)** :
`runPass2Apply()` désactive `WorkstationGroupObserver::disableSync()` et `WorkstationObserver::disableSync()` mais **omet** `AppProfileObserver::disableSync()`. `AppProfileObserver` existe (`app/Observers/AppProfileObserver.php`) et réagit aux événements `created` et `updated` en dispatchant des `AppProfileAdSyncJob` sortants Eloquent → AD. Lors de la passe 2, chaque `AppProfile::create(...)` et chaque `$profile->save()` déclenche donc un job sortant qui va écrire en AD ce qu'on vient de lire — violation directe de l'invariant cœur de la story.

**Avis Opus (3/3)** :
Confirmé. `AppProfile::create()` (l. 593) déclenche `dispatch(AppProfileAdSyncJob::create($id))` via observer enregistré dans `AppServiceProvider:201`. Le test ne le détecte PAS car `WpkgSchemaBootstrapper::bootstrap()` appelle `Model::unsetEventDispatcher()` (les observers sont mutés en test). En prod, chaque create/update de profil par le job entraîne un job sortant qui réécrit en AD ce qu'on vient de lire. Violation directe de l'invariant documenté lignes 53-58 du job. **Bloquant.**

Note : `saveQuietly()` (cf. #3) court-circuite déjà l'observer pour les paths idempotents, mais les paths `save()` / `create()` (créations + vraies updates + archivages + restaurations) restent affectés.

**Solutions possibles** :
1. Ajouter dans `runPass2Apply()` :
   ```php
   use App\Observers\AppProfileObserver;
   AppProfileObserver::disableSync();
   // dans finally :
   AppProfileObserver::enableSync();
   ```
2. Ajouter un test qui vérifie qu'aucun `AppProfileAdSyncJob` n'est dispatché pendant l'exécution du job durci (via `Queue::fake() + Queue::assertNotPushed(AppProfileAdSyncJob::class)`).

**Action** : ✅ corrigé automatiquement (fix mécanique, pas de choix de design).

### #2 — Scénario « Conflit GUID » (AC5.2) non implémenté

**Sévérité** : 🔴 Critique
**Fichier(s)** : `app/Jobs/SyncAllFromAdJob.php:407-425` + `tests/Feature/Jobs/SyncAllFromAdJobTest.php`

**Constat initial (review Sonnet)** :
La story (AC5.2 tableau, R3) exige : « Conflit `objectGUID` — 2 rows DB pour 1 GUID → log `error`, halte propre, lock libéré ». Le compteur `conflicts` est déclaré dans les stats mais **jamais incrémenté**. `keyBy('ad_guid')` silencieusement garde la dernière entrée — l'autre est perdue dans le diff et risque d'être archivée à tort. Aucun test ne couvre ce scénario.

**Avis Opus (2/3)** :
Confirmé partiellement. Le compteur `conflicts` est dans le rapport stats (l. 105, 114, 124) mais jamais incrémenté. `keyBy('ad_guid')` perd silencieusement les doublons côté AD (le 2e écrase le 1er en collection). Risque réel : R3 du tableau de risques (Faible × Élevé). Note : la corruption « 2 rows DB pour 1 GUID » côté DB serait également écrasée silencieusement au premier passage. Pas de halte propre, pas de log, pas de test.

**Sévérité ajustée : 2 (pertinent) plutôt que 3 (critique-critique)** car la probabilité est faible et le code ne crash pas — il écrase juste silencieusement.

**Solutions possibles** :
1. Avant le `keyBy`, détecter les doublons côté DB :
   ```php
   $grouped = WorkstationGroup::query()->whereNotNull('ad_guid')->get()->groupBy('ad_guid');
   $conflicts = $grouped->filter(fn($g) => $g->count() > 1);
   if ($conflicts->isNotEmpty()) {
       $logger->error('Conflit GUID détecté', [
           'conflicts' => $conflicts->keys()->all(),
           'entity' => 'workstation_group',
       ]);
       $stats['workstation_groups']['conflicts'] = $conflicts->count();
       throw new RuntimeException('Conflit GUID — halte propre, intervention manuelle requise');
   }
   $byGuid = $grouped->map->first();
   ```
2. Idem pour `AppProfile`.
3. Ajouter un test feature `conflict_guid_aborts_with_clean_log_and_lock_released`.

**Action** : ✅ corrigé automatiquement (logique sans choix de design ; suit la spec R3).

### #3 — Idempotence AC3.6 violée : `saveQuietly()` écrit `last_seen_at` à chaque run

**Sévérité** : 🟠 Important
**Fichier(s)** : `app/Jobs/SyncAllFromAdJob.php:472-476, 585-589`

**Constat initial (review Sonnet)** :
AC3.6 stipule « 0 écriture DB » lors d'un 2e run no-op. Mais dans le chemin « état aligné », le job appelle `$group->saveQuietly()` pour persister `last_seen_at = now()`. C'est une `UPDATE` SQL réelle à chaque exécution. Le test `noop_when_state_is_aligned` valide `idempotent=true` et `updated=0` mais n'asserte pas « zéro `UPDATE` SQL » — l'écriture silencieuse passe inaperçue.

**Avis Opus (2/3)** :
Confirmé. `saveQuietly` skip uniquement les events Eloquent (donc pas les observers métier — bonne nouvelle, mitige #1 partiellement pour ce sous-cas), mais le SQL est bien envoyé. Le test n'assert que les compteurs (created/updated/archived = 0), pas un `DB::enableQueryLog()` zero-write.

**Solutions possibles** :
1. (a) Assouplir l'AC en « 0 écriture métier » (accepter `last_seen_at` toujours écrit).
2. (b) Comparer avant `saveQuietly()` : ne mettre à jour que si `last_seen_at` est ancien (> 1 minute).
3. (c) **Recommandée Opus** : regrouper les `last_seen_at` en un seul `UPDATE ... WHERE id IN (...)` hors boucle, ou ne setter qu'aux écritures réelles (created/updated/restored).

**Action** : ⏳ en attente décision Henri (cf. Q1).

## Forces (signalées par Sonnet, confirmées Opus)

1. **Architecture 2 passes strictes** : `fetchParcsFromAd` + `fetchGroupesFromAd` en passe 1 isolée, `runPass2Apply` wrappée dans `DB::transaction` avec `finally` pour réactiver les observers. Le cas « passe 1 partielle → 0 écriture » (R4) correctement géré et testé.

2. **Fix bug `$preExistingGuidIds`** : la capture des IDs GUID-és avant la passe écriture pour délimiter le périmètre d'archivage est une solution propre. Tests `archives_orphan_db_row_when_absent_in_ad` + `pass1_failure_aborts_without_writes` valident les deux faces.

3. **Filtre D8 dans le resolver** : application de `whereNull('archived_at')` dans l'eager load (`appProfiles`, `groups`, `groups.appProfiles`) exhaustive et couverte par 4 tests dédiés. Changement non-breaking qui protège le pipeline en production.

4. **`EloquentFirstChemiCritiqueTest`** : binder tous les `App\LdapModels\*` et `LdapRecord\Connection` sur un mock `shouldNotReceive()` est la bonne stratégie pour tester l'invariant « zéro AD en chemin critique » au runtime (complémentaire au test AST statique).
