## Détail des problèmes

### #1 — Guard borne le privilège, pas la portée des `accounts` (🟠)

**Fichier(s)** : `app/Services/Agent/Providers/PrivilegeAuthoringGuard.php:68-74`, `agent/shared/handler_privilege.go:65-71`

**Constat** : l'allowlist `SeDeny*`-only désamorce la variante *grant*. Mais `SeDenyInteractiveLogonRight` (logon **console**) est dans l'allowlist, et ni le guard ni l'agent ne contraignent `accounts`. Une projection `{privilege:'SeDenyInteractiveLogonRight', accounts:['Domain Users']}` (ou `Authenticated Users`/`Administrators`, résolus verbatim) serait **acceptée** et **viderait le logon interactif de tout le monde** → poste inutilisable, sans passer par un grant. La sûreté revendiquée (« SeDeny vide par défaut ») ne couvre pas une SeDeny légitime pointée sur un principal trop large. Le seed livré (`@eleves` seul) est sûr ; le trou devient exploitable dès la réutilisation du guard par un formulaire (docblock `PrivilegeAuthoringGuard.php:30-32`).

**Solutions possibles** :
1. Denylist de principals à large portée (`Everyone`/`S-1-1-0`, `Authenticated Users`/`S-1-5-11`, `Domain Users`, `Administrators`, `SYSTEM`) refusés en `accounts` — miroir de la garde `fs_acl`. **(recommandée)**
2. A minima : documenter explicitement la limite (docblock guard + contrat §7.9).

**Action** : ✅ **CORRIGÉ** (décision Henri 2026-07-05, option 1). Denylist ajoutée des DEUX côtés :
- **Serveur** — `PrivilegeAuthoringGuard::BROAD_PRINCIPALS` (noms bien connus FR/EN, préfixe domaine retiré) + `BROAD_SIDS` (SID well-known + RID de domaine `-513/-512/-515`) ; refus de tout `accounts` littéral large avec message « poste VERROUILLÉ ». Les jetons `@…` (groupes métier) restent acceptés.
- **Agent** — `handler_privilege.go` : `isBroadPrincipalSid()` tranche sur le **SID résolu** par la LSA (robuste locale/alias) ⇒ **erreur d'item, sans application partielle** (iso compte irrésoluble).
- **Tests** — PHP `guard_refuses_broad_principals_in_accounts` (16 principals) + `guard_still_accepts_a_named_business_group_in_accounts` ; Go `TestPrivilegeBroadPrincipalRefused` (Domain Users, Everyone). Doc contrat §7.9 enrichie.

### #2 — Écrasement silencieux des entrées secpol manuelles (🟡)

**Fichier(s)** : `agent/shared/handler_privilege.go:337-352`

**Constat** : tout titulaire hors état désiré est révoqué (choix assumé D4). Sur un site utilisant déjà `SeDenyRemoteInteractiveLogonRight` via secpol pour un autre groupe, la 1re convergence efface l'entrée (seul `logInfo` local). Impact non signalé côté opérateur.

**Action** : ✅ **corrigé** — ajout au `warning` du seed (« toute entrée SeDeny posée à la main sera RETIRÉE à la convergence ») ; `contract-v1.md §7.9` couvrait déjà « y compris un compte accordé à la main » + remède secpol. Remontée serveur = ⏳ question #2.

### #3 — `LsaFreeMemory` sur buffer potentiellement NULL (🟡)

**Fichier(s)** : `agent/windows/handler_privilege_windows.go:122-125`

**Constat** : `defer LsaFreeMemory` armé sur SUCCESS avant le test `count==0 || buffer==nil` → si la LSA renvoie SUCCESS+nil, on libère un pointeur nul.

**Action** : ✅ **corrigé** — le `defer` n'est armé qu'après avoir écarté le buffer nul.

### #4 — Non-émission silencieuse d'un privilège hors allowlist (🟡)

**Fichier(s)** : `app/Services/Agent/Providers/PrivilegeCapabilityProvider.php:130-132`

**Constat** : un privilège hors `SeDeny*` fait `return []` sans log (asymétrique du compte irrésoluble qui loggue). Une projection mal formée en base serait ignorée sans trace.

**Action** : ✅ **corrigé** — `Log::warning` symétrique sur le rejet de privilège.

### #5 — `OBJECT_ATTRIBUTES` NT réutilisé pour un handle LSA (🟡 info)

**Fichier(s)** : `agent/windows/handler_privilege_windows.go:205-213`

**Constat** : `LsaOpenPolicy` attend `LSA_OBJECT_ATTRIBUTES` ; le code passe `windows.OBJECT_ATTRIBUTES` NT (layout-identique, idiome documenté). Pas un bug, dépendance implicite à noter.

**Action** : ✅ **documenté** — commentaire ajouté sur l'équivalence structurelle NT⇄LSA.
