## Détail des problèmes

### #1 — TOCTOU porte 2 étape 2 : pas de claim atomique avant `issueFor()`

**Sévérité** : 🟠
**Fichier(s)** : `app/Services/Agent/Enrollment/EnrollmentService.php` (handleGate2 étape 2)

**Constat initial (review sonnet)** : la porte 1 consomme le ticket par un UPDATE conditionnel atomique ; la porte 2 étape 2 (demande `approved` → token) ne dispose d'aucun claim. Deux check-ins concurrents → double `issueFor()`, le second écrase le premier, premier poste en échec silencieux.

**Avis Opus (2/3)** : réel mais sur-pondéré — la cible des deux `issueFor()` est le **même** poste (même faisceau), le dernier token gagné est valide, pas de prise de contrôle croisée ; réalisme faible (throttle 10,1 + agent Go mono-thread). Mitigation peu coûteuse recommandée quand même : faire de la **consommation le claim** (`delete ... where status=approved`) avant `issueFor()`, miroir exact de la porte 1.

**Action** : ✅ Corrigé. La demande est supprimée de façon conditionnelle (`whereKey(...)->where('status', APPROVED)->delete()`) AVANT `issueFor()` ; le perdant retombe sur `notAllowed()` (403 sans oracle). Méthode `consumeRequest()` devenue inutile, retirée.

### #2 — `approveManually`/`rejectManually` sans garde de statut

**Sévérité** : 🟡
**Fichier(s)** : `app/Services/Agent/Enrollment/EnrollmentService.php`

**Constat initial** : `forceFill` inconditionnel, pas de vérification `status === pending`. Non exploitable via l'UI (scope `pending()`), mais méthodes publiques non idempotentes — 25.5 pourrait ré-armer une demande `rejected` silencieusement.

**Avis Opus (2/3)** : confirmé ; contredit AC4 (re-armer doit être explicite).

**Action** : ✅ Corrigé. Garde `if ($request->status !== STATUS_PENDING) { return; }` (no-op idempotent) en tête des deux méthodes — défense en profondeur, l'UI restant le garde de premier rang.

### #3 — Bouton « Approuver » sur demande « inconnu » → impasse

**Sévérité** : 🟠 (review : 🟡, relevé par Opus)
**Fichier(s)** : `resources/views/pages/parc-settings/agent/_partials/enrollment-requests.blade.php`, `EnrollmentService.php`

**Constat initial** : pour une demande `matched_workstation_id = null` (badge « inconnu »), « Approuver » est rendu. L'approbation passe la demande `approved` sans cible → étape 2 exige `matched_workstation_id !== null` → 403 éternel ; la demande sort du scope `pending` → invisible, irrécupérable, aucune alerte.

**Avis Opus (3/3)** : trou fonctionnel direct contre AC2, c'est le plus sérieux côté UX. Le bouton ne doit pas être actionnable sans cible.

**Action** : ✅ Corrigé. Le bouton « Approuver » n'est rendu que si `matchedWorkstation` existe ; sinon un libellé désactivé « rapprochement requis » (tooltip) est affiché. Garde service : `approve()` Livewire refuse une demande sans rapprochement avec un toast explicite. La sélection d'un poste cible reste l'extension 25.5.

### #4 — Actions Livewire mutantes sans `Gate::authorize`

**Sévérité** : 🟠 (review : 🟡, relevé par Opus)
**Fichier(s)** : `resources/views/pages/parc-settings/agent/_partials/enrollment-requests.blade.php`

**Constat initial** : le pattern projet (printers-tab, drivers-tab, groups) appelle `Gate::authorize(...)` sur chaque action mutante. Ce composant n'en a aucun ; seul le middleware route `can:computer.install` (hérité par la page) protège — un composant Livewire est adressable directement (`livewire/update`), d'où la double protection du pattern maison.

**Avis Opus (3/3)** : vraie régression de sécurité vs le standard maison. Obligatoire.

**Action** : ✅ Corrigé. `Gate::authorize('computer.install')` (ability réellement utilisée par la route, web.php:181) ajouté en tête de `approve`, `confirmReject`, `enableCampaign`, `disableCampaign`, `openReject`.

### #M2 — Conflit `.first()` sous MAC partagée

**Sévérité** : 🟠/moyen — **manqué par la review sonnet, relevé par Opus**
**Fichier(s)** : `EnrollmentService.php` (resolveByIdentity / handleGate2 étape 1)

**Constat** : la détection de conflit (étape 1) utilise `resolveByIdentity().first()`. Si deux postes partagent une MAC et que l'un est enrôlé, `.first()` peut tomber sur le **non-enrôlé** → pas de 409, demande pending — le clone enrôlé n'est pas signalé. L'ordre des lignes en base décide du comportement de sécurité. Le test `enrolled_known_workstation_returns_409` ne couvre que le mono-poste.

**Action** : ✅ Corrigé (Henri, 2026-06-13). Conflit fondé sur `Workstation::where('mac',$mac)->whereNotNull('agent_token_hash')->exists()` — un clone enrôlé partageant la MAC est toujours détecté, indépendamment de l'ordre des lignes. Test neuf `enrolled_clone_sharing_mac_still_returns_409`.

### #M3 — Oracle 409 via uuid seul en porte 2

**Sévérité** : 🟠/moyen — **manqué par la review sonnet, relevé par Opus**
**Fichier(s)** : `EnrollmentService.php` (resolveByIdentity)

**Constat** : `resolveByIdentity` résout par `uuid` en priorité et retourne le poste. En porte 2, présenter l'uuid (preuve « faible », gap 3, spoofable) d'un poste enrôlé déclenche un 409 distinct du 403 → **oracle de présence** basé sur une preuve faible, alors que la story exige « sans oracle » (AC6). Légitime en porte 1 (résolution par hash de ticket), pas en porte 2.

**Action** : ✅ Corrigé (Henri, 2026-06-13). `resolveByIdentity()` supprimée ; le conflit ne lit plus l'uuid. Présenter l'uuid seul d'un enrôlé → 403 indistinct (+ pending non auto-approuvable), jamais 409. Contrat propagé à la porte 1 (`enrollment.md` §4) ; tests porte 1/porte 2 alignés + test neuf `uuid_only_of_enrolled_workstation_does_not_leak_409_oracle`.

### #M4 — `else` de `handleGate2` : approbation non-matérialisée jamais alertée

**Sévérité** : 🟡 — **manqué par la review sonnet, relevé par Opus**
**Fichier(s)** : `EnrollmentService.php` (handleGate2 branche else)

**Constat** : quand une demande `approved` ne se matérialise pas (poste devenu enrôlé entre-temps, hostname divergent, ou cible nulle — cf. #3), on tombe dans le `else` qui ne fait que refresh `last_seen_at`. Le poste reste 403 indéfiniment, la demande reste `approved` mais invisible (hors scope pending), personne n'est notifié.

**Action** : ✅ Corrigé. Un log `agent.enroll.stale_approval` (warning) est émis quand le refresh concerne une demande `approved` non matérialisée — angle d'observabilité fermé pour le SIEM/admin.
