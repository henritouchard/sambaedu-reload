## Détail des problèmes

### #1 — `addAssignment` ne fermait pas le piège #3 (vecteur ajout d'assignation)

**Sévérité** : 🟠 — **Pertinence Opus** : 3/3 (CONFIRMÉ, le vrai bug de la story)
**Fichier** : `resources/views/pages/shares/[id]/index.blade.php` (`addAssignment`)

**Constat (Sonnet, confirmé Opus)** : `addAssignment` persistait la ligne pivot + `reprovision()` sans appeler `assertNoLetterCollision`. Seuls `saveDetails` et `createShare` (où `share.id` null → audience vide → pas de collision) validaient. Opus a confirmé via `StateCompiler::selectAggregate` que la dédup se fait par **payload complet** (`contentKey`) : deux candidats `{P:, unc:A}` / `{P:, unc:B}` survivent tous deux → P: mappé 2× → indéterminé côté agent. Le validateur prédictif était l'UNIQUE garde, et `addAssignment` la contournait. `changeAccess`/`removeAssignment` ne peuvent pas introduire de collision (lettre/cible fixes, ou audience rétrécie) — OK.

**Failure scenario** : Share A `P:`+User1 ; Share B `P:` sans audience ; assigner User1 à B → collision réelle non détectée → 2 montages P: UNC différentes pour User1.

**Action — corrigé** : `addAssignment` enveloppe `updateOrCreate` + `assertNoLetterCollision($this->share)` dans une `DB::transaction` ; sur `NetworkShareLetterCollisionException` → rollback de l'assignation + `toastError`, pas de `reprovision`. Forme transactionnelle (vs delete manuel) pour gérer proprement le cas upsert. Test ajouté : `letter_collision_is_blocked_on_add_assignment_and_rolled_back` (vérifie l'absence de la ligne pivot après refus).

### #2 — Double `WorkstationGroup::find()`

**Sévérité** : 🟡 — **Pertinence** : 1/3
**Fichier** : `[id]/index.blade.php` (`describeAssignable`)

**Constat** : la branche WG appelait `find($id)` 2× quand `display_name` falsy. **Action — corrigé** : arm `match` convertie en closure avec variable locale `$wg` (un seul `find`).

### #3 — `LETTER_POOL` hardcodé dans le validateur

**Sévérité** : 🟡 — **Pertinence** : 1/3
**Fichier** : `NetworkShareValidator::suggestNextFreeLetter` + `DrivesStateProvider`

**Constat** : `range('M','Z')` codé en dur au lieu du foyer canonique `LETTER_POOL` (resté privé). Identique aujourd'hui, risque de divergence future. **Action — corrigé** : `LETTER_POOL` private→public sur le provider (symétrie avec `RESERVED_LETTERS`, Q4) ; `suggestNextFreeLetter` le consomme.

### #4 — `RoutesProtectionTest` incomplet

**Sévérité** : 🟡 — **Pertinence** : 2/3
**Fichier** : `tests/Feature/Http/RoutesProtectionTest.php`

**Constat** : le filet de non-régression du middleware `can:` ne couvrait pas les routes `shares`. **Action — corrigé** : ajout de `'shares listing' => ['/app/shares', 'networkshare.view']` et `'shares show' => ['/app/shares/1', 'networkshare.view']`. RoutesProtection 32/32.

### #5 — Index `mount()` sans `abort_unless`

**Sévérité** : 🟡 — **Pertinence** : 1.5/3 (exposition surévaluée par Sonnet)
**Fichier** : `resources/views/pages/shares/index.blade.php`

**Constat** : asymétrie avec la page détail (qui a `abort_unless` au mount). Opus note que le risque d'hydratation directe via `/livewire/update` est quasi-nul (Livewire protège par checksum de snapshot, lui-même obtenu via un rendu déjà gardé par la route) — le vrai défaut est l'incohérence + le test manquant. **Action — corrigé** : `abort_unless(Gate::allows('view-networkshare'),403)` en tête de `mount()` (defense-in-depth) + test `user_without_view_permission_is_forbidden_on_index`.

### M-A — Collision cross-maille non détectée (DÉCISION USER)

**Sévérité** : 🟠 — **Trouvé par Opus (manqué par Sonnet)**
**Fichier** : `NetworkShareValidator::audienceKeys/letterCollisions`

**Constat** : le recouvrement d'audience est calculé sur les clés LITTÉRALES du pivot (`User#5`, `UserGroup#12`), pas sur l'appartenance effective. Une collision où un user est atteint par DEUX mailles différentes (direct + via son groupe ; ou direct + via un parc) n'est pas signalée. Rouvre partiellement le piège #3 sur le vecteur multi-maille. Le test `letter_collision_is_blocked_on_save` ne couvre que le cas même-maille.

**Avis Opus** : corriger exigerait d'expandre l'appartenance (`UserGroup→users`), à rebours du principe « pure lecture, zéro re-requête d'appartenance » du provider ; le cas WG est de toute façon imprédictible (qui se connecte sur les postes du parc est inconnu). **Reco : limitation assumée et documentée, fermeture en 34.x** (où la lettre stable règle aussi le sujet). Documenté dans le docblock `audienceKeys` + le runbook QA. **Non corrigé en attente de ta décision.**
