### #1 — Câblage onglet `state` des pages parentes non testé

### #3 — `via_app_id` non déterministe (multi-parents, même batch BFS)

**Sévérité** : 🟠

**Constat initial (review)** : `whereIn(...)->get()` sans ORDER BY ; premier parent rencontré = attribué. Si une dépendance a ≥ 2 parents dans le même batch, le libellé « Dépendance de X » varie selon le plan SQL. L'ensemble `app_id` (invariant AC3) n'est pas affecté.

**Avis Opus** : 2/3 — confirmé ; impact purement cosmétique (tooltip), le choix inter-batch (profondeur) reste déterministe. `orderBy` = hardening zéro-risque.

**Solutions possibles** : 1. `->orderBy('application_id')` + test 2-parents.

**Action** : corrigé automatiquement.

### #7 — Onglet `state` fiche poste accroché au mauvais `@if` (découvert en test réel)

**Sévérité** : 🔴
**Fichier(s)** : `resources/views/pages/parc/machines/[id]/index.blade.php:1528`

**Constat (Henri, test réel VM)** : la card « Groupes logiques » (branche Général) apparaît dans l'onglet État cible. Vérification structurelle : la chaîne d'onglets est `@if wpkg → @elseif agent → @else (Général)` ; le `@elseif ($tab === 'state')` (l.1528) a été inséré DANS la branche `@else`, accroché au `@if ($deploySuccess->isNotEmpty() || …)` de la card déploiement (l.1399). Deux effets : (a) en `?tab=state` toute la branche Général se rend au-dessus de l'état cible ; (b) sur un poste ayant des statuts de déploiement, le `@elseif` n'est jamais atteint ⇒ l'état cible ne se rend pas du tout. La page PARC est correctement câblée (le `@elseif state` y précède le `@else`). Ce défaut est exactement ce que le finding #1 (câblage jamais testé end-to-end) annonçait — il aurait été attrapé par un test `setTab('state')` de page.

**Solutions possibles** : 1. Remonter le bloc `@elseif ($tab === 'state')` dans la chaîne plate (avant le `@else` Général), redonner au `@if` déploiement son `@endif` propre, + tests de page dans les deux sens (état cible visible avec statuts de déploiement présents ; « Groupes logiques » absent en tab=state, présent en tab=general).

**Action** : corrigé automatiquement (passe de corrections en cours).

### P1 — Navigation ressentie lente vers l'onglet État cible (signalement Henri)

**Sévérité** : 🟠
**Fichier(s)** : les deux SFC `desired-state-tab.blade.php`

**Constat** : la bascule d'onglet monte le SFC en synchrone dans le même roundtrip que le re-rendu complet de la page parente (1 600-2 100 lignes). Mesures VM : le service est rapide (`applicationsFor` 9-23 ms, `shortcutsFor` 3-6 ms, `applicationsForGroup` 13 ms), env sain (prod, debug off, TTFB 40 ms, `wire:poll` uniquement pendant une action). Le coût ressenti = cycle Livewire complet + montage synchrone. NB : le bug #7 y contribuait aussi (rendu de la branche Général EN PLUS de l'état cible).

**Solutions possibles** : 1. Lazy-loading Livewire (`#[Lazy]`/param maison + placeholder squelette DaisyUI) — pattern déjà présent dans le projet (`parc/index`, `admin/settings/gpo`).

**Action** : corrigé automatiquement (passe de corrections en cours).
