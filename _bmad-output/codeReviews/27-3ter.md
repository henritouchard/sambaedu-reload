## Détail des problèmes

### #1 — `try/catch` mort dans `saveOverride()`

**Sévérité** : 🟠 — **Fichier** : `resources/views/pages/parc/groups/_partials/registry-tab.blade.php`

**Constat (sonnet)** : `try { $x = f(); } catch (ValidationException $e) { throw $e; }` re-lance immédiatement sans rien faire (Livewire gère nativement `ValidationException`). Dead code + asymétrie trompeuse avec `saveDefault()` (sans try/catch).
**Avis Opus** : pertinence 2. Confirmé, impact fonctionnel nul, cosmétique trompeur.
**Action** : ✅ **Corrigé** — try/catch supprimé, appel direct `$serialized = $this->validatedSerializedValue($setting);` (symétrique avec `saveDefault()`).

### #2 — N+1 dans `overrides()`

**Sévérité** : 🟠 — **Fichier** : `registry-tab.blade.php`

**Constat (sonnet)** : un `RegistrySetting::find()` par ligne d'override.
**Avis Opus** : pertinence 1 (sur-évalué par sonnet : borné par la taille du catalogue, pas un hot path), mais réel et à corriger avant que le catalogue grossisse.
**Action** : ✅ **Corrigé** — une seule requête `whereIn('id', …)->get()->keyBy('id')` ; 2 requêtes au total quel que soit le nombre d'overrides. Modèles complets conservés (helpers `hasWarning()`/`displayValue()`).

### #3 — Nom de route

**Sévérité** : 🟡 — **Fichier** : `routes/web.php`
**Constat/Opus** : `.name('settings.registry')` dans le groupe `.name('admin.')` → `admin.settings.registry` (correct, utilisé tel quel dans les vues). Idiomatique, iso sœurs. **Non-issue.**
**Action** : ❌ Non corrigé (rien à corriger).

### #4 — Override sur réglage retiré : résolu par le « gel » (D8)

**Sévérité** : 🟡 — **Fichier** : `registry-tab.blade.php`
**Avis Opus** : pertinence 2, vraie incohérence interne.
**Discussion Henri** : le débat a révélé que `is_active = false` (couper la diffusion) **fige les postes** sur leur dernière valeur (stranding), et qu'un décommissionnement sûr exige la **convergence observée** de la flotte (non garantie : cycle agent ~1 h, postes éteints).
**Action** : ✅ **Résolu autrement (D8)** — le toggle `is_active` est **retiré** de l'UI ; nouveau flag **`overrides_locked`** (« geler ») verrouille les **nouveaux** overrides **sans couper la diffusion** (provider intouché). Les overrides existants restent **listés/éditables** (donc `overrides()` les montre volontairement — ce n'est plus un orphelin). Le vrai décommissionnement → **story de suivi** gatée sur la convergence. Migration `090300`, `toggleLock`, filtre `addableSettings`, +2 tests.

### #5 — Tests manquants validation SZ vide

**Sévérité** : 🟡 — **Fichiers** : tests onglet parc + page serveur
**Constat** : le code rejette bien la chaîne vide (SZ/EXPAND_SZ) mais aucun test ne couvrait ce chemin (piège n°7 : couverture critique).
**Action** : ✅ **Corrigé** — `validation_rejects_empty_string_for_sz` (parc) + `validation_rejects_empty_string_default_for_sz` (serveur) ajoutés.

### #6 — `withPivot('value')` partiel

**Sévérité** : 🟡 — **Fichier** : `app/Models/RegistrySetting.php`
**Constat** : présent seulement sur `workstationGroups()`. Pas de bug v1 (provider lit en SQL brut) mais incohérence défensive.
**Action** : ✅ **Corrigé** — ajouté à `workstations()`/`userGroups()`/`users()`.

### #N1 — Overflow QWORD silencieusement tronqué (trouvé par Opus)

**Sévérité** : 🟡 — **Fichiers** : `registry-tab.blade.php` + `admin/settings/registry/index.blade.php` (`validatedSerializedValue`)
**Constat (Opus)** : une valeur QWORD > `PHP_INT_MAX` (ex. 20 chiffres) passe la regex, est **clampée** par `(int)` à `PHP_INT_MAX`, la borne `$int > $max` est alors fausse → **acceptée et stockée tronquée** au lieu d'être rejetée. Silent input corruption (mineur : nécessite un QWORD à 20 chiffres).
**Action** : ✅ **Corrigé** — bornage **sans `(int)`**, par comparaison de la chaîne de chiffres (longueur puis `strcmp`), négatifs rejetés. Appliqué aux **deux surfaces** + 2 tests de régression (`validation_rejects_qword_overflow_*`).
