## Questions en attente Henri

> Questions bloquantes nécessitant un arbitrage Henri AVANT de pouvoir merger.

**Q1 — BOOTSTRAP_TOKEN absent du fragment (Finding #1, pertinence 3/3)** :

Le fragment migration envoie `X-Bootstrap-Token: $env:BOOTSTRAP_TOKEN` (Windows) ou `X-Bootstrap-Token: ${BOOTSTRAP_TOKEN:-}` (Linux), mais aucun mécanisme côté serveur ne fournit ce token au poste. `MigrationFragmentRenderer::resolveTemplateVariables()` n'injecte pas de token. Le middleware `RequireBootstrapToken` retourne 401 strict si absent → boucle 401 sur 100% des postes vierges SE4.

Option A — **Mint token serveur** : `MigrationController::serveFragment` génère un token éphémère, le stocke en APCu (`apcu_store('apps.'.$tok, ['uuid'=>$uuid, 'time'=>time()], 1800)`), l'injecte comme variable Blade dans le fragment. Le fragment fait `set "BOOTSTRAP_TOKEN=<tok>"` avant le curl enroll.

Option B — **Endpoint enroll "first-call" sans bootstrap** : `/api/v1/agent/enroll` accepte les appels sans bootstrap_token si le header `X-Migration-Source: fragment` est présent + IP LAN. Sécurité = LAN-only confiance.

Option C — **Hybride** : token long (256 bits) lié à l'UUID dans le fragment, mis en cache courte durée APCu, validé par le middleware comme variante du chemin actuel.

> **Recommandation Opus : Option A** (parité 16.11 + minimum d'écart au code existant `RequireBootstrapToken`). Coût implémentation : ~30 lignes (1 service mint + 1 injection variable Blade + 2 lignes dans chaque fragment + tests).

---

**Q2 — Opus-A : Compteur "X/Y postes migrés" non scoped par filtre UI** :

`getMachineStats()` calcule le compteur sur la **globalité** des postes, indépendamment du filtre OS / groupe / migration actif. L'admin voit toujours X/Y global même en filtrant Linux uniquement.

Option α — **Scoper le compteur aux filtres actifs** (cohérence UX) : passer les filtres au service, appliquer les mêmes restrictions.
Option β — **Garder le global + ajouter un compteur secondaire scoped** dans le header du tableau machines.
Option γ — **Ne rien changer** (le compteur global est une volonté).

> **Recommandation Opus : Option α** (cohérence visuelle simple — ce que l'admin voit dans le tableau doit correspondre au compteur).

### #1 — BOOTSTRAP_TOKEN absent du fragment

**Sévérité** : 🔴 Critique
**Fichier(s)** : `resources/views/auth/v1/migration/fragment-cmd.blade.php:65`, `resources/views/auth/v1/migration/fragment-sh.blade.php:64`, `app/Auth/V1/Migration/Services/MigrationFragmentRenderer.php:169-183`

**Constat initial (sonnet)** :
Le fragment envoie un header `X-Bootstrap-Token` mais aucun mécanisme ne fournit le token au poste. `RequireBootstrapToken` rejette 401 systématiquement. Boucle infinie en prod : fragment → enroll → 401 → pas de `Migrated=1` → prochain boot → même fragment.

**Avis Opus (3/3 — confirmé)** :
Vérification indépendante OK. `MigrationFragmentRenderer::resolveTemplateVariables()` n'injecte pas de token. La story confirme explicitement (l.130) qu'après Option β, `applications.php` ne pose plus de clé APCu. Aucun mode de dégradation dans `RequireBootstrapToken`. C'est un bug d'intégration entre les designs 16.11 (qui mintait le token via `InjectBootstrapFragment::mintBootstrapToken()`) et 16.13bis (qui supprime ce middleware sans remplacement).

**Solutions possibles** :
1. **Option A — Mint token serveur** dans `MigrationFragmentRenderer` (parité 16.11)
2. **Option B — Mode "first-enroll" LAN-only** sans bootstrap token (`X-Migration-Source: fragment` + middleware `EnsureLanIp`)
3. **Option C — Token long lié UUID** posé en APCu courte durée

**Action** : ⏳ En attente arbitrage Q1 Henri (recommandation Opus : Option A).
