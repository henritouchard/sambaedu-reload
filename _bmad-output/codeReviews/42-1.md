## Détail des problèmes

### #1 — Chemins d'écriture pivot oubliés : deux UI créent des arêtes `member` pour des profs

**Sévérité** : 🟠
**Fichier(s)** : `resources/views/pages/users/[login]/index.blade.php:238`, `resources/views/components/organisms/groups-drawer.blade.php:354,358`

**Constat (review sonnet)** :
`syncGroupsFromAd()` et `applyChanges()` écrivent le pivot avec des tableaux plats d'ids : toute nouvelle arête reçoit le défaut DB `'member'` sans passer par `defaultRoleForGlobalRole()`. Un prof rattaché via ces UI devient `member` silencieusement. Pas une régression (ces flux n'écrivaient pas `is_head_teacher` non plus), et AC5 scope littéralement la dérivation à `persistUserGroupsToSql` — mais vrai risque produit.

**Évaluation orchestrateur** :
Pertinence : 3 — confirmé sur code ; l'enjeu dépasse le cosmétique : dès 42.2 la projection AD routera par rôle d'arête, donc un prof `member` serait projeté dans `Classe_X` (régression vs l'heuristique `isProf` actuelle). Solution dérivable sans choix d'archi : même pattern « nouvelles arêtes uniquement » que `persistUserGroupsToSql`.

**Solutions possibles** :
1. Instrumenter les deux call sites dès 42.1 (retenue).
2. Documenter comme dette à lever en 42.3.

**Action** : corrigé automatiquement — helper partagé `User::userGroupSyncPayloadWithDerivedRole()` (arêtes nouvelles → `['role' => dérivé]`, arêtes existantes → sans attribut, jamais réécrites) câblé sur les 3 écritures ; 3 tests dédiés (`UserDerivedRolePayloadTest`), dont la survie d'un `owner` à un resync.
