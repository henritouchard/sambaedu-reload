## Détail des problèmes

### #M1 — SE4FS_NAME : la variable racine substituée part avec le catalogue supprimé

**Sévérité** : 🟠 (manqué par la review sonnet, identifié au second avis opus)
**Fichier(s)** : `app/Wpkg/Deployment/Services/WpkgBundleGenerator.php:198-210`, `app/Services/AppStore/PackagesXmlService.php`, `tests/.../WpkgBundleGeneratorTest.php`

**Constat (second avis)** :
Le catalogue `resources/wpkg/packages.xml` supprimé (D2) portait `<variable name="SE4FS_NAME" value="se4fs_name" source="sambaedu"/>` **à la racine `<packages>`**. `PackagesXmlService::regenerate()` ne génère QUE les `<package>` des recipes installés — il n'émet jamais de variable racine. Le legacy `packages_xml_out.php` substitue par-package, et les recipes réels (ex. firefox) portent la variable **à l'intérieur de leur `<package>`**. Ces variables-là survivent à `regenerate()` (pas dans la liste stripée) et `buildSubstitutedCatalog` les retrouve via `getElementsByTagName('variable')` (récursif). **Donc le chemin par-package fonctionne** — mais les tests/QA ne le prouvaient qu'au niveau racine (cas qui ne se reproduit plus).

**Avis Opus** : pertinence 2. Risque fonctionnel réel mais **conditionnel** : le code est correct si les recipes portent la variable par-package. À confirmer en /vm.

**Action** : ✅ test ajouté (`se4fs_name_substitution_is_applied_on_per_package_variable`) prouvant la substitution d'une variable **imbriquée dans un `<package>`**. ⏳ Validation terrain Henri (cf. Question 1) : inspecter un recipe réel du parc.

### #1 — D5 : pas de re-vérification de l'écriture après régénération

**Sévérité** : 🔴 (sonnet) → 🟡 (opus : scénario quasi-impossible, TOCTOU)
**Fichier(s)** : `app/Wpkg/Deployment/Services/WpkgBundleGenerator.php:137-146`

**Constat initial** : `moduleCatalogPath()` appelle `regenerate()` si le fichier est absent puis retourne `$path` sans re-`is_file()`. Si `regenerate()` finissait sans écrire, `buildSubstitutedCatalog` lèverait « Catalogue source introuvable » (trace trompeuse).

**Avis Opus** : pertinence 1. `regenerate()` throw lui-même si `save()` échoue ; le scénario exige un TOCTOU. Cosmétique, mais le guard est sûr et clarifie le diagnostic.

**Action** : ✅ corrigé — guard `is_file($path)` après `regenerate()`, `RuntimeException` au message explicite « Régénération D5 terminée mais catalogue module toujours absent ».

### #2 — `regenerate()` hors du try/catch D4

**Sévérité** : 🟠 · **Avis Opus** : pertinence 1 — **rejeté**. La prémisse « casse le flux sans log » est fausse : `updateLocalPackagesXml()` est appelé dans `finalizeInstallation()` → try/catch de `installApplication()` qui logge `[AppStore] Erreur installation` et marque l'install `Failed`. L'asymétrie (catalogue = échec dur, bundle = tolérant) est **un choix de design correct et documenté** (docblock D4). Pas de correction.
