## Détail des problèmes

### #1 — Dispatch event hors transaction (pas via `DB::afterCommit`)

**Sévérité initiale Sonnet** : 🟠 → **réévalué Opus** : 🟡

**Fichier(s)** : `app/Services/AppProfile/AppProfileService.php:200-209, 229-238, 261-270, 292-301, 323-332, 354-363` + nouvelles méthodes 15.4 (`addApplicationsToWorkstationGroup`, `removeApplicationsFromWorkstationGroup`, `addApplicationsToWorkstation`, `removeApplicationsFromWorkstation`) ~lignes 392-508.

**Constat initial (sonnet)** : toutes les méthodes mutatrices font `DB::transaction(fn() => ...)` puis `event(...)` HORS transaction. Si transaction parente imbriquée (Command/Job futur), savepoint → dispatch trop tôt → cache invalidé pour état non commit. AC6.3 demandait `DB::afterCommit()`.

**Avis Opus** :
- Pertinence **1** (peu pertinent en pratique).
- Livewire n'ouvre pas de transaction racine par défaut. Listeners `InvalidateWorkstationPackagesCache` et `RegenerateWorkstationIniOnOptionsChanged` sont **synchrones** (pas de `ShouldQueue`).
- Le `event()` hors closure est appelé après la fermeture de `DB::transaction` qui a déjà commit → dispatch correct dans le contexte actuel.
- Risque réel : si futur appel depuis Command/Job/bulk import avec transaction parente.
- Le pattern `DB::afterCommit` reste plus robuste et auto-documentant.

**Solutions possibles** :
1. Wrapper le `event(...)` dans `DB::afterCommit(fn() => event(...))` à l'intérieur de chaque closure de transaction (6 méthodes existantes + 4 nouvelles + `cloneConfiguration`). Hygiène défensive.
2. Laisser tel quel et inscrire en dette technique.

**Action** : ⏳ Question Q1 utilisateur.

### #4 — `LEGACY_OPTIONS` PHPDoc + `normalizeValue` accepte int

**Sévérité** : 🟡

**Fichier(s)** : `app/Wpkg/Deployment/Services/WorkstationOptionsService.php:135-141, 143-164`

**Constat initial (sonnet)** : `allowedKeys()` mappe `LEGACY_OPTIONS` ; PHPDoc dit `array<string,bool|string>` mais AC5.4 demande string strict ; `normalizeValue` accepte 1/'1'/0/'0'.

**Avis Opus** : Pertinence **1** (faux positif partiel).
- `allowedKeys()` est verrouillé sur la constante canonique (pas de risque de désync).
- PHPDoc légèrement imprécise mais le `normalizeValue` couvre `bool|int|string|null` proprement et lève sur valeur invalide.
- Accepter `1`/`0` est défensif (utile pour ints venant de `request()->boolean`). Pas un défaut, plutôt une feature.

**Solutions possibles** :
1. Resserrer la PHPDoc à `array<string, bool|string|int|null>` pour refléter la réalité.
2. Laisser et documenter dans un commentaire que la coercion est volontaire.

**Action** : ❌ Non corrigé (Opus juge OK).
