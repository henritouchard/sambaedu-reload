## Détail des problèmes

### #1 — 🔴 Scope `session` incompatible avec l'écriture machine-wide de `policies.json`

**Fichier(s)** : `agent/windows/handler_app_config_windows.go:49-61,133-154` · `app/Services/Agent/Providers/AppConfigStateProvider.php:49-54` (scope session)

**Constat (review sonnet, confirmé opus au code)** : `Write()` fait `os.MkdirAll` + `os.WriteFile` + `os.Rename` sous `%ProgramFiles%\<app>\distribution\` (ACL `Users: Read & Execute` seulement). Le provider déclare `scope = session` → le compagnon exécute à l'identité de l'élève au logon → `ACCESS_DENIED`. Sur tout poste non pré-ACLisé, l'item `app_config` est en `error` permanente. Le dev l'a documenté (non-ignoré), mais c'est **fonctionnellement inopérant en prod**, pas « dégradé ».

**Avis Opus (pertinence 3)** : ce n'est pas qu'une limite documentée — c'est une **contradiction de conception** entre le *mécanisme de livraison* (policies.json = artefact MACHINE, admin-write) et le *scope d'exécution* (session = user). Le dev a choisi `session` pour une bonne raison (les niveaux 5-6 du merge 4.8 — UserGroups/User — exigent `$user`, connu au logon). Mais un fichier machine-wide **ne peut pas** porter des policies par-user, ni être écrit par un process user. La promesse « combiner parc + user » (la question d'origine d'Henri) est, pour le mécanisme `policies.json`, **mécaniquement bancale** : on peut RÉSOUDRE parc+user côté serveur, mais on ne peut pas le LIVRER via un fichier machine non-writable par l'user.

⚠️ Correctif de cadrage de mon conseil initial : j'avais dit « scope session permet de combiner parc+user ». C'est vrai pour la *résolution*, faux pour la *livraison* d'un `policies.json` (machine-wide, admin-write). Je le corrige ici.

**Solutions possibles** :
1. **(recommandé) Scope `machine`** : `app_config` porté par le `MachineEngine` SYSTEM (iso `registry` HKLM 27.3). `resolvePoliciesForMachine($wg, null, $kind, $os)` → résout niveaux 1-4 (template + auto + défaut étab + WG). SYSTEM écrit Program Files (OK). **Coût** : on perd les niveaux 5-6 (Firefox par-user) — mais le legacy ne les faisait pas, et un fichier machine-wide ne peut de toute façon pas les porter proprement. Robuste, aligné sur la nature de `policies.json`.
2. **Scope `session` + ACL pré-provisionnée** : l'installeur Firefox (27.5) pose `Users: Write` sur `distribution\`. Garde le par-user (réécriture par logon), mais sémantique douteuse (fichier machine thrashé par logon, last-logon-wins sur poste partagé), dépendance de déploiement, et affaiblit la sécurité (Users écrit sous Program Files).
3. **Scope `session` + registre HKCU** (À VÉRIFIER) : si Firefox lit les policies depuis `HKCU\Software\Policies\Mozilla\Firefox` (support à confirmer selon version), un compagnon user écrit HKCU (writable) → vrai par-user sans bricolage ACL. **Coût** : change le mécanisme (fichier → registre) ; spike de validation requis.

**Action** : décision Henri requise. Recommandation opus = **option 1 (machine scope)** — corrige le défaut, accepte que la config d'app via `policies.json` est par-parc (parité legacy), et reste robuste. Si le par-user Firefox est un vrai besoin terrain, spike option 3.

### #2 — 🟠 Collapse WG multi-parcs logiques : perte silencieuse du 2ᵉ parc

**Fichier(s)** : `app/Services/Agent/Providers/AppConfigStateProvider.php:157-169` (`precedenceWinningGroup()`)

**Constat** : `precedenceWinningGroup()` prend `logicalGroupIds[0]` (plus petit id SQL après `sort()`). Un poste dans 2 parcs logiques avec policies Firefox différentes → seul le parc au plus petit id est résolu, l'autre disparaît, statut `compliant` trompeur. Comportement différent des autres providers (qui émettent 1 item/maille et laissent le compilateur arbitrer). Aucun test PHP du cas 2-parcs.

**Avis Opus (pertinence 2)** : conséquence directe de l'impédance « `resolvePoliciesForMachine` ne prend qu'UN `$wg` ». La décision est défendable (1 item/app), mais le tiebreak « plus petit id » est un **artefact** non métier. Pour un mécanisme de policies *fusionnables*, l'idéal serait de merger les policies de TOUS les WG applicables (vrai aggregate) ; à défaut, le tiebreak doit être une **règle explicite** (ex. priorité de parc, ou `updated_at`), pas l'ordre SQL. Lié à #1 (si machine scope, le collapse reste mais sur niveaux 1-4).

**Solutions** : (a) documenter + tester le comportement actuel (auto) ; (b) [design Henri] remplacer le tiebreak par une règle métier OU merger tous les WG.

**Action** : test + doc en correction auto ; règle de tiebreak = question Henri n° 3.

### #3 — 🟠 Pas de test de parité des canonicalizers Go (`json.Number`)

**Fichier(s)** : `agent/shared/handler_app_config.go:382-405` · `agent/windows/handler_app_config_windows.go:248-271`

**Constat** : `shared.canonicalPolicies` (cible) et l'encodeur windows (fichier relu) sont deux implémentations censées produire les MÊMES octets, mais aucun test ne le vérifie avec des `json.Number` (le payload réseau est décodé `UseNumber`). Si elles divergent (ex. `json.Number("1")` vs `int(1)`, tableau vide, unicode), `Matches()` renvoie toujours `false` → réécriture du `policies.json` **à chaque logon** (perte d'idempotence), invisible aux tests actuels (littéraux Go natifs).

**Avis Opus (pertinence 3)** : vrai risque de prod (boucle de réécriture) non couvert. Bonne prise.

**Solution** : test Go construisant un spec avec `json.Number`, comparant la forme canonique cible et la forme relue. Si divergence → unifier la canonicalisation (idéalement UNE fonction partagée dans `shared`, appelée par windows).

**Action** : correction auto (ajout test ; correctif si rouge).

### #7 — 🟡→🟠 Faux `compliant` quand `policies.json` hors-périmètre présent

**Fichier(s)** : `agent/shared/handler_app_config.go:167-168` · `agent/windows/handler_app_config_windows.go:82-101`

**Constat** : un `policies.json` sans marqueur (admin/autre outil) occupant le chemin Firefox + Firefox dans les règles → `Test()` = `true` → rapport `compliant`. Or les policies SambaEdu ne sont PAS actives (c'est le fichier étranger qui pilote Firefox). L'admin croit la policy en place.

**Avis Opus (pertinence 2, sévérité relevée à 🟠)** : c'est un **faux positif d'observabilité**. La non-ingérence (AC5 : ne jamais écraser) est juste, mais rapporter `compliant` est mensonger. Tension à trancher : `compliant` (faux), `drift` (mais drift STRICT ré-imposerait = écraserait, ce qu'on ne veut pas), ou `error` (« conflit : fichier étranger non géré » — surface le problème SANS écraser). Je penche `error` + documentation.

**Solution** : rapporter `error` (ou un statut « conflit ») quand un fichier hors-périmètre bloque l'application, OU a minima documenter explicitement que `compliant` = « non-ingérence, policy agent non active ».

**Action** : décision Henri (statut) ; doc en correction auto quoi qu'il arrive.
