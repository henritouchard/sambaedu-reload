## Détail des problèmes

### #1 — Variable `$primaryGroupName` trompeuse

**Sévérité** : 🟡 — **Fichier** : `app/Services/UserGroupService.php:69`

**Constat (review sonnet)** : `$primaryGroupName` n'est plus utilisée par la sync (remplacée par `syncRoleAwareAdGroupMembers`), seulement comme sélecteur SQL après `syncFromAd` (l.78). Trompeur pour un futur lecteur.

**Avis Opus** : pertinence 2. Confirmé, pas un bug, lisibilité.

**Action** : ✅ Corrigé — commentaire explicite ajouté précisant que la variable ne sert que de sélecteur post-sync, et que la garantie « nom nu sans préfixe » (#2) rend la résolution correcte.

### #2 — `stripClasseLikePrefix` faux positif sur nom nu à préfixe réservé

**Sévérité** : 🟠 — **Fichier** : `app/Services/UserGroupService.php` (`syncRoleAwareAdGroupMembers` / `createGroup`)

**Constat (review sonnet)** : un nom nu saisi comme `PP_terminale` (regex `validateData` autorise `_`) avec type `classe` : `GroupRepository::createGroup` bypasse via `resolvePrefixedGroupOu` et ne crée qu'`PP_terminale` ; puis `stripClasseLikePrefix('PP_terminale') = 'terminale'` → sync vers `Equipe_terminale`/`Classe_terminale` **inexistants** → add LDAP fail-soft **silencieux**.

**Avis Opus** : pertinence 3 — seul finding réellement bloquant. Précise que `resolvePrefixedGroupOu` est dans `GroupRepository` (pas `UserGroupService`), que le cas est saisissable via l'UI réelle, et qu'il existe un **pendant aval** (#2bis) : le sélecteur SQL post-sync cherche `Classe_PP_terminale` → throw « introuvable ». Nuance : la collision de préfixe **préexiste** à 4.12 (avant, ça syncait `Classe_PP_terminale`) ; 4.12 change la forme de l'échec, ne l'introduit pas.

**Solutions possibles** :
1. Bloquer dès la validation un nom à préfixe réservé pour type classe/équipe. *(retenue)*
2. Normaliser silencieusement (dé-préfixer à la saisie).
3. Documentation seule (laisser le comportement préexistant).

**Action** : ✅ Corrigé — `guardReservedPrefixOnCreate($name, $type)` ajouté dans `createGroup` (chemin create uniquement, pour ne pas casser `updateGroup` dont le `name` SQL est légitimement le CN préfixé `Classe_X`). Lève `InvalidArgumentException` si type ∈ {classe, équipe} et nom commençant par `Classe_`/`Equipe_`/`PP_`. Couvre aussi #2bis (le nom nu est désormais garanti sans préfixe → `resolvePrimaryGroupName` donne le bon CN). Test ajouté : `it_rejects_reserved_prefix_name_for_classe_like_create`.

### #3 — Requêtes SQL redondantes

**Sévérité** : 🟡 — **Fichier** : `app/Services/UserGroupService.php` (`syncRoleAwareAdGroupMembers` + `syncAdGroupMembersByUserIds`)

**Constat** : `desiredDns` et `sqlKnownDns` recalculés une fois par cible (2× par classe). Volume < 100 membres → impact nul.

**Avis Opus** : pertinence 1 — DRY mineur, code idempotent existant non touché par la story.

**Action** : ❌ Laissé en dette (backlog). Toucher la couche `syncAdGroupMembersByUserIds` réutilisée dépasse le scope du fix.

**Avis Opus** : pertinence 2 — confirmé, hygiène.

**Action** : ✅ Corrigé — purge par réflexion de `User::$ldapCache → []` ajoutée dans `tearDown`.

### #5 — Couverture de bascule asymétrique

### #6 — `'équipe'` accentué absent de la liste classe-like

**Sévérité** : 🟡 — **Fichier** : `app/Services/UserGroupService.php:526`

**Constat (review sonnet)** : type `'équipe'` accentué tomberait en non-classe-like → double préfixe `Classe_Classe_3A`.

**Avis Opus** : pertinence 1 — **diagnostic review erroné** : `'équipe'` tombe en `default => $rawName` dans `resolvePrimaryGroupName` (pas de double préfixe). Le vrai effet serait une partition shuntée (Equipe vide). Surtout : chemin **non atteignable** — l'UI envoie `equipe`/`classe` sans accent (`validateData` passe le type brut, jamais accentué).

**Action** : ❌ Laissé. Note : le garde-fou #2 inclut tout de même `'équipe'` par robustesse défensive.

### #7 — Ordre Equipe→Classe : micro-fenêtre transitoire

**Sévérité** : 🟡 — **Fichier** : `app/Services/UserGroupService.php` (ordre des deux `syncAdGroupMembersByUserIds`)

**Constat** : entre les deux syncs, un membre basculé peut être brièvement dans aucun (prof→élève) ou les deux (élève→prof) groupes.

**Avis Opus** : pertinence 1 — chaque sync est un diff add+remove séquentiel mono-thread PHP, sans observateur concurrent ; reco « aucune action » correcte.

**Action** : ❌ Laissé (acceptable).
