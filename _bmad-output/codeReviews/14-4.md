## Détail des problèmes

### #1 — Pipeline Carbon → `password_changed_at` toujours NULL (D7 cas 4 cassé)

**Sévérité** : 🔴 Critique
**Fichier(s)** : `app/Services/Concerns/ResolvesPwdLastSet.php` (l. 49-52, 71-92)

**Constat initial (review)** :
Le trait casse la décision D7 et l'AC13 cas 4 (« Carbon instance (LdapRecord auto-cast) → idem cas 3 (`now()`) »).

- `resolvePwdLastSetRaw(Carbon)` retourne `1` quand le timestamp Carbon est positif (l. 51).
- Ensuite, `pwdLastSetToCarbon(1)` calcule `intdiv(1 - 116444736000000000, 10_000_000) = -11644473599` (négatif).
- Le garde-fou l. 87 `if ($unixTimestamp < 0 …) return null;` renvoie donc **`null`**.

Conséquence : si LdapRecord auto-caste `pwdlastset` en `Carbon` (cas documenté dans la story l. 39), `password_changed_at` est mis à **NULL** au lieu de `now()` (cas 3) — donc le user apparaît comme « mdp par défaut » à TORT.

**Solutions possibles** :
- **Option A (recommandée)** : faire que `resolvePwdLastSetRaw` retourne **`-1`** (au lieu de `1`) pour un Carbon valide. `pwdLastSetToCarbon(-1)` renvoie déjà `Carbon::now()`.
  ```php
  if ($rawValue instanceof Carbon) {
      return $rawValue->getTimestamp() > 0 ? -1 : 0;
  }
  ```
- **Option B** : exposer une 3e méthode `pwdLastSetFromCarbon(Carbon): Carbon` qui préserve la VRAIE date au lieu de tomber sur `now()`.

**Action** : ✅ Corrigé (Option A — Carbon→-1). Cf. `app/Services/Concerns/ResolvesPwdLastSet.php:51` + tests `ResolvesPwdLastSetTest::it_returns_minus_one_for_carbon_*` et e2e dans `AuthenticationServicePasswordChangedAtTest::it_sets_approx_now_when_pwdLastSet_is_a_carbon_instance` + `UserSyncServicePasswordChangedAtTest::ldap_user_to_ad_data_handles_carbon_pwdlastset_as_now`.

### #2 — `upsertUser` écrase `password_changed_at` avec NULL et avale la date du login

**Sévérité** : 🔴 Critique
**Fichier(s)** : `app/Services/UserSyncService.php` (l. 628, 643)

**Constat initial (review)** :
Dans les deux branches `create` et `update`, on écrit `'password_changed_at' => $adUser->passwordChangedAt` SANS condition. Si l'AD répond `pwdlastset=0` (ou attribut absent), on **écrase la valeur existante en SQL** par `NULL`.

Scénario :
1. User `alice` s'est loggé hier → `AuthenticationService::persistPasswordChangedAt` a écrit `2026-05-20 10:00:00`.
2. Cron 5 min plus tard : si pour une raison X l'AD répond `pwdlastset` absent (ACL LDAP, attribut filtré côté replica…), `$adUser->passwordChangedAt = null`.
3. L'`update` écrit `password_changed_at = NULL` → alice apparaît comme « mdp par défaut » à tort.

**Solutions possibles** :
- (a) `'password_changed_at' => $adUser->passwordChangedAt ?? $user->password_changed_at`
- (b) Écrasement assumé (filtre piloté uniquement par AD)
- (c) `if ($adUser->passwordChangedAt !== null) { ... }`

**Action** : ✅ Corrigé (Option (a) — `??` preserve SQL existant). Appliqué uniquement sur branche `update` ; la branche `create` (nouveau user, aucune valeur SQL préexistante) reste écriture directe. Cf. `app/Services/UserSyncService.php` + tests `UserSyncServicePasswordChangedAtTest::upsert_user_keeps_existing_password_changed_at_when_ad_returns_null` et `::upsert_user_overwrites_password_changed_at_when_ad_returns_value`.
