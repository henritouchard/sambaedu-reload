## Détail des problèmes

### #1 — Test NFR3 vacuitement vrai (singleton réchauffé)

**Sévérité** : 🟠 — **Pertinence Opus** : 2/3
**Fichier(s)** : `tests/Feature/Livewire/Parc/CapabilitiesOverrideAuditTest.php`

**Constat initial (review)** :
Le test `standalone_override_is_audited_local_without_extra_item_query` appelle `openAdd()` (qui résout déjà le singleton `UpstreamLockResolver` via `isCapabilityLocked` → `ensureResolved()`) AVANT `DB::enableQueryLog()`. Le resolver est donc chaud ; dans la fenêtre mesurée (`saveOverride`), `ensureResolved()` court-circuite et ne touche AUCUNE table → `assertSame(0, $itemQueries)` passe pour la mauvaise raison.

**Avis Opus** : Confirmé (singleton enregistré `AgentServiceProvider.php:117` ; `Livewire::test` rend le composant, la vue appelle `addableCapabilities()`→`isCapabilityLocked()`→`ensureResolved()`). **Nuance** : le comportement *de production* est correct (en PHP-FPM le singleton est par-requête ; render+save dans la même requête → résolution unique, 0 requête `items` ajoutée). Le test est seulement faible **en tant que preuve du court-circuit**. Pour rendre la preuve robuste, ajouter aussi l'assertion qu'`controlhub_contracts` a bien été requêté (sinon on ne distingue pas « court-circuit » de « rien résolu »).

**Action** : ✅ **Corrigé automatiquement** — `app()->forgetInstance(UpstreamLockResolver::class)` avant `DB::enableQueryLog()` (résolution fraîche dans `saveOverride`) + assertion `assertGreaterThanOrEqual(1, $contractQueries)` (le contrat actif est bien cherché) en plus de `assertSame(0, $itemQueries)`. Le test prouve désormais réellement le court-circuit.

### #3 — `created_at` dans `$fillable`

**Sévérité** : 🟡 — **Pertinence Opus** : 1/3
**Fichier(s)** : `app/Models/CapabilityOverrideAuditLog.php`

**Constat initial (review)** : `created_at` fillable (suit `QuotaAuditLog`) → `create(['created_at'=>...])` pourrait antidater une trace, contrairement à `DelegationHistory` qui l'a retiré.

**Avis Opus** : triple barrière neutralise le risque (`log()` unique writer hardcode `now()` ; append-only ; migration `useCurrent()`). **Nuance critique manquée par sonnet** : le fix naïf « retirer du fillable » **casserait** le test unit `assertNotNull($entry->created_at)` car le modèle a `$timestamps=false` (l'instance en mémoire ne serait pas peuplée sans `refresh()`). Le durcissement correct exige de basculer sur le pattern `DelegationHistory` complet (timestamps Eloquent auto), disproportionné.

**Action** : ❌ **Non corrigé** — décision : ne rien faire (recommandation des 2 avis).

### #4 — Trace d'audit `delete` fantôme dans `removeOverride`

**Sévérité** : 🟡 — **Pertinence Opus** : 2/3
**Fichier(s)** : `resources/views/pages/parc/groups/_partials/capabilities-tab.blade.php`

**Constat initial (review)** : si `removeOverride($capabilityId)` est appelé sans override existant (rejeu, appel Livewire direct), le `delete` supprime 0 ligne mais un audit `action=delete, old_value=null` est quand même écrit → ligne fantôme dans le registre de conformité.

**Avis Opus** : confirmé et **atteignable** (`authorizeUpstream` ne refuse que `locked` ; une capacité `local`/`permissive` sans override poursuit le flux). C'est exactement le modèle de menace « propriété publique hydratée / rejeu Livewire » déjà traité en défense-in-depth pour 29.2. Surtout, la story revendique le principe (Dev Notes) : « une trace fantôme sans acte serait trompeuse ». Le fantôme viole donc un invariant que la story pose elle-même.

**Action** : ✅ **Corrigé automatiquement** — early-return dans `removeOverride()` après `authorizeUpstream` (un `locked` reste refusé explicitement) : lecture de la ligne via `first(['value'])` (distingue absence de ligne d'une `value` nulle), `return` si `null` (aucun acte → aucune trace). Test ajouté `removing_a_non_existent_override_logs_nothing`.

### #5 — Double requête `exists()`+`value()` dans `saveOverride`

**Sévérité** : Nit — **Pertinence Opus** : 1/3
**Fichier(s)** : `resources/views/pages/parc/groups/_partials/capabilities-tab.blade.php`

**Constat initial (review)** : `exists()` (pour `$hasExistingOverride`) puis `value('value')` (pour `$oldValue`) = 2 requêtes sur la même ligne ; fusionnables en `first(['value'])`.

**Avis Opus** : **piège non signalé par sonnet** — la colonne `value` est nullable ; un merge naïf `hasExistingOverride = $row?->value !== null` serait un **bug** (un override existant à `value=null` serait classé « create »). Le merge correct est par présence-de-ligne (`$row !== null`). Gain marginal (table légère).

**Action** : ❌ **Non corrigé** — nit à faible valeur avec footgun ; laissé tel quel (le code actuel est correct).

### M1 — `updateOrInsert` réécrit `created_at` du pivot (manqué par sonnet)

### M4 — Scope d'autorisation par-groupe (manqué par sonnet)

**Sévérité** : 🟠 — **Fichier(s)** : `resources/views/pages/parc/groups/_partials/capabilities-tab.blade.php` (`guardCustomize`)

**Constat (Opus)** : `groupId` est une propriété publique hydratée ; `guardCustomize()` vérifie `app.customize` **globalement**, pas par `WorkstationGroup`. Un refnum pourrait écrire/auditer sur un autre groupe en modifiant `groupId`. Gap connu (mémoire `delegation_enforcement_wpkg_gap`), **pré-existant à 29.5**. L'audit de 29.5 ne l'aggrave pas — il le *trace* fidèlement (`assignable_id` reflète la valeur utilisée).

**Action** : ⏳ **Backlog** — pré-existant, à acter dans le chantier d'enforcement de délégation par périmètre (cf. 29.1).
