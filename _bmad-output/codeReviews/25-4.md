## Questions en attente

> Questions nécessitant une réponse de Henri avant clôture / déploiement parc.

1. **(M4) `startup.cmd` réécrit la stable à CHAQUE refresh (240 min) — interaction avec l'auto-update 25.2.** Le script GPO télécharge inconditionnellement le binaire **stable** vers `agent.exe` à chaque boot/refresh. Opus juge l'effet **probablement bénin** : (a) un binaire en cours d'exécution est verrouillé par Windows → `curl -o` échoue silencieusement tant que le service tourne ; (b) le rôle « filet » assume justement de reposer la stable, puis l'auto-update re-converge vers la cible ring. **Confirmes-tu ce comportement comme intentionnel** (le filet repose la stable, l'auto-update reconverge), ou veux-tu que `startup.cmd` ne télécharge le binaire **que si `agent.exe` est absent** (réparation pure, sans écrasement périodique) ? — décision de design, laissée ouverte.

Le smoke `gpresult /H` (ligne Scripts présente) est le seul juge définitif que la CSE se déclenche.

## Détail des problèmes

### #1 — `startup.cmd` : `>/dev/null` au lieu de `>nul` (+ M1 fiabilité schtasks)

**Sévérité** : 🟠 — **Pertinence Opus : 3**
**Fichier(s)** : `resources/gpo/se4_agent_bootstrap/Machine/Scripts/Startup/startup.cmd:35,45,46`

**Constat initial (review)** : `cmd.exe` n'a pas de `/dev/null` ; `>/dev/null` crée un fichier parasite `dev\null` dans le cwd (typiquement `C:\Windows\system32\dev\null` en SYSTEM), réécrit à chaque boot et refresh.

**Avis Opus** : Confirmé sur les 3 lignes. Non bloquant fonctionnellement (les commandes s'exécutent), mais comportement Windows incorrect + incohérent avec le `2>&1` valide qui suit. **M1** : combiné à la redirection invalide, l'`errorlevel` de `schtasks /Query` peut être faussé sur cwd non inscriptible → boucle de recréation de tâche (bénigne car `/F`, mais bruyante). Touche la fiabilité du filet #27.

**Action** : ✅ Corrigé — `>nul 2>&1` sur les 3 occurrences. CRLF vérifié préservé (48 CR / 48 lignes).

### #2 — GPT.INI `gPCMachineExtensionNames` en `[CSE]` (requalifié)

**Sévérité** : 🟠 (Sonnet) — **Pertinence Opus : 1 (faux positif sur le fichier)**
**Fichier(s)** : `resources/gpo/se4_agent_bootstrap/GPT.INI`

**Constat initial (review)** : Sonnet : Windows lit `gPCMachineExtensionNames` dans `[General]` ; en `[CSE]` seul, la Scripts CSE ne s'exécute jamais.

**Avis Opus** : La prémisse est **fausse pour le fichier**. Le `[CSE]` est la **convention de template SambaEdu** : `export_gpo` legacy l'écrit ainsi, `get_gpo_template_info`/`GpoTemplateRegistry::hasCseExtensions()` la lit ainsi. À la publication réelle, `import_gpo` régénère le `GPT.INI` SYSVOL en `[General]` seul ET pose `gPCMachineExtensionNames` comme **attribut LDAP** de l'objet GPO (`modify_ad`) — c'est CE canal que lit Windows. Donc le `GPT.INI` du template est **correct**, le test `gpt_ini_carries_a_cse_section…` aussi. **MAIS** le risque pressenti par Sonnet est réel sur le **chemin de publication manuel** du runbook → voir M2.

**Action** : ✅ Requalifié — pas de modif du fichier (convention correcte) ; le vrai trou est traité en M2.
