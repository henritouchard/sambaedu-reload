## Détail des problèmes

### #1 — Note ops silencieuse sur déplacement physique du dossier archive

**Sévérité** : 🔴 Critique (Sonnet) / score Opus : 2

**Fichier(s)** : `docs/wpkg-deploy/architecture.md` (§ Migration .env), `config/sambaedu.php`

**Constat initial (review)** :
L'ancien path `reports_archive_path` valait `/var/sambaedu/unattended/install/wpkg/rapports/archive`. Le nouveau `reports_archive` vaut `/var/sambaedu/unattended/install/wpkg/archive`. Ce n'est pas un simple rename de clé : c'est un **déplacement physique** du répertoire. La note ops ne mentionne que le retrait des variables `WPKG_REPORTS_*`. Sur une VM prod avec archives existantes dans `rapports/archive/`, ces archives deviennent invisibles après déploiement.

**Avis Opus** :
Diagnostic correct (vérifié sur le diff `config/sambaedu.php`). Score 2 (et non 3) car aucun consommateur du chemin archive ne survit dans le code (grep `reports_archive_path` = 0 hits) → le runtime ne casse pas, l'archive nouvelle sera créée vide. Mais l'impact « archives historiques invisibles » suppose qu'il existe déjà des archives en prod (vraisemblable). Reste un trou de doc qui surprendra l'équipe ops.

**Solutions possibles** :
1. Ajouter une sous-section dédiée dans `docs/wpkg-deploy/architecture.md` : « Avant déploiement, exécuter `mv /var/sambaedu/unattended/install/wpkg/rapports/archive /var/sambaedu/unattended/install/wpkg/archive` (ou symlink) sinon l'historique des archives ne sera pas listé par le futur dashboard Story 15.5. » + scénario 1.6 dans `docs/qa/domains/wpkg-deploy.md`.
2. Restaurer le path `rapports/archive` dans `config/sambaedu.php` pour parité legacy stricte (sans déplacement physique), documenter le futur cleanup en dette.
3. Ajouter un check au démarrage qui détecte `rapports/archive` encore existant avec contenu, et loggue un warning explicite sur `wpkg-deploy`.

**Action** : ⏳ en attente de décision utilisateur (question 1).

### #9 — Test concurrent sans timeout parent

**Sévérité** : 🟡 Mineur / score Opus : 1 (manqué par Sonnet)

**Fichier(s)** : `tests/Feature/Support/AtomicFileWriterConcurrencyTest.php` (l. 115)

**Avis Opus** :
Le parent fait `pcntl_waitpid()` sans timeout. Si un fork bloque, le test bloque indéfiniment au lieu de fail. Risque réel faible (producer/reader ont leur propre deadline), mais bonne pratique pour CI : `pcntl_alarm()` ou `pcntl_waitpid(WNOHANG)` en boucle avec deadline + `posix_kill(SIGKILL)` au-delà de `deadline + 5s`.

**Action** : ⏳ correction recommandée comme robustesse CI.
