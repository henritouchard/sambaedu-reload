## Détail des problèmes

### P-1 — Requête en exception 500 non auditée

**Sévérité** : 🟠 · **Pertinence Opus** : 2
**Fichier(s)** : `app/Http/Middleware/Auth/AuditExternalAction.php` (handle, ~ligne 52-64)

**Constat initial (Sonnet)** : `$response = $next($request)` puis `writeAudit()` inline. Si `$next()` throw une exception non catchée, elle remonte au-dessus du middleware → `writeAudit()` n'est jamais atteint. Une mutation fédérée qui crashe (500) n'est pas auditée.

**Avis Opus (2/3)** : mécaniquement exact, mais Sonnet sur-évalue la gravité au regard de la décision **Q-5 best-effort** (la disponibilité prime, l'audit n'est pas garanti-transactionnel) et du fait qu'une 500 n'a généralement **pas** muté l'état (exception avant commit). À traiter comme **dette documentée**, pas correctif bloquant. Véhicule de fond si Henri veut combler : `terminate()` (cf. P-2).

**Solutions possibles** :
1. Documenter la limite (commentaire code + runbook QA) — *retenu pour auto-correction (M-2 voisin)*.
2. Refactor `terminate()` (résout aussi P-2) — décision utilisateur.

**Action** : ✅ **Corrigé (post-review, arbitrage Henri)** — refactor en
middleware **terminable** : `handle()` se réduit à `return $next($request)` et
l'audit vit dans `terminate(Request, Response)`. Le handler d'exceptions
convertit le throw en réponse 500 AVANT `terminate()` → l'action en erreur est
désormais auditée (`status_code=500`). Nouveau test
`mutating_federated_action_returning_500_is_audited`. Commentaire P-1 du code
mis à jour (limite supprimée). `Auth::user()` confirmé résolvable en
`terminate()` (test `auth_user_is_resolvable_in_terminate`) — aucun fallback
`FederatedSession` nécessaire.

### P-2 — Middleware non-Terminable, latence inline

**Sévérité** : 🟠 · **Pertinence Opus** : 2
**Fichier(s)** : `app/Http/Middleware/Auth/AuditExternalAction.php`

**Constat initial (Sonnet)** : l'INSERT d'audit est dans la pile de réponse → son temps s'ajoute au TTFB. Propose `terminate()`.

**Avis Opus (2/3)** : exact ; `terminate()` est la bonne cible (s'exécute après l'envoi de la réponse, corrige partiellement P-1 puisque le handler convertit la 500 en réponse). MAIS impact latence réel faible (1 INSERT local) et le refactor touche un middleware auth sensible → à faire **délibérément avec test dédié**, pas en correction automatique aveugle.

**Action** : ✅ **Corrigé (post-review)** — résolu par le même refactor
`terminate()` que P-1 : l'INSERT d'audit s'exécute **après** l'envoi de la
réponse au client → sort de la pile de réponse, zéro latence ajoutée au TTFB.

### P-3 — Assertion AC7 tautologique

**Sévérité** : 🟡 · **Pertinence Opus** : 2
**Fichier(s)** : `tests/Feature/Auth/Federated/ExternalActionAuditTest.php`

**Constat initial (Sonnet)** : l'assertion `! str_contains(json_encode($context), 'Tech Externe')` porte sur un `$context` construit en dur (`['action_type'=>..., 'exception'=>$e::class]`) qui ne peut structurellement jamais contenir la PII → l'assertion ne peut pas régresser.

**Avis Opus (2/3)** : exact et bien vu. La proposition `assertSame(['action_type','exception'], array_keys($context))` pin la forme exacte du contexte et casserait si quelqu'un rajoutait `'message'=>$e->getMessage()` (la régression précisément redoutée par le correctif PII du dev).

**Action** : ✅ **Corrigé automatiquement** — assertion remplacée par un contrôle exact des clés du contexte.

### P-4 — GET route sans nom non testé

**Sévérité** : 🟡 · **Pertinence Opus** : 1
**Fichier(s)** : `app/Http/Middleware/Auth/AuditExternalAction.php` (isSensitiveGetRoute), test absent

**Constat initial (Sonnet)** : `isSensitiveGetRoute()` retourne `false` si `getName()===null` → une route GET sensible non nommée échapperait à l'audit, sans test ni alerte.

**Avis Opus (1/3)** : marginal — le mécanisme D-2 est par conception basé sur les noms, toutes les routes app/admin réelles sont nommées, les mutations restent auditées sans nom. Cas-test défensif bienvenu mais faible priorité.

**Action** : ✅ **Corrigé automatiquement** — ajout d'un test défensif « GET route sans nom → non audité ».

### P-5 — `/test-auth` atteignable sans `federated.audit`

**Sévérité** : 🟡 · **Pertinence Opus** : 2
**Fichier(s)** : `routes/web.php` (~ligne 24)

**Constat initial (Sonnet)** : route top-level `sambaedu.auth` seule, atteignable par un externe fédéré actif, sans `federated.audit` → faux négatif d'imputabilité ; pattern dangereux pour futures routes hors groupes app/admin.

**Avis Opus (2/3)** : **nuance que Sonnet rate** — `/test-auth` est une route de **debug** (renvoie `{status:ok, time}`, aucune PII, aucune mutation) → risque concret nul aujourd'hui. Le vrai enjeu est **préventif** : un test d'archi « toute route `sambaedu.auth` ⇒ `federated.audit` » est la bonne mitigation de fond.

**Solutions possibles** :
1. Supprimer `/test-auth` (route de debug).
2. Ajouter `federated.audit` + test d'archi anti-régression.

**Action** : ✅ **Corrigé (post-review, arbitrage Henri)** — `/test-auth` reçoit
`federated.audit` (no-op fonctionnel : GET debug non sensible, hors allowlist).
Ajout d'un **test d'archi** `FederatedAuditCoverageTest` qui vérifie l'invariant
TOTAL « toute route `sambaedu.auth` ⇒ `federated.audit` » via la pile RÉELLE
(`Route::gatherMiddleware()`, groupes inclus).

> **Découverte (à arbitrer)** : le test d'archi a révélé **2 autres** routes
> `sambaedu.auth` SANS `federated.audit`, NON corrigées (hors scope P-5, non
> triviales) et placées en allowlist d'exceptions tracée dans le test :
> - `livewire/update` (POST) — endpoint Livewire enregistré programmatiquement
>   (`AppServiceProvider::setUpdateRoute`, + variante préfixée proxy). Vrai canal
>   mutant → vraie lacune, correction sensible (impacte tout le front).
> - `api/v1/health/detailed` (GET) — route API privée legacy (`routes/api.php`),
>   lecture seule health check.
>
> Toute **nouvelle** route `sambaedu.auth` sans audit fera échouer le test ; la
> liste sert de TODO à vider quand la décision est prise.
