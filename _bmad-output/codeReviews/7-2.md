## Détail des problèmes

### #M1 — Scoping classe inopérant en production (AuthUser vs User)

**Sévérité** : 🔴 Critique — RGPD, invalide les décisions (a) et (b) du kickoff
**Fichier(s)** : `app/Policies/UserPolicy.php:149-170` + `app/Models/AuthUser.php`

**Constat (Opus, manqué par Sonnet)** : En production, `auth()->user()` retourne un `App\Models\AuthUser` (via `LdapUserProvider::retrieveById → AuthUser::findByLogin`). Or `UserPolicy::isProfOnly` guarde `if (!$actor instanceof \App\Models\User) { return false; }` — donc retourne toujours `false` en prod. Même guard dans `sharesClassWithTarget`. Résultat : le flow `view($actor, $target)` tombe dans le dernier `return true`, aucun scoping n'est appliqué. Idem `resetPassword`.

**Bug dans `hasGlobalUserRole`** : `if (!$actor instanceof \Spatie\Permission\Traits\HasRoles ...)` — en PHP, `instanceof <trait>` est toujours `false`. La condition se réduit à `!method_exists($actor, 'hasAnyRole')`. `AuthUser` n'a pas `hasAnyRole` → méthode retourne false, mais `isProfOnly` retourne false aussi, donc le `return true` final gagne systématiquement.

**Pourquoi les tests passent** : ils créent `App\Models\User::create()` et font `$this->actingAs($user)` → `$actor instanceof User` = true → scoping appliqué en test, pas en prod.

**Impact** : les décisions (a) et (b) de la Story 7.2 sont **annulées en production**. Un Prof voit tous les users, reset tous les MDP. RGPD grillé.

**Avis Opus** : 3/3. Bug critique qui invalide le cœur fonctionnel de la story.

**Correction appliquée (Option A retenue)** :
- `AuthUser::getEloquentUser()` existait déjà (pont Spatie), il est désormais utilisé par la Policy.
- `UserPolicy::resolveEloquentActor()` ajouté : résout `AuthUser → User::where('login', …)` ou renvoie `null` (fail-closed si orphelin).
- Appelé en tête de `view()` et `resetPassword()`. Sans Eloquent User correspondant → 403.
- 2 nouveaux tests : `test_policy_resolves_authuser_to_eloquent_and_applies_scoping` et `test_policy_denies_authuser_without_eloquent_counterpart`.

### #2 — `fromBitmask` double-mapping `AppCustomize`+`ComputerInstall` pour bit 0x800

**Sévérité** : 🟠 Important (dégradée de 🔴 après nuance Opus)
**Fichier(s)** : `app/Enums/SambaPermission.php:78`, `app/Services/PermissionService.php:522`

**Constat initial (Sonnet)** : `AppCustomize::bitmask() === ComputerInstall::bitmask() === 0x800`. `fromBitmask(0x800)` retourne les DEUX permissions. Un profil rapatrié AD avec bit 0x800 (ex `RefNum` = 0x90B) reçoit `app.customize` qu'il ne devrait pas avoir.

**Avis Opus** : 2/3. La matrice §11 documente que `AppCustomize => ComputerInstall` est une convention **voulue** pour les profils admin complets (`ComputerAdmin` doit bien recevoir `app.customize` après sync). Le problème est **étroit** : il concerne les **profils custom** avec bit 0x800 **sans le reste du composite `ComputerAdmin`** (ex: `0x900` = `ComputerView + ComputerInstall`) qui reçoivent indûment `app.customize`.

**Correction appliquée** :
- `PermissionService::importCustomProfilesFromAd()` filtre `AppCustomize` hors de `fromBitmask()` si `($bitmask & LegacyRight::computerAdmin()) !== LegacyRight::computerAdmin()`.
- Convention matrice §11 conservée pour les admins complets.
- 2 tests ajoutés dans `SyncFromAdCustomProfilesTest` : profil 0x900 (partiel) → pas de `app.customize` ; profil 0xEF00 (composite complet) → `app.customize` attendue.

### #8 — `BulkResetListingService` non filtré = bypass scoping classe via bulk

**Sévérité** : 🟠 Important (sécurité/defense-in-depth)
**Fichier(s)** : `app/Services/UserService.php:700` (bulkResetPasswords)

**Constat (Sonnet + Opus)** : `UserService::bulkResetPasswords` check uniquement le droit global `user.password.init`, pas `Gate::forUser($actor)->check('resetPassword', $target)` sur chaque user cible. Un Prof déclenchant bulk contourne le scoping classe.

**Avis Opus** : 3/3. Aujourd'hui un Prof n'a pas l'UI bulk, mais c'est du defense-in-depth indispensable — si demain on expose l'action à un Prof (flow légitime), le scoping est absent. Correction 3 lignes.

**Correction appliquée** :
- `UserService::bulkResetPasswords` : ajout d'un bloc de validation après `$outOfScope` qui pour chaque login résout le User Eloquent (via `$sqlUsers[$login]` + re-query défensive) et applique `Gate::forUser($actor)->check('resetPassword', $target)`.
- Rejet avec log `audit.user.password.reset.denied` + motif `out_of_class_scope` si un user est hors périmètre pédagogique.
- Les users sans cache SQL (tests unitaires, sync non-faite) laissent passer (comportement d'avant-correction).
- Test ajouté dans `UserPolicyResetPasswordScopedTest::test_gate_forUser_filters_bulk_targets_by_class_scoping` pour valider le filtre Gate côté Policy (re-vérifie que `Prof` ne voit que ses élèves via le même Gate que le bulk).
