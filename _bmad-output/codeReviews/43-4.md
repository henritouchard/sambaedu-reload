## Détail des problèmes

### #1 — 🟡 Fuite de refcount `GetModuleHandleEx`

**Fichier(s)** : `agent/windows/notice_windows.go` (`noticeModuleHandle`)

**Constat initial (review)** : `GetModuleHandleEx(0, nil, &module)` avec `flags = 0` incrémente le
refcount du module à chaque appel (contrairement à `GetModuleHandleW`), sans `FreeLibrary`
correspondant, et la fonction est appelée à chaque `createNoticeWindow` (donc à chaque
`explorer_restart`). Impact réel quasi nul (module = l'exe lui-même, jamais déchargé), mais viole le
contrat de l'API.

**Solution appliquée** : ajout du flag `GET_MODULE_HANDLE_EX_FLAG_UNCHANGED_REFCOUNT` (`0x00000002`,
const `getModuleHandleExUnchangedRefcount`) → l'appel devient iso-`GetModuleHandleW` (pas de bump).

**Action** : ✅ Corrigé automatiquement.

### #2 — 🟡 Lead-time payé même sans fenêtre affichée

**Fichier(s)** : `agent/shared/companion.go` (branche `RefreshExplorerRestart`)

**Constat initial (review)** : `ShowRestartNotice` ne renvoie aucun signal de succès (`dismiss`
toujours non-nil, y compris en échec — contrat D4). Le compagnon exécute donc `Sleep(leadTime)`
inconditionnellement, même quand la création de la fenêtre a échoué → ~2 s de délai mort avant le
kill du shell, sans fenêtre à lire (léger ralentissement vs 2.10.0 sur ce chemin d'échec rare).

**Solution appliquée** (option 1, tranchée user) : `ShowRestartNotice` remonte désormais
`(shown bool, dismiss func())`. `shown` vaut `true` uniquement quand la fenêtre a réellement été
affichée (`false` sur échec de création OU timeout de création). Le compagnon n'exécute
`time.Sleep(noticeLeadTime())` QUE si `shown == true` — plus de délai mort avant le kill quand il n'y
a rien à lire. Interface `RefreshOps`, impl Windows, fake de test et site d'appel `runRefreshGesture`
mis à jour ; build/vet/tests re-vérifiés verts.

**Action** : ✅ Corrigé.

### #3 — 🟡 `GetMessage == -1` laissait une fenêtre figée résiduelle

**Fichier(s)** : `agent/windows/notice_windows.go` (`pumpNoticeMessages`)

**Constat initial (review)** : sur `GetMessage` retournant `-1` (erreur), la boucle `return`
immédiatement sans détruire la fenêtre : plus de pump, `hwnd` toujours valide → fenêtre top-most
gelée à l'écran jusqu'à la fin du process compagnon ; un `WM_CLOSE` posté par `dismiss` ne serait
jamais dépilé. Cas rare mais très visible sur un parc verrouillé.

**Solution appliquée** : `pumpNoticeMessages(hwnd)` prend désormais le HWND ; sur `ret == -1`, appel
`DestroyWindow(hwnd)` (légal sur le thread créateur) avant de sortir.

**Action** : ✅ Corrigé automatiquement.

### #4 — 🟡 Test AC5 = proxy structurel, nom surpromettait

**Fichier(s)** : `agent/shared/companion_test.go`

**Constat initial (review)** : le test injecte un item `machine`-scope dans un `Companion.RunPass` et
vérifie l'absence de geste/notice — il prouve que le compagnon ignore les items machine-scope, mais
l'AC5 porte sur le `MachineEngine` SYSTEM (session 0), chemin de code distinct non exercé ici. Le nom
`...NeverReachedFromMachineScope` surpromettait. La garantie session 0 reste STRUCTURELLE (le
`MachineEngine` ne reçoit aucune `RefreshOps` — `main_windows.go` sans diff) et est documentée par la
story ; aucune correction de code fonctionnelle requise.

**Solution appliquée** : renommage `TestCompanionRestartNoticeNeverReachedFromMachineScope` →
`TestCompanionIgnoresMachineScopeItems` (le commentaire renvoie déjà à
`TestRegistryHkuNeverTriggersShellRefresh` de 43.1 pour l'argument SYSTEM/HKU).

**Action** : ✅ Corrigé automatiquement (renommage, aucun changement de logique).

### #5 — 🟡 Idempotence RÉELLE (`sync.Once`) non testée

**Fichier(s)** : `agent/shared/companion_test.go` (fake) vs `agent/windows/notice_windows.go`

**Constat initial (review)** : `TestCompanionRestartNoticeDismissIdempotent` teste l'idempotence du
FAKE, pas du `once.Do(n.dismiss)` réel ; le no-op « fenêtre jamais créée » et le chemin timeout ne
sont vérifiés que par lecture. Intrinsèque au périmètre (rendu Win32 non testable hôte, validé en
runbook) ; l'idempotence réelle est structurellement garantie par `sync.Once`.

**Action** : ❌ Non corrigé — limite de couverture assumée par la story (validation e2e = runbook QA
post-publication). Le runbook 43.4 couvre le double-dismiss implicite via le retour du shell.

### #6 — 🟡 Lisibilité / DPI du STATIC

**Fichier(s)** : `agent/windows/notice_windows.go`

**Constat initial (review)** : fenêtre à dimensions en pixels physiques, appli non DPI-aware ; à fort
DPI le texte pouvait déborder verticalement. `SS_CENTER` gère le retour à la ligne horizontal (pas de
clipping latéral).

**Solution appliquée (partielle)** : fenêtre agrandie (480×184) avec zone message dédiée (432×72) +
police plus grosse (`CreateFontW` Segoe UI, message ~14 pt semibold, spinner ~22 pt bold), ce qui
augmente la marge avant troncature. Le DPI-awareness formel reste non traité.

**Action** : ⏳ Atténué. DPI-awareness formel = Question #2 (à trancher selon la réalité du parc).

### #7 — 🟡 `Companion.NoticeLeadTime` public sans borne haute

**Fichier(s)** : `agent/shared/companion.go`

**Constat initial (review)** : champ public injectable justifié (sinon la suite de tests dort 2 s par
restart ; honore D5 « valeur tunable »), mais sans plafond — une valeur aberrante bloquerait la passe
d'autant. Risque faible (config interne, best-effort).

**Solutions possibles** : clamper à un plafond raisonnable (ex. 10 s) dans `noticeLeadTime()`, ou
laisser tel quel.

**Action** : ❌ Non corrigé — nit acceptable (config interne, aucune surface externe). À clamper si un
usage réel le justifie.
