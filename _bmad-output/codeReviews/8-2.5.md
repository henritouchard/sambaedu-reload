## Detail des problemes

### #1 — Test trompeur `extract_tar_gz_cleans_intermediate_tar`

**Severite** : 🟠
**Fichier(s)** : `tests/Unit/Services/FileManagerServiceTest.php`

**Constat initial (review)** :
Le test verifie que le `.tar` intermediaire est nettoye, mais l'implementation utilise `exec('tar xzf')` qui ne cree jamais de `.tar` intermediaire. Le test passe par accident car le helper `createTarGz()` supprime deja le `.tar` via `Phar::unlinkArchive()`.

**Action** : Supprime. Remplace par un commentaire dans l'implementation expliquant le choix.

### #2 — Divergence spec : exec('tar') vs PharData

**Severite** : 🟠
**Fichier(s)** : `app/Services/FileManagerService.php`

**Constat initial (review)** :
La story specifie "via PharData" mais l'implementation utilise `exec('tar xzf')`. Ce choix a des implications :
- Dependance systeme (tar doit etre installe)
- Securite (exec peut etre dans disable_functions)
- Performance (exec est plus fiable sur grosses archives)

**Action** : En attente de decision utilisateur.

### #3 — Path traversal dans processDeletes/processUntars/processUnzips

**Severite** : 🔴
**Fichier(s)** : `app/Services/AppStore/PackageInstallerService.php`

**Constat initial (review)** :
Les chemins proviennent du XML distant et sont concatenes avec `$this->storagePath`. Un depot malveillant pourrait injecter `../../etc/important_file` dans une directive `<delete>`.

**Solutions possibles** :
1. Ajouter une methode `resolveAndValidatePath()` qui verifie que le chemin resolu reste sous `storagePath`
2. Valider les chemins au moment du parsing des directives

**Action** : Corrige — validation ajoutee dans chaque methode process*.
