## Détail des problèmes

### #1 — StateHasher : divergence liste/objet sur clés numériques séquentielles ≥ 11

**Sévérité** : 🟠
**Fichier(s)** : `agent/shared/hasher.go`, `agent/shared/hasher_test.go`

**Constat (review opus)** :
`phpListKeys` était appelé sur les clés **triées** et comparait `sortedKeys[i] == itoa(i)`. Le tri octet place `"10"` avant `"2"` : dès 11 clés `"0".."10"`, la détection de liste échouait → Go émettait un objet là où PHP (json_decode assoc → liste) ré-encode un tableau. Confirmé par exécution croisée contre le StateHasher PHP réel (VM). Viole l'AC3 « à l'identique » ; latent (payloads actuels snake_case plats) mais c'est exactement la classe de bug que la story devait éliminer — un hash divergent = faux drift silencieux quand 24.6 se servira des empreintes.

**Évaluation orchestrateur** :
Pertinence : 3 — bug mécaniquement vérifié dans le code ET reproduit contre le PHP réel. **La contre-vérification a en outre montré que le correctif proposé par opus (test ensembliste) était lui-même incomplet** : la sémantique PHP dépend de l'**ordre d'insertion des clés dans le document** (`array_is_list` est évalué au `json_decode`, avant tout tri). Preuves VM 2026-06-12 :
- `{"0":"a",…,"10":"k"}` (ordre document) → `array_is_list` vrai → **liste**, hash `8854cf4d…` ;
- `{"1":"b","0":"a",…,"10":"k"}` (hors ordre) → `array_is_list` faux → ksort → clés triées `"0","1","10","2",…` → **objet**, hash `c99fe485…`.
Un test ensembliste aurait émis une liste dans les deux cas → nouvelle divergence. Une `map[string]any` Go perd l'ordre du document : le correctif fidèle exige un décodage ordonné.

**Solutions possibles** :
1. Détection ensembliste sur map (proposition opus) — REJETÉE : infidèle au contre-cas hors-ordre.
2. **Décodage ordonné + sémantique PHP en 2 temps** — APPLIQUÉE : type `OrderedMap` (ordre du document préservé) + `DecodeJSONOrdered` (décodage par tokens) ; `appendCanonicalObject` reproduit la chaîne PHP exacte : (1) clés `"0".."n-1"` dans l'ordre du document ⇒ liste jamais triée ; (2) sinon ksort SORT_STRING puis re-test séquence ⇒ liste ; (3) sinon objet trié. `Canonicalize` **refuse** désormais les `map[string]any` (une seule voie d'entrée = aucun hash silencieusement faux). `HashState`/`HashItem` prennent un `*OrderedMap`.

**Action** : corrigé automatiquement (correctif élargi au-delà de la proposition opus). +4 tests croisés (2 hash + 2 formes canoniques, références calculées sur le PHP réel de la VM, sources en hex). `go vet` (linux + windows) ✅, `go test ./...` **77 PASS** (73 → 77) ✅, cross-compile ✅.

### #2 — Grand entier hors int64 : PHP float vs Go verbatim

**Sévérité** : 🟡
**Fichier(s)** : `agent/shared/hasher.go`

**Constat (review opus)** :
`{"n":99999999999999999999999}` → PHP émet `1.0e+23` (json_decode → float), Go ré-émet le littéral verbatim. Hashes divergents. Cas hors-contrat : §4.1 interdit explicitement les floats, et un entier de 23 chiffres tombe dans le cas proscrit « sérialisation dépendante de la plateforme ».

**Évaluation orchestrateur** :
Pertinence : 1 — divergence factuelle réelle mais des deux côtés hors-contrat ; aucune garde ne serait elle-même iso-PHP (il faudrait simuler la perte de précision float de PHP, absurde). La discipline est côté providers serveur.

**Solutions possibles** :
1. Garde côté agent (refus des entiers > 2^63-1) — rejetée : comportement non iso-PHP, faux positifs possibles.
2. Documentation du cas comme hors-contrat — APPLIQUÉE (commentaire `NB review 24.5 #2` dans `appendCanonical`).

**Action** : corrigé automatiquement (documentation seule).
