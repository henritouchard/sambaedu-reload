## Détail des problèmes

### #1 — 3 fixtures Windows logon identiques : couverture « par script » illusoire

**Sévérité** : 🔴 Critique
**Fichier(s)** : `tests/Feature/Gpo/ApplicationsScriptsCriticalParityTest.php`, `tests/Concerns/AssertsScriptParity.php`, `tests/Fixtures/Gpo/applications/windows_logon_{wallpaper,shortcuts,firefox}/expected.cmd`, `app/Gpo/Services/ApplicationScriptsAssembler.php::assemble()`

**Constat initial (review)** :
`assemble($info, $scripts)` ne sait pas isoler un script : pour `action=logon/os=windows` il concatène **tous** les fragments applicables (`associations`, `chrome`, `firefox`, `shortcuts`, `wallpaper`, …) dans `$out['cmd']`. Les 3 scénarios ont un `$info` strictement identique sauf `id` (md5), et `assertScriptParity()` normalise justement l'`id`. Preuve (normalisation exacte du trait appliquée aux 3 fixtures) :
```
wallpaper / shortcuts / firefox (normalisés) → md5 23eac4c12ebe3b7c79742a076c61ae90 (IDENTIQUES)
```
Les 3 tests « par script critique » exécutent donc **3 fois la même assertion**. AC1.2 (« parité bytes par script critique ») n'est pas satisfait au sens rédigé. On prouve uniquement « le blob logon/windows global est iso-legacy », pas la parité isolée de wallpaper/shortcuts/firefox.

**Solutions possibles** :
1. **Option A (reco)** : assumer la parité globale par contexte + remplacer les 3 tests redondants par des assertions ciblées par fragment (marqueurs distinctifs).
2. **Option B** : filtrer `$scripts` par app avant `assemble()` + recapturer fixtures isolées (surcoût, diverge du runtime réel).

**Action** : en attente décision Henri (Q1).

### #5 — Tests endpoint AC2.1 = quasi no-op (body vide non détecté)

**Sévérité** : 🟠 Important
**Fichier(s)** : `ApplicationsScriptsApiV1Test::it_returns_200_with_cp1252_*` / `it_returns_200_with_utf8_*`

**Constat initial (review)** : le controller `apiV1` renvoie toujours `resolveContentType($os)` y compris sur le chemin dégénéré `emptyOk()` (200 + body vide) quand `resolveInfo() === []`. En test sans poste AD réel, `resolveInfo` retourne probablement `[]` → 200 body vide. Les tests `assertContains(status, [200])` + `assertStringContainsString('cp1252', contentType)` passent **sans déclencher l'assemblage**. AC2.1 (« body PAS vide pour un poste résolu ») n'est pas testé. Ces tests passeraient même si l'Assembler était cassé.

**Solutions possibles** :
1. Seeder un contexte résolvable (seed `Workstation` + relations / mock `resolveInfo`) → forcer body non vide + asserter marqueur (`REM cmd` / `#!/bin/bash`).
2. Requalifier en « smoke route+auth+charset » et déplacer la garantie d'assemblage vers les tests de parité.

**Action** : en attente décision Henri (Q5).

### #7 — Normalisation `id` trop large

**Sévérité** : 🟡 Mineur
**Fichier(s)** : `tests/Concerns/AssertsScriptParity.php` (regex `/\bid=([a-f0-9]{32})\b/i`)

**Constat initial (review)** : `\bid=<32hex>\b` remplace toute occurrence `id=<32hex>`, pas seulement l'ID de session. Les fragments firefox (hash hardcodé) / once (`md5_file`) pourraient contenir des hex 32 capturés à tort → masque une divergence réelle. Risque faible (préfixe `id=` spécifique) mais permissif (`i` + `\b`).

**Solutions possibles** :
1. Restreindre au contexte connu (footer curl `-F "id=…"`, header `SET id=`). Documenter l'innocuité par audit des occurrences `id=` dans les 5 scripts.

**Action** : en attente (dépend P1/P6).
