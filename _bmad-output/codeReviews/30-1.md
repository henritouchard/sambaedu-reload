## Détail des problèmes

### P1 — PHPDoc de `InvalidUpstreamContractException` non mis à jour

**Sévérité** : 🟡

**Constat initial (review sonnet)** :
Le docblock énumère 3 causes de rejet (enum hors domaine, incohérence de cible, champ manquant) mais pas la nouvelle cause d'intégrité référentielle `imposed_groups.label_name` orphelin ajoutée par 30.1.

**Avis Opus** : pertinence 2/3. Gap de doc réel, correctif trivial. À corriger conjointement avec A1 (même oubli sur le docblock de classe du service).

**Action** : ✅ Corrigé — puce « intégrité référentielle `imposed_groups.label_name` (FR9, Story 30.1) » ajoutée au docblock.

### A1 — Docblock de classe du service muet sur le garde-fou (manqué par sonnet)

**Action** : ✅ Corrigé — puce « Intégrité référentielle `imposed_groups.label_name → label déclaré` » ajoutée au sommaire de validations.

### P3 — Compteur `imposedGroups['deleted']` jamais testé > 0

**Sévérité** : 🟡
**Fichier(s)** : `tests/Feature/ControlHub/UpstreamLabelsImposedGroupsReceptionTest.php`

**Constat initial (review sonnet)** :
AC#3 demande que les compteurs `created/updated/deleted` reflètent le delta. Pour les groupes imposés, `deleted` était asserté `=0` partout, jamais `>0` (alors que la symétrie était couverte pour les labels via `labels['deleted']===1`).

**Avis Opus** : pertinence 2/3. Gap de couverture réel vs AC#3 ; sévérité atténuée car `reconcileChildren()` est générique et le chemin prune+compteur est déjà prouvé sur labels/items/catalogApps. Complétude, pas couverture d'un chemin non prouvé.

**Action** : ✅ Corrigé — ajout d'un groupe imposé `parc-anciens` (label déclaré `salle-info`) dans la 1re ingestion, pruné à la 2e → assertion `imposedGroups['deleted'] === 1`. Test vert.

### P2 — `?? null` redondant sur `label_name`

**Sévérité** : 🟡
**Fichier(s)** : `app/Services/ControlHub/ControlHubContractIngestionService.php`

**Constat initial (review sonnet)** :
`$labelName = $group['attrs']['label_name'] ?? null;` — `normalizeImposedGroups()` produit toujours la clé `label_name`, donc `?? null` est redondant et « contractuellement trompeur ».

**Avis Opus** : pertinence 1/3. Strictement inoffensif (clé absente ou null → même `null`) ; « contractuellement trompeur » exagéré. Seul vrai argument = cohérence interne : `$group['key']['name']` deux lignes plus bas est lu sans `??` (style établi pour les structures normalisées internes ; les `?? null` du service portent sur le payload externe non fiable, contexte différent).

**Action** : ✅ Corrigé — `?? null` retiré pour aligner sur l'accès direct des structures normalisées internes.

### A2 — Asymétrie `items[].target_label` vs `imposed_groups.label_name` (info)

**Sévérité** : 🟢 info
**Constat (Opus)** : un item `target_type=label` avec `target_label` introuvable est accepté (aucun cross-check) alors qu'un `imposed_groups.label_name` orphelin est rejeté. Conforme au cadrage : l'intégrité `items[].target_label` est explicitement déférée à 30.4.

**Action** : ❌ Non corrigé volontairement — frontière de scope assumée, pas une incohérence.

### A3 — Pas de test « sibling valide + orphelin dans le même payload » (info)

**Sévérité** : 🟢 info
**Constat (Opus)** : aucun test n'envoie un groupe valide ET un orphelin dans le même payload pour prouver que le sibling valide n'est pas écrit non plus. Couvert indirectement : le garde-fou lève avant `DB::transaction`, et le test orphelin asserte déjà les 3 tables à 0.

**Action** : ❌ Non corrigé volontairement — valeur faible, couverture déjà indirecte.
