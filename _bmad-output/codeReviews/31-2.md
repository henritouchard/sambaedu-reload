## Détail des problèmes

### #1 — Aucun test pour un ordre `permissive` (D1 non verrouillée)

**Sévérité** : 🟠 — **Pertinence Opus : 2/3**
**Fichier(s)** : `tests/Feature/ControlHub/UpstreamInstallOrderTest.php`

**Constat initial (review sonnet)** :
Les helpers `orderInstance()`/`orderLabel()` forcent tous `enforcement_state: Locked`. D1 pose que `locked` ET `permissive` signifient « app présente » (aggregate, aucune distinction d'enforcement). Le code indexe bien les deux (`whereIn` inclut `permissive`, et la branche `applications` n'inspecte pas `enforcement_state`), mais aucun test ne le verrouille → un futur filtre `enforcement_state` perdrait silencieusement `permissive`.

**Avis Opus** : Vrai et pertinent (2/3). La branche d'indexation `applications` n'inspecte pas `enforcement_state` (correct vis-à-vis de D1), mais c'est une décision explicite non testée. Risque de régression réaliste. Correction triviale et non ambiguë.

**Action** : ✅ Corrigé — ajout d'un cas `permissive`/instance asserant la présence projetée.

### #2 — `maille`/`sourceId` des candidats upstream non vérifiés (AC1)

**Sévérité** : 🟠 — **Pertinence Opus : 1/3**
**Fichier(s)** : `tests/Feature/ControlHub/UpstreamInstallOrderTest.php`

**Constat initial (review sonnet)** : `maille==Broadcast` (D4) et `sourceId==Application.id` (déterminisme `selectAggregate`) seulement couverts pour le chemin LOCAL, pas upstream.

**Avis Opus** : Faible (1/3). L'hydratation est **mono-chemin** : qu'un `app_id` vienne du resolver, du défaut-parc ou de l'amont, il passe par le même `concat → unique → whereIn('app_id') → boucle candidats`. Il est **structurellement impossible** qu'un app_id d'origine amont obtienne une `maille`/`sourceId` différents — c'est le sens même de D3 (pont au niveau ensemble). Aucune branche divergente n'existe.

**Action** : ❌ Non corrigé — couvert par construction (décision concordante 2 avis).

### #3 — Claim PHPDoc NFR3 « trompeur » pour le flux décorateur production

**Sévérité** : 🟠 — **Pertinence Opus : 1/3**
**Fichier(s)** : `app/Services/ControlHub/Resolution/UpstreamContractSource.php` (PHPDoc), `tests/Feature/ControlHub/UpstreamInstallOrderTest.php` (AC4)

**Constat initial (review sonnet)** : En production `UpstreamAwareProvider::itemsFor()` appelle `candidatesFor('applications',Machine,ctx)` qui, si le contrat a des items `registry/label`, déclenche `labelsCarriedBy()` → requête `controlhub_label` émise par le décorateur → preuve NFR3 incomplète + PHPDoc trompeur.

**Avis Opus** : Le cœur de l'argument est **erroné** (1/3). La requête `controlhub_label` n'apparaît QUE quand un contrat actif porte une cible label — coût légitime du ciblage 30.4 préexistant, jamais le « standalone byte-identique » que NFR3 protège. De plus `labelsCarriedBy` est **mémoïsé par poste** → l'accesseur 31.2 et le décorateur partagent la même unique requête → **31.2 ajoute zéro requête**. NFR3 n'est jamais violé. Le PHPDoc parle de l'accesseur, qui court-circuite réellement. **Seul kernel valide** = renvoie à l'angle manqué A (aucun test du décorateur réel).

**Action** : 🟡 Nuance PHPDoc (optionnelle) — préciser que le court-circuit est garanti « pour cet accesseur seul ; en production le décorateur peut invoquer `labelsCarriedBy()` pour d'autres types, résultat mémoïsé par poste, sans requête supplémentaire ». Aucune correction de code/test (le fond est couvert par l'angle A).

## Autres angles manqués (notés, sans action — 2e avis Opus)

- **B — Dédup AC3 faite par le PROVIDER, pas le compilateur.** Dans le cas mono-provider, `->unique()` collapse `firefox` au niveau `app_id` avant hydratation. La « dédup aggregate du `StateCompiler` » invoquée par AC3/D3 n'est pas le mécanisme qui agit ici (il n'agirait que via le flux adaptateur rejeté). Le test passe (count==1), mais ne pas sur-attribuer la robustesse au compilateur. Conceptuel, non bloquant.
- **C — Fuite d'`app_id` vide hors du provider.** Si `$item->key` est null/'' pour un item `applications`, l'accesseur retourne `['']` (l'accesseur ne filtre pas les vides — seul le provider filtre). Un futur consommateur direct (31.3 lit ces app_id pour approvisionner) hériterait d'un `''`. Robustesse mineure ; un `array_filter` du vide dans l'accesseur serait plus défensif. **À garder pour 31.3.** Non bloquant ici.
- **D — `array_unique` (case-sensitive) vs `strcasecmp` (case-insensitive)** dans l'accesseur : `Firefox`/`firefox` survivraient à `array_unique`. Comportement iso 27.5 (même asymétrie côté provider) → pas une régression 31.2, casse variable d'`app_id` = incohérence improbable. Aucune action.
