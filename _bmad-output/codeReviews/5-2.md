   → **Quelle option Henri ?**

   - Option B : refuser et logger un warning, demander à l'admin de nettoyer manuellement.
   - Option C : décalque legacy (laisse comme tel, bug accepté).
   → **Préférence Henri ?**

3. **Comportement `shares:resync-class` quand toutes les classes sont verrouillées** (cf. #2) :
   La commande retourne `SUCCESS` actuellement quand `locked=N, resynced=0, failed=0`. Pour un cron monitoring, c'est trompeur (rien fait mais SUCCESS).
   - Option A : retourner FAILURE si `resynced === 0 && (failed + locked) === count`.
   - Option B : code retour distinct (`2`) pour "skipped due to locks".
   - Option C : laisser SUCCESS (rien à faire = succès).
   → **Préférence Henri ?**

## Détail des problèmes

### #1 — Observer D5=A incapable d'implémenter l'archivage D3=A

**Sévérité** : 🔴 Critique
**Fichier(s)** : `app/Observers/UserGroupUserPivotObserver.php:81-93`, `app/Services/Filesystem/ShareService.php:408-451`, `app/Services/UserService.php:1414` (`syncEloquentGroupsForUser`)

**Constat initial (Sonnet)** :
L'Observer reçoit des events atomiques — un seul pivot `(user, group)` à la fois. Lors d'un changement de classe Alice 6A → 5B, Laravel déclenche deux events séparés :
1. `created(alice, 5B)` → `syncUserClassMemberships(alice, oldClassIds=[], newClassIds=[5B.id])`
2. `deleted(alice, 6A)` → `syncUserClassMemberships(alice, oldClassIds=[6A.id], newClassIds=[])`

L'archivage D3=A (`Classe_6A/alice/ → Classe_5B/alice/Archives/`) ne se déclenche que si `$added` ET `$removed` sont tous deux non vides dans le même appel. Avec l'Observer atomique : impossible. Tests verts car `ShareServiceTest` appelle `syncUserClassMemberships` directement avec les 2 listes — ne teste pas le chemin réel via Observer.

**Avis Opus (3/3)** :
Sonnet a raison ET c'est PIRE qu'il le décrit. J'ai vérifié `app/Services/UserService.php:1414` — c'est le SEUL site dans tout le code Laravel qui mute la pivot `user_group_user`, et il utilise `syncWithoutDetaching`. Par construction, cette méthode N'APPELLE JAMAIS `detach()` — donc l'événement `deleted` du pivot **ne fire JAMAIS** lors d'un changement de classe en prod (Story 2.2). Le test `it_triggers_sync_on_detach_classe_pivot` passe uniquement parce qu'il appelle `$user->groups()->detach($classe->id)` directement, ce qui n'a aucun équivalent dans le code applicatif.

Conséquences réelles :
- L'archivage D3=A ne se déclenche **jamais** via UI Story 2.2.
- L'unique branche `removeAcl(user:alice)` (ligne 471-472) ne se déclenche jamais non plus → fuite d'ACL `user:alice:rwx` sur l'ancienne classe.
- Le filet `shares:resync-class` ne récupère pas non plus (il appelle `createClassShare`, pas `syncUserClassMemberships`).

**Solutions possibles** :
1. **Option B (recommandée Opus)** : modifier `UserService::syncEloquentGroupsForUser()` pour calculer `$oldClassIds = $sqlUser->groups()->where('type','classe')->pluck('id')->all()` AVANT le sync, calculer `$newClassIds` après, puis appeler `ShareService::syncUserClassMemberships()`. Remplacer `syncWithoutDetaching` par `sync()` (ou un sync ciblé classes-only) pour faire émettre les vrais events `deleted`. L'Observer reste en filet pour attach/detach manuels.
2. **Option D pure** : accepter que l'archivage se fait uniquement via Artisan (manuel/cron). Reformuler AC 4. Étendre `shares:resync-class` pour gérer `syncUserClassMemberships` en plus de `createClassShare`.

**Action** : ⏳ En attente — Question Henri Q1.

### #2 — Race condition lock commande/service + SUCCESS factice

**Sévérité** : 🟠 Important
**Fichier(s)** : `app/Console/Commands/SharesResyncClassCommand.php:133-151, 191`

**Constat initial (Sonnet)** :
```php
$lock = Cache::lock($lockKey, 60);
if (!$lock->get()) { /* skip */ continue; }
try {
    $lock->release();  // ← Lock relâché
    $ok = $this->shareService->createClassShare($group, ...);  // ← createClassShare re-prend le lock
```
Fenêtre de race entre `release()` et `createClassShare`. Si Observer pivot s'exécute simultanément, il acquiert le lock → `createClassShare` trouve lock occupé → return false → comptage failed factice.
Condition retour `Command::FAILURE = $resynced===0 && $failed>0`. Si toutes verrouillées (`locked=N, failed=0, resynced=0`) → SUCCESS trompeur cron.

**Avis Opus (2/3)** :
Race lock = risque microseconde, faible mais réel. Plus inquiétant : SUCCESS factice si toutes verrouillées (cron qui ne fait rien remonte SUCCESS).

**Solutions possibles** :
1. Supprimer le double-lock dans la commande, ne garder que celui dans `ShareService::createClassShare` (idempotent + thread-safe via lock interne).
2. Modifier condition FAILURE en `($resynced === 0 && ($failed + $locked) === $classes->count())` pour distinguer "rien fait" de "tout réussi".
3. Bonus : code retour distinct (`2`) si `$locked > 0` pour monitoring.

**Action** : ⏳ En attente — Question Henri Q3.

### #3 — `setfacl -R` sans `-P` : régression sécurité vs legacy (symlink traversal)

**Sévérité** : 🟠 Important
**Fichier(s)** : `app/Services/Filesystem/AclService.php:148, 167, 199, 229`

**Constat initial (Sonnet)** :
Legacy `partages.inc.php` lignes 372, 492, 498, 506 utilise systématiquement `setfacl -R -P --set ...`. L'option `-P` = "physical, do not follow symbolic links". Sans elle, `setfacl -R` suit les symlinks → un attaquant qui plante un `ln -s /etc /var/sambaedu/Classes/Classe_6A/alice/evil` peut faire poser des ACLs sur `/etc/*` lors d'un resync.

Le code 5.2 omet `-P` dans **tous** ses appels `setfacl -R` (`setAcls`, `addAcl`, `removeAcl`).

**Avis Opus (3/3)** :
Vérifié — régression sécurité réelle vs legacy. Exploitabilité concrète :
- Un élève (qui a `rwx` sur son `Classe_6A/alice/`) plante `ln -s /etc /var/sambaedu/Classes/Classe_6A/alice/evil`.
- Lors d'un `shares:resync-class --classe=6A`, `setfacl -R` (sans `-P`) suit le symlink → applique des ACLs sur `/etc/`.
- Sudoers permet `setfacl` en root sans password → l'attaque marche au premier coup.

C'est un trou de sécurité du même ordre que les vulnérabilités path traversal classiques. AC 12 mentionne "AUCUN appel `sudo setfacl` n'est exécuté" pour les paths malveillants, mais une fois le path validé, l'exécution récursive ouvre une nouvelle surface.

**Solutions possibles** :
1. Ajouter `-P` dans `AclService::setAcls`, `addAcl`, `removeAcl` quand `$recurse=true`. Concrètement : `$option = $recurse ? '-R -P' : '';`.
2. Test anti-régression vérifiant la présence de `-P` dans la commande générée.

**Action** : ⏳ En attente — correction triviale, à appliquer en étape 8.

### #7 — `chownAndChgrp()` échec silencieux sans log

**Solutions possibles** :
```php
private function chownAndChgrp(string $path): bool
{
    if (! $this->aclService->validatePath($path)) return false;
    $escaped = escapeshellarg($path);
    $r1 = Process::run(sprintf('sudo chown www-admin %s', $escaped));
    $r2 = Process::run(sprintf("sudo chgrp 'domain admins' %s", $escaped));
    if (! $r1->successful()) Log::warning('ShareService: chown échec', ['path' => $path, 'err' => $r1->errorOutput()]);
    if (! $r2->successful()) Log::warning('ShareService: chgrp échec', ['path' => $path, 'err' => $r2->errorOutput()]);

}
```

**Constat (Opus)** :

Donc une classe `name='Seconde B'` semble supportée mais échoue en pratique. Test `it_lowercases_and_escapes_spaces_in_acl_class_name` ligne 144 testé en isolation — ne passe pas en intégration.

**Solutions possibles** :
1. Décider : (A) supporter les espaces partout (relâcher `validatePath` regex pour autoriser espaces, escapeshellarg gère), ou (B) refuser dans `escapeAclClassName` pour cohérence et documenter "classes avec espaces non supportées en 5.2".

**Action** : ⏳ En attente — clarification architecturale (recommandation B = simple, A = legacy-faithful).
