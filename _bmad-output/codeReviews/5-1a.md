### #2 — Chemin `dirname(__DIR__, 3)` décalé d'un niveau après rename

**Sévérité** : 🟠 Important
**Fichier(s)** : `app/Services/Filesystem/XfsQuotaService.php:43`

**Constat initial (review)** :
L'ancien `QuotaService.php` était dans `app/Services/`, donc `dirname(__DIR__, 3)` pointait sur `codebase/` (parent du projet). Le nouveau fichier est dans `app/Services/Filesystem/`, donc `dirname(__DIR__, 3)` pointe sur `e5-files/` (racine du projet). Le `file_exists()` retourne false dans les deux cas (le fichier cible n'existe ni à la racine projet ni dans le parent), donc c'est un no-op fonctionnel aujourd'hui. Mais si un jour un `includes/config.inc.php` est posé à l'un des deux niveaux, le comportement change silencieusement. Incohérent avec la promesse "iso-comportement" de la story.

**Solutions possibles** :
1. Changer en `dirname(__DIR__, 4)` pour préserver le chemin ancien (→ parent du projet).
2. Documenter dans les Dev Notes de la story que le chemin a changé et pourquoi c'est sans impact aujourd'hui.
3. Utiliser un chemin explicite via `base_path('../includes/config.inc.php')` ou via configuration.

**Action** : ✅ Corrigé automatiquement — `base_path('../includes/config.inc.php')` dans `XfsQuotaService::loadLegacyConfig`. Règle générale mémorisée pour futurs refactors (privilégier `base_path()` aux `dirname(__DIR__, N)` partout dans le code SER).

### #3 — Absence de tests unitaires dédiés HomeDir/XfsQuota

**Sévérité** : 🟠 Important
**Fichier(s)** : `tests/Unit/Services/Filesystem/*` (inexistant)

**Constat initial (review)** :
Les 5 méthodes home et les ~25 méthodes de `XfsQuotaService` n'ont aucun test unitaire dédié. Seuls `UserServiceCreateTest` (tests indirects sur createHomeDirectory + test regex statique), `WallpaperResolverTest`, `WallpaperComposerTest` (mocks de 2-3 méthodes) touchent indirectement ces services. Les méthodes `archiveHomeDirectory/restoreHomeDirectory/deleteHomeDirectoryPermanently/hasArchivedHome` n'ont aucun test de validation de login maintenant qu'elles sont publiques.

**Solutions possibles** :
1. Créer `tests/Unit/Services/Filesystem/HomeDirServiceTest.php` avec 4 tests de validation de login (regex invalide → Log::error appelé) sur les méthodes publiques.
2. Reporter en 5.1d avec un ticket de dette technique explicite.
3. Acter que la couverture indirecte suffit pour un refactor pur.

**Action** : ✅ Corrigé automatiquement — créé `tests/Unit/Services/Filesystem/HomeDirServiceTest.php` avec 41 tests (8 logins malveillants × 5 méthodes + 1 test dossier trash absent). Couvre la garde anti-injection regex sur `createHomeDirectory`, `archiveHomeDirectory`, `restoreHomeDirectory`, `deleteHomeDirectoryPermanently`, `hasArchivedHome`. Scope volontairement limité à la validation ; les flux filesystem (mkdir/mv/rm sudo) restent couverts indirectement. Tests `XfsQuotaService` dédiés reportés (dette tracée).

### #6 — Retrait cache 5 min → risque flood shellout wallpaper

**Sévérité** : 🟠 Important
**Fichier(s)** : `app/Services/Wallpaper/WallpaperComposer.php:420-424, 589-601, 606-619`

**Constat initial (review)** :
`WallpaperComposer` appelle `getDiskUsage` 2-4 fois par résolution. Sur une classe de 30 élèves simultanés → 60-120 shellouts concurrents `sudo quota -u`. Avant, cache 5 min = 1 shellout toutes les 5 min/user. La story 5.1b remettra un snapshot BDD, mais entre 5.1a et 5.1b il y a un risque de charge soudaine au login groupé.

**Solutions possibles** :
1. Accélérer la livraison 5.1b.
2. Ajouter une mémoisation intra-requête dans `XfsQuotaService::getDiskUsage` (2 lignes : `if (isset($this->memo[$user])) return $this->memo[$user];`) comme mesure intermédiaire. Aucun impact fonctionnel, juste évite la redondance dans UNE même requête HTTP.
3. Accepter le risque (faible fenêtre de déploiement).

**Action** : ❌ Non applicable — décision Henri : Epic 5 ne sera pas déployée en prod avant la fin de 5.1b (snapshot BDD). Le cache 5 min retiré en 5.1a sera remplacé par la lecture BDD avant qu'un utilisateur ne voie le code. Pas de mesure intermédiaire requise.
