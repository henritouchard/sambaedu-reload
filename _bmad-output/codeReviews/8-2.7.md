## Questions en attente

> Questions nécessitant une décision de l'utilisateur avant de marquer la story `done`.

1. **M3 — métadonnées de version figées sur ré-installation d'une app existante** (constat précisé après analyse) : `AppStoreService::installApplication()` fait `Application::firstOrCreate(['app_id' => …], [version, xml_url, xml_sha, category, …])`. Si l'app **existe déjà**, `firstOrCreate` retourne la row **inchangée** et **ignore** le bloc d'attributs. Or le téléchargement, lui, utilise `$depotApp->xml_url`/`$depotApp->xml_sha` (valeurs **fraîches**) → les fichiers et le `Application.xml` (recipe) SONT rafraîchis, le catalogue `packages.xml` servi au poste est donc bien le **nouveau**. **Ce ne sont QUE les colonnes métadonnées** (`version`, `installed_version`, `xml_url`, `xml_sha`, `category`…) qui restent **gelées** à la 1re install — `finalizeInstallation()` écrit `installed_version = $application->version` (la valeur **stale**). Conséquence : le n° de version **affiché/enregistré par SE5 ment** (lag), et toute future détection de MAJ comparant `depot.version` vs `installed_version` re-signalerait « MAJ dispo » à perpétuité. **PRÉ-EXISTANT et actuellement INERTE** : `ApplicationStatus::UpdateAvailable` n'est écrit **nulle part** dans `app/` (uniquement lu) → l'affordance « Mise à jour » (`@if($app->is_installed && $app->has_update)`) ne se déclenche jamais aujourd'hui ; le chemin « mettre à jour une app installée » n'est pas câblé de bout en bout. 8.2.7 ne l'active pas. → **Recommandation : story de suivi** (fix = `updateOrCreate` + `installed_version = $depotApp->version`). Hors-scope du périmètre « async » de 8.2.7.

2. **#5 / M1-config (mineur)** : faut-il (a) ajouter un index composite `installation_logs(status, initiated_by)` et (b) aligner le défaut `config/cache.php` (`apc`) + `.env.example` sur un store partagé pour éviter le footgun documenté en M1 ? Recommandation : story de suivi, non bloquant (prod déjà en `file`, volumétrie faible).

## Détail des problèmes corrigés automatiquement

### #2 + M2 — `failed()` : code mort + rattrapage du mauvais log (fusionnés)

**Sévérité** : 🟠 (#2 pertinence 3, M2 manqué par sonnet)
**Fichier** : `app/Jobs/InstallApplicationJob.php`

**Constat** :
- #2 : le log était cherché via `->inProgress()` (scope = `whereNotIn(status, [Success, Failed])`), donc le résultat est par construction non-terminal → la condition `if ($log === null || $log->isTerminal())` ne pouvait jamais être vraie sur sa 2e branche → code mort, et le docblock affirmait un garde-fou inexistant.
- M2 : `->latest('id')->first()` ne rattrapait que le log le plus récent. Or `installApplication()` crée un `InstallationLog` **par tentative** (L114, inconditionnel) sans corrélation 1:1 Job↔log. Si plusieurs logs non-terminaux coexistent pour la même app (worker tué mid-job, double dispatch), les antérieurs restaient « in progress » à perpétuité → affichés sans fin par le panneau de polling 3s (pattern « fantôme de conformité »).

**Solution appliquée** : `failed()` récupère désormais **tous** les logs non-terminaux de l'app (`->inProgress()->get()`) et les passe `Failed` (+ app `Error`). `inProgress()` exclut déjà les états terminaux → idempotent par construction (ne réécrit jamais un `Success`/`Failed`). Le code mort `isTerminal()` disparaît ; docblock corrigé.

### #6 — Test ne vérifiait pas la key WithoutOverlapping

**Sévérité** : 🟡 (pertinence 2)
**Fichier** : `tests/Feature/Jobs/InstallApplicationJobTest.php`

**Constat** : `it_declares_without_overlapping_middleware_keyed_on_app` n'asseyait que `assertInstanceOf(WithoutOverlapping)` — le nom « keyed_on_app » mentait, la key (`appstore.install.<app_id>`) n'était jamais inspectée. Un retour accidentel à une key par `depotApplicationId` passerait inaperçu.

**Solution appliquée** : assertion ajoutée sur `$middlewares[0]->key === 'appstore.install.job-test-app'`.

### M1 — Note documentaire (lock cross-worker)

**Sévérité** : 🟡 (manqué par sonnet, ré-évalué après vérification empirique)
**Fichier** : `app/Services/AppStore/AppStoreService.php`

**Constat** : la prémisse Opus (`CACHE_DRIVER=apc` → cache par-processus → lock inopérant entre les 2 workers) est **fausse en prod** : la VM tourne `CACHE_DRIVER=file`, dont les locks sont partagés sur le filesystem entre processus → AC8 tient réellement. Seul le **défaut** `apc` de `config/cache.php` + `.env.example` constituerait un footgun (déploiement futur en apc/cli → lock per-process).

**Solution appliquée** : note ajoutée au commentaire du `Cache::lock` précisant que la sérialisation cross-worker exige un store **partagé** (`file`/`database`/`redis`) — prod = `file` (OK) — et que l'atomicité `.tmp`+rename reste le garde-fou de fond quel que soit le store.

## Problèmes laissés en l'état (justifiés)

- **#1** — Ne PAS déplacer le lock dans le Job : `updateLocalPackagesXml()` est aussi appelé par `uninstallApplication()`. Le double-log au retry est une propriété pré-existante du design « 1 log/appel », cosmétique (pas de corruption). La refonte M2 limite désormais la prolifération de logs *non-terminaux*.

- **M4** — `wire:loading.attr=disabled` (UI) + `WithoutOverlapping` (store `file` opérant) couvrent le double-clic ; `ShouldBeUnique` serait redondant.
