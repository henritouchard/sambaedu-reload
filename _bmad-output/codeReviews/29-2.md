## Détail des problèmes

### #1a — Message de refus trompeur sur `parc-defaults`

**Sévérité** : 🟠 — **Pertinence Opus** : 2
**Fichier(s)** : `resources/views/pages/admin/settings/parc-defaults/_partials/registry-tab.blade.php` (`authorizeUpstream`)

**Constat initial (review sonnet)** : sur la surface `parc-defaults`, le gate refuse pour deux raisons (verrou amont OU `app.customize` manquant) mais affiche toujours « verrouillé par un contrat amont », message faux si la cause réelle est la permission.

**Avis Opus** : confirmé (note 2). Sur `capabilities-tab` le problème n'existe pas (`guardCustomize` garantit déjà `app.customize`). Corrigeable automatiquement (polish de message, ne touche pas le design).

**Action** : ✅ **Corrigé automatiquement.** `authorizeUpstream` conditionne désormais le toast à `UpstreamLockResolver::isCapabilityLocked()` : « verrouillé par un contrat amont » si réellement verrouillé, sinon « Vous n'avez pas le droit de modifier cette capacité. »

### #1b — Couplage `app.customize` sur une surface `server.admin`

**Sévérité** : 🟠 — **Pertinence Opus** : 2
**Fichier(s)** : `app/Policies/CapabilityPolicy.php` (plancher `app.customize`) ; `registry-tab.blade.php` (surface `server.admin`)

**Constat initial (review sonnet)** : un `server.admin` sans `app.customize` perdrait l'édition du défaut même en standalone (changement de comportement vs pré-29.2).

**Avis Opus** : note 2, mais **neutralisé** : `SambaRole::SuperAdmin` synchronise tous les droits concrets (`app.customize` inclus), aucun rôle `server.admin`-only réel n'existe aujourd'hui. Choix de design explicitement documenté par le dev (story L.255) et acceptable sous « zéro prod ».

**Solutions possibles** :
1. Statu quo (accepté/documenté) — **recommandé**.
2. Gate distinct `modify-capability-default` à plancher `server.admin` pour découpler les deux surfaces.

**Action** : ✅ **Statu quo accepté par Henri (2026-06-27)** — plancher `app.customize` unique conservé, neutralisé par les rôles réels. Pas de gate dédié.

### #2 — Tests de refus ne prouvent pas le message explicite

**Sévérité** : 🟠 — **Pertinence Opus** : 2
**Fichier(s)** : `tests/Feature/Livewire/Parc/CapabilitiesTabUpstreamLockTest.php` ; `tests/Feature/Livewire/Admin/ParcDefaultsUpstreamLockTest.php`

**Constat initial (review sonnet)** : les tests vérifient l'absence d'écriture mais pas le toast. AC#1/#2 exigent « un message explicite, pas un échec silencieux » — non prouvé.

**Avis Opus** : confirmé (note 2), corrigeable auto. Le toast EST émis (`toastError` → dispatch `toastMagic` status `error`).

**Action** : ✅ **Corrigé automatiquement.** Ajout de `assertDispatched('toastMagic', fn($e,$p) => $p['status'] === 'error')` aux 4 tests de refus (saveOverride, removeOverride, saveDefault, toggleLock).

### #3 — Cas multi-clés non couvert

**Sévérité** : 🟡 — **Pertinence Opus** : 2
**Fichier(s)** : `tests/Unit/Services/ControlHub/UpstreamLockResolverTest.php`

**Constat initial (review sonnet)** : sémantique « au moins une clé » de `isCapabilityLocked` non prouvée pour une capacité à plusieurs clés.

**Avis Opus** : confirmé (note 2). À l'implémentation, découverte d'une contrainte d'unicité `(capability_id, os, mechanism)` → une capacité n'a qu'**une** projection registry ; le cas multi-clés se modélise donc par **plusieurs `spec.keys[]` dans une projection unique** (test ajusté en conséquence).

**Action** : ✅ **Corrigé automatiquement.** Test `capability_with_multiple_keys_is_locked_when_any_one_key_matches` : projection à 2 clés, seule la 2ᵉ verrouillée → capacité verrouillée.

### #4 — Footgun du helper de test `lockItem()`

**Sévérité** : 🟡 — **Pertinence Opus** : 1
**Fichier(s)** : `tests/Unit/Services/ControlHub/UpstreamLockResolverTest.php`

**Constat initial (review sonnet)** : `lockItem()` crée un nouveau contrat actif par appel ; deux appels → `ensureResolved()->first()` n'en voit qu'un. Fragilité latente (non déclenchée aujourd'hui).

**Avis Opus** : note 1 — footgun de test, pas bug prod (invariant ≤ 1 contrat actif garanti en réception 28.2 ; même patron `->first()` que `UpstreamContractSource`).

**Action** : ✅ **Corrigé** (documentation). PHPDoc d'avertissement ajouté au helper (« n'appeler qu'une fois par test »).

### #5 — Alignement de clé prouvé implicitement

**Sévérité** : 🟡 — **Pertinence Opus** : 1
**Fichier(s)** : `tests/Unit/Services/ControlHub/UpstreamLockResolverTest.php`

**Constat initial (review sonnet)** : le test vérifie le format du provider mais ne compare pas directement avec la normalisation interne du resolver.

**Avis Opus** : note 1 — gap cosmétique (code byte-identique des deux côtés ; preuve fonctionnelle via `isCapabilityLocked`).

**Action** : ✅ **Corrigé automatiquement.** Cross-check direct ajouté : `assertArrayHasKey($providerKey, $resolver->lockedRegistryKeys())` — la clé indexée par le resolver est byte-identique à `exclusiveKey()` du provider.
