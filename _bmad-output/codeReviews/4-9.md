# Code Review — Story 4.9 : Sync AD machine via observer Eloquent + LdapRecord modrdn

## Questions en attente

1. **#1 — Stratégie enrollment `create`** : aujourd'hui `WorkstationEnrollmentService::enrollName()` ligne 161 fait `Workstation::create()` (qui déclenche l'observer → job AD async) PUIS appelle directement `adMachineManager->check()` + `registerHardware()` lignes 169-172. C'est une double passe AD. Deux options :
   - (a) **Garder appels directs + bypass observer** : wrapper `Workstation::create()` dans `WorkstationObserver::withoutSync(...)`. L'enrollment garde son flux sync 1-pass + `EnrollNameResult::created($ws, $sanitized, $adOk=résultat réel)`. Les autres call-sites (admin UI, seeders) restent observer-driven.
   - (b) **Supprimer appels directs + tout via job** : laisser `Workstation::create()` déclencher l'observer, supprimer lignes 169-172, retourner `$adOk=true` ou `null` dans `EnrollNameResult` (le résultat AD est différé en async). Plus propre conceptuellement mais on perd le feedback synchrone du firmware iPXE.

2. **#3 — Race condition rename+status simultanés** : si un `save()` modifie name ET status, l'observer dispatche deux jobs. Le job `status` cherche AD par le nouveau name → si le job `rename` n'a pas encore tourné, no-op silencieux et status AD désynchro. Deux options :
   - (a) **Job `update` fusionné** : nouvelle action job `update` qui regroupe rename+status en une opération, dispatchée quand les deux changent ensemble.
   - (b) **Documenter limitation** : « ne pas modifier name et status dans un même `save()` ; faire deux saves séparés ». Et ajouter un test guard qui throw si les deux dirty.
   - (c) **Status retry sur old_name** : si `findBy($newName)` null, retenter avec `getOriginal('name')` (complexifie).

## Détail des problèmes

### #1 — Double exécution AD dans enrollment create

**Sévérité** : 🔴 **Pertinence Opus** : 3
**Fichier** : `app/Ipxe/Services/WorkstationEnrollmentService.php:161-189`

**Constat** : `Workstation::create()` ligne 161 déclenche l'observer `created` → job `WorkstationAdSyncJob::create` (qui appelle samba-tool `check` + `registerHardware`). Lignes 169-172 re-appellent les mêmes méthodes en synchrone. En queue=sync (déploiement initial), c'est littéralement 2× les ops AD bloquantes pour le firmware iPXE. En queue async, le log `ad_result='success'` reflète les appels synchrones, alors que `ad_guid` ne sera posé qu'au passage du job — incohérence d'observabilité.

**Action** : En attente de décision utilisateur (cf. Q1 supra).

### #2 — AC9 incomplet : tests LdapRecord/DirectoryEmulator manquants

**Sévérité** : 🔴 **Pertinence Opus** : 2 (« choix conscient documenté »)
**Fichier** : `tests/Unit/Jobs/AdSync/WorkstationAdSyncJobTest.php`

**Constat** : 13 tests présents mais aucun n'exerce `MachineModel::findBy/rename/delete/save`. La garantie de préservation `objectGUID`/`netbootGUID` (raison d'être de la story) repose entièrement sur le runbook manuel `docs/qa/domains/ad-sync.md`. L'équipe documente ce choix (commentaire lignes 21-27 du fichier de test). Opus tempère : c'est une dette technique acceptable si le runbook est rejoué périodiquement.

**Action** : Différable. Follow-up : intégrer `LdapRecord\Testing\DirectoryEmulator` dans une story ultérieure.

### #3 — Race condition rename+status simultanés

**Sévérité** : 🟠 **Pertinence Opus** : 2
**Fichier** : `app/Observers/WorkstationObserver.php:85-111`, `app/Jobs/AdSync/WorkstationAdSyncJob.php:323`

**Constat** : Deux jobs indépendants dispatchés si name et status dirty ensemble. Le job status cherche AD par le nouveau name ; si rename pas encore exécuté, `findBy(newName)` null → no-op idempotent → status AD désynchro de manière silencieuse et non-retry-able.

**Action** : En attente de décision utilisateur (cf. Q3 supra).

### #4 — Status périmé : `params['status']` dominante

**Sévérité** : 🟠 **Pertinence Opus** : 1
**Fichier** : `app/Jobs/AdSync/WorkstationAdSyncJob.php:308`

**Constat** : `$status = (string) ($this->params['status'] ?? $ws->status);` — la valeur du dispatch domine. Si status change pendant que le job est en backoff, on applique la valeur périmée. Convergence finale garantie sauf si on perd des jobs, mais peu pertinent en pratique.

**Action** : ✅ Auto-fix — inverser la priorité (`$ws->status ?? $this->params['status']`), 1 ligne.

### #5 — Docblock isDirty/wasChanged (Sonnet)

**Sévérité** : 🟠 **Pertinence Opus** : 0 (rejet)
**Constat** : faux positif. Opus a vérifié le code Eloquent : `wasChanged()` reste le bon choix, le commentaire est défendable.

**Action** : ❌ Aucune.

### #6 — `$adResult=true` hardcodé + `$oldName` mort

**Sévérité** : 🟠 **Pertinence Opus** : 3
**Fichier** : `app/Ipxe/Services/WorkstationEnrollmentService.php:200, 210, 211, 216`

**Constat** : Log iPXE émet toujours `ad_result='success'` même si le job AD fail x3 — log mensonger pour un opérateur en troubleshooting. Variable `$oldName` capturée puis immédiatement `unset()` — code mort.

**Action** : ✅ Auto-fix — passer `ad_result='dispatched'` (ou supprimer le champ), retirer `$oldName` et son `unset`.

### #7 — `SAMBAEDU_DOMAIN` vide

**Sévérité** : 🟡 **Pertinence Opus** : 2
**Fichier** : `app/Jobs/AdSync/WorkstationAdSyncJob.php:254-263, 370-374` (méthode `resolveDomain()`)

**Constat** : Si `config('sambaedu.domain', '')` renvoie `''`, on pose `dnsHostName=$newName` (sans `.domain`) et SPN sans FQDN. Pas de log warning. En prod le domain sera toujours posé, mais en dev/CI fraîche c'est silencieux et Kerberos peut casser subtilement.

**Action** : ✅ Auto-fix — log warning explicite + skip `dnsHostName`/`servicePrincipalName` si domain vide (vs poser des valeurs cassées).

### #8 — Dispatch hors `afterCommit()` (manqué par Sonnet)

**Sévérité** : 🔴 **Pertinence Opus** : 3
**Fichier** : `app/Observers/WorkstationObserver.php` (`created` / `updated` / `deleting`)

**Constat** : Les `dispatch()` sont émis dans les hooks observer alors que la transaction Eloquent (ou `DB::transaction()` englobante de `WindowsPostInstallTracker::wrapTransaction`) n'est pas encore committée. En queue=sync (déploiement initial), le worker peut `find($id)` → null si la row n'est pas visible. En queue=database/redis le risque est plus faible mais existe.

**Action** : ✅ Auto-fix — ajouter `public $afterCommit = true;` sur `WorkstationAdSyncJob`, ou `dispatch($job)->afterCommit()` dans l'observer (équivalent en Laravel 11+).

### #9 — `handleDelete` par cn vs `ad_guid` stable (manqué par Sonnet)

**Sévérité** : 🟠 **Pertinence Opus** : 2
**Fichier** : `app/Jobs/AdSync/WorkstationAdSyncJob.php:281-289`

**Constat** : `handleDelete` fait `MachineModel::findBy('cn', $name)`. L'observer passe pourtant `ad_guid` dans les params (capturé dans `deleting`). Si entre le `deleting` et l'exécution du job le compte AD a été renommé hors-Sambaedu (ex. admin direct ldap), `findBy('cn', oldName)` retourne null → idempotent no-op → fuite de compte AD orphelin. L'`ad_guid` est l'identifiant stable.

**Action** : ✅ Auto-fix — `findByGuid($ad_guid)` en priorité, fallback `findBy('cn', $name)` si guid absent.

### #10 — `WorkstationObserver::$syncEnabled` global state (manqué par Sonnet)

**Sévérité** : 🟠 **Pertinence Opus** : 2
**Fichier** : `app/Observers/WorkstationObserver.php` (helpers `enableSync`/`disableSync`)

**Constat** : `disableSync()` est `public static`. Un appel sans pair `enableSync()` dans un worker queue persistant désactive la sync pour toute la durée du process. `withoutSync()` est try/finally-safe mais le footgun reste public.

**Action** : ✅ Auto-fix — rendre `disableSync`/`enableSync` `private`, exposer uniquement `withoutSync()`.

### #11 — `handleCreate` ne consulte pas `getAdOu()` (manqué par Sonnet)

**Sévérité** : 🟠 **Pertinence Opus** : 2
**Fichier** : `app/Jobs/AdSync/WorkstationAdSyncJob.php:138, 187`

**Constat** : Le job crée toujours dans `CN=Computers,DC=...` (comportement samba-tool par défaut). Si la machine est rattachée à une `PhysicalRoom` avec une `ad_dn` spécifique (OU), il y a divergence. Comportement iso-legacy : le move OU se fait après-coup via un autre flux. Pas dans le scope de cette story.

**Action** : Différable. Clarifier dans le suivi epic 4.

### #12 — Tests existants iPXE muets sur observer

**Sévérité** : 🟡 **Pertinence Opus** : 2
**Fichier** : `app/Providers/AppServiceProvider.php:209` (guard `! environment('testing')`)

**Constat** : Hors `WorkstationObserverTest`, aucune suite de test ne déclenche l'observer Workstation. `WorkstationEnrollmentServiceTest`, `WindowsPostInstallTrackerTest` valident donc juste le PG-side. C'est cohérent avec la stratégie « tests offline-LDAP », mais c'est une dette de couverture.

**Action** : Différable. Pattern d'activation manuelle déjà documenté dans `WorkstationObserverTest`.

## Corrections appliquées 2026-05-28

### Problèmes corrigés

- **#1** — Double exécution AD enrollment create : `Workstation::create()` wrappé
  dans `WorkstationObserver::withoutSync(...)` dans la branche « cas 1 » de
  `WorkstationEnrollmentService::enrollName()`. Après `check()` +
  `registerHardware()` synchrones, lecture `MachineModel::findBy('cn', $sanitized)`
  et stockage `ad_guid` + `ad_dn` via un second `withoutSync()` pour cohérence
  PG↔AD sans repasser par le job.
- **#3** — Race rename+status : nouvelle action `ACTION_UPDATE` + factory
  `WorkstationAdSyncJob::update(...)` + handler `handleUpdate()` (rename modrdn
  + UAC en une seule transaction LDAP). Observer modifié pour dispatcher UN
  SEUL job `update` quand `wasChanged('name')` ET `wasChanged('status')`.
- **#4** — `handleStatus` lit désormais `$ws->status` en priorité, params en
  fallback.
- **#6** — `WorkstationEnrollmentService::enrollName()` branche rename :
  variable `$oldName` morte supprimée ; `ad_result` log passe à `'dispatched'`
  (le résultat AD réel est désormais async via la queue).
- **#7** — `handleRename` et `handleUpdate` : si `resolveDomain()` retourne `''`,
  warning explicite + skip `dnsHostName` et `servicePrincipalName` (pas de
  fallback cassé).
- **#8** — Dispatch via `->afterCommit()` côté `WorkstationObserver` pour
  `create` / `rename` / `status` / `update` / `delete`. Voie observer-side
  choisie (vs propriété `$afterCommit` sur le job) car plus explicite et
  compatible Laravel 12 sans assumption sur le contract `ShouldQueue`.
- **#9** — `handleDelete` : priorité `MachineModel::findByGuid($adGuid)` ;
  fallback `findBy('cn', $name)` si guid absent / not found. Log warning
  explicite si le CN AD diffère du `name` PG (audit rename hors-Sambaedu).
- **#10** — `disableSync()` / `enableSync()` passés `private`. Seule API
  publique : `withoutSync(callable $cb)`. Call-site externe
  (`WorkstationService::importFromAd`) refactoré pour lire/restaurer
  `$syncEnabled` manuellement (la transaction DB englobante ne permet pas
  un wrap closure simple). Tests utilisent toujours `$syncEnabled` en lecture
  pour inspection — compatible.

### Décisions design appliquées

- **#1 (a)** — Henri 2026-05-28 : conservation des appels sync

  back-fill `ad_guid` / `ad_dn` post-création AD.
