## Détail des problèmes

### #1 — `action: allow` non validé (angle mort du mécanisme)
**Sévérité** : 🟠 · **Pertinence** : 3 · **Fichiers** : `FirewallAuthoringGuard.php`, `handler_firewall.go`

**Constat (review sonnet)** : Q3 ne restreint que `block`. Une future capacité (ou donnée insérée par migration Query Builder contournant l'observer) `{in, allow, explicit, 0.0.0.0/0, tcp, 3389}` ouvrirait RDP à tout Internet, sans garde-fou serveur ni agent.

**Évaluation orchestrateur** : réel mais hors périmètre de la donnée livrée (aucune capacité `allow` en v1 ; `internet_access`/`block` entièrement gardé). C'est une décision de POLITIQUE du mécanisme, non couverte par Q3/Q4 → question Henri (Q5). Un docblock « angle mort assumé v1 » a été ajouté ; l'implémentation attend la décision.

**Action** : ✅ Corrigé (Q5 tranchée par Henri → garde-fou minimal). `FirewallAuthoringGuard` exige désormais un `warning` non vide sur toute règle `allow` + `direction:in` dont la portée remote couvre l'Internet ouvert (`/0` détecté par intervalles, miroir du refus Q3 block ; source du warning identique au deny fs_acl). Côté agent : server-only assumé et documenté — le `warning` est métadonnée de capacité, jamais au payload (invariant 27.12) ; un refus agent casserait les `allow` légitimes. Réserve documentée : union de plages étroites couvrant `/0` (ex. `0/1`+`128/1`) non détectée (cohérent avec la logique per-plage de Q3). Commit `775cbf7`.

### #2 — Session COM STA sans LockOSThread
**Sévérité** : 🟡 (relevé pertinence 3) · **Fichier** : `agent/windows/handler_firewall_windows.go::withFwRules`

**Constat (review sonnet)** : la session COM apartment-threaded n'était pas épinglée à un OS thread ; la préemption asynchrone de Go (≥1.14) peut migrer la goroutine entre deux `syscall.SyscallN` d'une même session STA (illégal COM → HRESULT imprévisibles). Auto-réparé au cycle suivant, mais vrai risque de fiabilité sur un mécanisme de sécurité.

**Évaluation orchestrateur** : gotcha Go+COM classique, réel. Bug pré-existant identique dans `handler_shortcuts_windows.go` (27.x) — hors périmètre 36.2, noté en suivi.

**Action** : ✅ Corrigé. `runtime.LockOSThread()` en tête de `withFwRules`, `defer runtime.UnlockOSThread()` (unlock après `CoUninitialize`). `GOOS=windows go build`/`vet` OK. **Suivi** : appliquer le même correctif à `handler_shortcuts_windows.go`.

### #3 — `rule_id` émis en casse d'origine
**Sévérité** : 🟡 · **Pertinence** : 2 · **Fichier** : `FirewallCapabilityProvider.php::expand()`

**Constat** : `rule_id` émis avec la casse d'origine ; seule `exclusiveKey()` minusculise. Le nom de règle Windows dérivé hérite de la casse → si `rule_id` change de casse en coïncidant avec un changement de propriété, la séquence Remove/Add pourrait laisser une règle orpheline (si `INetFwRules::Remove` est sensible à la casse).

**Action** : ✅ Corrigé. `strtolower()` dès l'émission (cohérence `exclusiveKey`). Golden inchangé (`internet-block` déjà minuscule).

### #4 — slug `rule_id` non validé côté agent
**Sévérité** : 🟡 · **Pertinence** : 2 · **Fichier** : `handler_firewall.go::parseFirewallSpec`

**Constat** : le serveur valide `rule_id` contre `^[a-z0-9][a-z0-9_-]{0,63}$` ; l'agent vérifie seulement `!= ""`. Un `rule_id` malformé atteignant l'agent produirait un nom de règle non slugifié — rupture de la symétrie défense-en-profondeur affichée pour Q3.

**Action** : ✅ Corrigé. Regex slug miroir en Go (`firewallRuleIDSlug`) dans `parseFirewallSpec` + test `TestFirewallRuleIDSlugRejected`.

### #5 — `ensure` en liste passe le guard en silence
**Sévérité** : 🟡 · **Pertinence** : 2 · **Fichier** : `FirewallAuthoringGuard.php::ensureValues()`

**Constat** : si `ensure` est une liste (ni littéral ni map), `ensureValues()` retourne `[]` → aucune valeur validée. Fail-closed en aval, mais masque une erreur d'authoring.

**Action** : ✅ Corrigé. Cas liste = violation explicite + test `guard_refuses_ensure_as_list`.

### #6 — Commentaire observer incomplet
**Sévérité** : 🟡 · **Pertinence** : 2 · **Fichier** : `AppServiceProvider.php`

**Constat** : le commentaire au-dessus de l'enregistrement de `CapabilityProjectionObserver` ne mentionnait que fs_acl (36.1), pas la réutilisation firewall (36.2).

**Action** : ✅ Corrigé (doc).
