## Détail des problèmes

### #3 — URL 404 silencieuse si `saveto` hors `packages/`

**Sévérité** : 🔴
**Fichier(s)** : `app/Services/AppStore/PackagesXmlService.php:234-290`

**Constat initial (review Sonnet)** :
La dérivation `saveto → http://<se4fs>/wpkg/files/<rel>` suppose que tout `saveto` commence par `packages/`. `PackageInstallerService::downloadFiles` dépose le payload à `storagePath/saveto` ; l'alias Apache sert `storagePath/packages`. Un `saveto` = `softwares/firefox/firefox.exe` est déposé hors de l'arbre servi → URL `/wpkg/files/softwares/...` → 404 silencieux (la classe de bug que la story prétend résoudre). Le commentaire de `stripPackagesPrefix()` « l'URL reste cohérente » est trompeur.

**Avis Opus** : pertinence **3**, et **sous-évalué** dans sa formulation : ce n'est pas hypothétique.
- `saveto` pris **verbatim** du XML de recette ; ni le legacy (`admin_app_upload.php`) ni SE5 (`PackageInstallerService:66`, `LegacyWpkgImporter:246` place à `storage_path/saveto` sans normaliser le préfixe) n'imposent `packages/`. C'est une **convention, jamais une garantie**.
- Vérification croisée (grep fixtures) : des `saveto` réels existent hors `packages/` → `softwares/7zip/7z.exe`, `softwares/firefox/firefox.exe`, `wpkg/packages/firefox/setup.exe`. Déposés hors de l'arbre `…/install/packages` servi par l'alias T1.
- Commentaire ligne 280-281 **factuellement faux**.

**Action** : **corrigé automatiquement**. Garde-fou ajouté : un `<download>` d'une recette `%SOFTWARE%` dont le `saveto` ne commence pas par `packages/` n'est PAS réécrit en HTTP (non livrable par l'alias) → strip + `Log::warning` diagnosable (au lieu d'une URL 404 silencieuse). Commentaire de `stripPackagesPrefix()` corrigé (les appelants garantissent désormais le préfixe). Test ajouté.

### #1 — Recette `%SOFTWARE%` sans payload HTTP livrable

**Sévérité** : 🟠
**Fichier(s)** : `app/Services/AppStore/PackagesXmlService.php:197-226`

**Constat initial (review Sonnet)** :
Si une recette a `%SOFTWARE%` dans un `<install cmd>` mais que son `<download>` n'a pas de `saveto` (strippé ligne 209), l'install est tout de même réécrit en `%TEMP%` sans qu'aucun payload n'y soit téléchargé → `xcopy %TEMP%\…` échoue silencieusement. Cas dégénéré non testé.

**Avis Opus** : pertinence **2**. Vrai et non testé, mais cas dégénéré (un `<download>` sans saveto est inhabituel). À traiter avec le même garde-fou que #3.

**Action** : **corrigé automatiquement**. Après traitement des `<download>`, si la recette dépend de `%SOFTWARE%` mais qu'aucun `<download>` n'a été réécrit en HTTP (tous strippés : sans saveto, hors `packages/`, ou archive extraite serveur), `Log::warning` signale que l'install échouera sur le poste (faute de payload). Couvre #1 et #3 sous un même invariant de cohérence. Test ajouté.

### #M1 — Collision `%TEMP%` entre paquets — **RETIRÉ (invalide)**

**Sévérité** : ~~🟠~~ → néant
**Fichier(s)** : `app/Services/AppStore/PackagesXmlService.php:234-247` ; `app/Services/AppStore/PackageInstallerService.php:66,93,103`

**Avis Opus initial** : pertinence **2** — `target` sans préfixe unique par paquet collisionnerait dans `%TEMP%` ; le serveur évite ça via `str_replace('/', '_', saveto)`.

**Réfutation (vérif code, sur challenge utilisateur)** : `target` = `saveto` moins le préfixe fixe `packages/`, **sous-arborescence conservée**. Or `saveto` est le chemin de **dépôt physique serveur** (`downloadFiles:66` = `storagePath/<saveto>`, `move()` :103 écraserait tout doublon) → **`saveto` est unique par fichier, invariant filesystem**. Retirer un préfixe fixe est une bijection → `target` unique ssi `saveto` unique → deux fichiers distincts ne peuvent PAS viser le même `%TEMP%\…`. La sous-arborescence étant gardée, pas de collision de basename non plus (`app/setup.exe` ≠ `mix/setup.exe`). Deux paquets « au même chemin » = même `saveto` = **même fichier physique** (payload partagé) → même contenu, inoffensif/idempotent. Le `str_replace('/', '_', saveto)` (:93) sert au **nom de staging `tmp2/`** (aplatir un chemin en un nom de fichier pour le download serveur), **pas** à éviter une collision de placement final → analogie d'Opus erronée.

**Action** : **retiré**. Aucun correctif requis.

### #M2 — `%TEMP%` jamais purgé _(manqué par la review)_

**Sévérité** : 🟠
**Fichier(s)** : `app/Services/AppStore/PackagesXmlService.php` (section 5 de `transformPackageForHttpDelivery`)
**Avis Opus** : pertinence **2**. Accumulation non bornée de binaires dans `%TEMP%` (SYSTEM = `C:\Windows\Temp`, **non purgé au reboot par Windows**). Trou opérationnel cohérent avec [[project_agent_resource_state_per_machine_type_no_session]].

**Action (directive Henri)** : **corrigé** — « si l'install est un succès, on supprime immédiatement de `%TEMP%` ». Pour chaque `<download>` réécrit en HTTP, une `<install>` de purge est **appendue en fin de package** : `cmd /c del /F /Q "%TEMP%\<target>" 2>nul & exit /b 0`. Garanties tirées du moteur (`wpkg-se4.js:5820-5888`) :
- Les `<install>` s'exécutent dans l'ordre du document ; une commande de code ≠ 0 sans `<exit>` correspondant **throw → avorte le package** (5886). La purge en dernier ne tourne donc **que si tous les installs réels ont réussi** = sémantique « succès → purge ». Si l'install échoue, le payload **reste** pour diagnostic.
- `exec` = `WScript.Shell.Exec` (CreateProcess, pas de shell) → `del` (builtin) **exige** `cmd /c` ; cmd.exe expanse `%TEMP%` lui-même. Le `exit /b 0` final garantit que la purge **ne fait jamais échouer** le package.
- Le `<check>` vise le fichier **installé** (`%WinDir%\…`), pas le payload `%TEMP%` → purge sans impact sur l'idempotence.

Test : `http_delivery_appends_temp_purge_after_install`.
