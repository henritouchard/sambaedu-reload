## Détail des problèmes

### #1 — `--dry-run` bloqué par le garde `anonymize_enabled=false`

**Sévérité** : 🟠 — **Pertinence Opus** : 2
**Fichier(s)** : `app/Console/Commands/FederatedPurgeIdentitiesCommand.php`

**Constat initial (review Sonnet)** : Le check `if (!$enabled) return SUCCESS;` survient avant le `if ($dryRun)`. Avec le toggle OFF par défaut (D-8), `federated:purge-identities --dry-run` ne liste jamais les candidats — inutilisable pour l'audit préventif / la validation pré-activation par le DPO.

**Avis Opus** : Réel et gênant. Un `--dry-run` est par définition sans effet de bord et devrait pouvoir énumérer même toggle OFF. Aucun risque juridique (ne modifie rien).

**Action** : ✅ Corrigé — le `--dry-run` énumère désormais les candidats même quand `anonymize_enabled=false` (le garde toggle ne bloque plus que l'exécution réelle).

### #2 — `anonymize()` sans transaction DB

**Sévérité** : 🟠 — **Pertinence Opus** : 2 (renforcé par M-4)
**Fichier(s)** : `app/Auth/Federated/ExternalIdentityLifecycleService.php`

**Constat initial (review Sonnet)** : `anonymize()` enchaîne `identity->save()` (PII vidée + sub réécrit + anonymized_at), puis `foreach users -> save()` (désactivation), puis `identity->delete()` (soft-delete) — sans transaction. Si un `save()` User échoue au milieu, l'identité est anonymisée mais des Users restent `is_active=true` → accès résiduel post-purge (viole AC12).

**Avis Opus** : Réel. **M-4 aggrave** : l'idempotence repose sur `isAnonymized()` qui retourne immédiatement au rejeu → l'état partiel devient **irréparable par rejeu de la commande** (les Users restés actifs ne seront jamais re-désactivés). C'est la vraie raison de transactionner.

**Action** : ✅ Corrigé — corps d'`anonymize()` (et de `softDeleteWithReason()` par symétrie) enveloppé dans `DB::transaction()`.

### #3 — Garde d'idempotence `deactivate()`

**Sévérité** : 🟡 — **Pertinence Opus** : 1
**Fichier(s)** : `app/Auth/Federated/ExternalIdentityLifecycleService.php`

**Constat initial (review Sonnet)** : La garde `!is_active && deactivated_reason !== null` n'attrape pas le cas `is_active=false + reason=null` → `deactivate()` écrit le motif.

**Avis Opus** : Partiellement faux. Écrire un motif sur une identité qui n'en avait pas est un **complément légitime**, pas une corruption. Aucun chemin ne ré-écrase un motif existant (cas nominal bloqué). Pas un bug.

**Action** : ❌ Non corrigé (faux positif).

### #4 — Hash `sha256(sub)` sans sel (RGPD)

**Sévérité** : 🟡 — **Pertinence Opus** : 2
**Fichier(s)** : `app/Auth/Federated/ExternalIdentityLifecycleService.php` (`hashSub`)

**Constat initial (review Sonnet)** : `hash('sha256', $sub)` sans sel ; un `sub` à faible entropie est ré-identifiable par bruteforce/rainbow → `anon:<sha256>` resterait pseudonyme, invalidant l'argument « plus une donnée personnelle ».

**Avis Opus** : Pertinent mais c'est un **choix de conception en tension directe avec D-5** (le hash doit rester re-corrélable pour le forensique 20.4 : re-hasher un sub connu). Un sel `app.key` casserait cette propriété. Un HMAC à clé dédiée persistée serait un compromis. Arbitrage DPO — **ne pas corriger automatiquement**.

**Solutions possibles** :
1. Garder `sha256` nu en exigeant contractuellement (20.5) que controlHub émette des `sub` UUID v4 (≥122 bits → bruteforce impraticable).
2. HMAC-SHA256 avec une clé de rétention dédiée persistée (re-corrélable côté SE5, non-réversible pour un tiers).

**Action** : ⏳ En attente de décision Henri (Q-1 du document).
