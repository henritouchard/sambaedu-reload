## Détail des problèmes

### #1 — `cloneConfiguration` contourne le bornage catalogue

**Sévérité** : 🟠 — **Fichier(s)** : `app/Services/AppProfile/AppProfileService.php:617`, `resources/views/pages/parc/groups/[id]/index.blade.php:1676`

**Constat initial (Sonnet)** : `cloneConfiguration` appelle `assertCanAssignWpkgOnGroup($target)` (garde 29.1) mais jamais `assertApplicationsInUpstreamCatalog` avant `$target->applications()->sync(...)`. Cloner un parc source contenant une app hors catalogue la copie sans refus. `executeClone` n'a pas de catch dédié.

**Avis Opus** : pertinence **2/3**, constat **vérifié vrai**. C'est bien un chemin d'AJOUT (périmètre D4). Atteignabilité conditionnelle (la source doit contenir une app hors catalogue, possible « zéro prod / contrat arrive après »). Hors liste explicite T3 (la story ne listait que 3 méthodes) → angle mort de la story elle-même. **Corriger maintenant** : guarder `$appsAdded` (le delta ajouté, pas `$sourceAppIds` entier), + catch dédié dans `executeClone`.

**Action** : ✅ **Corrigé** — `assertApplicationsInUpstreamCatalog($appsAdded)` ajouté après calcul du delta, avant la transaction ; catch `ApplicationNotInUpstreamCatalogException` ajouté à `executeClone`. Test `clone_copying_out_of_catalog_app_is_refused_without_pivot_write`.

### #2 — Inconsistance `\Exception` vs `\Throwable` (page machine)

**Sévérité** : 🟡 — **Fichier(s)** : `resources/views/pages/parc/machines/[id]/index.blade.php:877`

**Constat initial (Sonnet)** : la page machine utilise `catch (\Exception)` en filet générique alors que la page groups utilise `\Throwable` ; un `Error` PHP remonterait en 500.

**Avis Opus** : pertinence **1/3**. L'exception catalogue (`extends RuntimeException extends Exception`) est captée par le catch **dédié** avec le bon message FR8 ; le `\Exception` n'est qu'un filet. La différence ne joue que pour un `Error` PHP, étranger au catalogue. Incohérence **pré-existante** (toute la page machine utilise `\Exception`), non introduite par 31.1.

**Action** : ❌ **Non corrigé** — impact nul sur la feature, refactor cosmétique pré-existant hors scope story.

### #3 — `WpkgSchemaBootstrapper` sans `controlhub_contract_catalog_apps`

**Sévérité** : 🟡 — **Fichier(s)** : `tests/Support/WpkgSchemaBootstrapper.php:190`

**Constat initial (Sonnet)** : le bootstrapper crée `controlhub_contracts` (vide) mais pas `controlhub_contract_catalog_apps`. Un futur test créant un contrat actif déclencherait `no such table`.

**Avis Opus** : pertinence **2/3**, **vérifié vrai** — fragilité latente, demi-correctif (exactement la classe de bug déjà corrigée pour `controlhub_contracts`). Inoffensif aujourd'hui (court-circuit NFR3), foot-gun demain. **Corriger maintenant** (trivial).

**Action** : ✅ **Corrigé** — table vide ajoutée au `bootstrap()` + au `tearDown()`.

### #4 — App `app_id = null` refusée silencieusement

**Sévérité** : 🟡 — **Fichier(s)** : `app/Services/AppProfile/AppProfileService.php:826`

**Constat initial (Sonnet)** : une app avec `app_id = null` → `(string) null = ''` → `permits('')` false → refusée, non documenté ni testé.

**Avis Opus** : pertinence **1/3**, constat **partiellement inexact** : le comportement n'est pas « silencieux » (l'exception est levée avec message), c'est un **deny cohérent des deux côtés**. `app_id` est de fait requis (docblock `string`, jamais nullable en pratique PG). Scénario quasi-inatteignable.

**Action** : ❌ **Non corrigé** — quasi-inatteignable, comportement défendable (une app sans identifiant catalogue ne peut pas y appartenir).

### #M1 — Page de composition de profils non bornée (manqué par Sonnet)

**Sévérité** : 🟠 — **Fichier(s)** : `resources/views/pages/parc-settings/profiles/index.blade.php:213,303`

**Avis Opus (pertinence 3/3)** : **cause racine = erreur de cadrage de la story**. T2 a filtré `AppProfileService::listApplicationsForSelect()` qui est du **code mort** (utilisé uniquement par le test, par aucune vue). La **vraie** surface de composition de profil, `getAvailableApplicationsProperty()`, utilisait `Application::query()` **brut** → apps hors catalogue **proposées** (violation AC1). `addSelectedApps()` appelle bien le garde (aucun pivot hors-catalogue écrit), **mais** son catch `\Exception` générique affichait « Erreur lors de l'ajout » au lieu du message FR8 « hors catalogue amont » (violation AC2/FR8 — le « bouton opaque » que la story voulait éviter).

**Action** : ✅ **Corrigé** — `->inUpstreamCatalog()` ajouté à `getAvailableApplicationsProperty()` ; catch `ApplicationNotInUpstreamCatalogException` → `toastError($e->getMessage())` ajouté à `addSelectedApps()` (+ import). _(Le filtrage de `listApplicationsForSelect` est conservé : couvert par test, inoffensif.)_

### #M2 — `is_parc_default` broadcast non borné (manqué par Sonnet)

### #M3 — `createProfile`/`updateProfile` sans garde (manqué par Sonnet)

**Sévérité** : 🟡 — **Fichier(s)** : `app/Services/AppProfile/AppProfileService.php:94,124`

**Avis Opus (pertinence 2/3)** : `createProfile` (`attach($data['application_ids'])`) et `updateProfile` (`sync(...)`) composent un profil avec des apps **sans** garde. Non atteignable depuis l'UI actuelle, mais **bypass latent** si un futur appelant passe `application_ids`.

**Action** : ✅ **Corrigé** — `assertApplicationsInUpstreamCatalog($this->normalizeIds($data['application_ids']))` ajouté en tête des deux méthodes (avant transaction, inerte hors-contexte). Tests `create_profile_with_out_of_catalog_app_is_refused` + `update_profile_syncing_out_of_catalog_app_is_refused`.
