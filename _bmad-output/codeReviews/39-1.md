## Points solides confirmés (non-défauts)

- **Auth-avant-corps (NFR-A3) structurel** : le middleware `controlhub.auth` ne lit que le header `Authorization` ; le corps est lu paresseusement par le seul contrôleur → un payload volumineux/malformé ne peut pas crasher avant auth. Token jamais loggé.
- **Mapping HTTP complet** : `ingest()` ne lève en phase pure que `UnsupportedSchemaVersionException` et `InvalidUpstreamContractException` (les deux catchées → 422) ; les deux listeners synchrones avalent tout `\Throwable` → pas de 500 non voulu.
- **Pas de mass-assignment / injection** : le service sélectionne explicitement les champs (`updateOrCreate` sur tableaux contrôlés).
- **Retrait `master_api_key` propre et complet** : branche morte par construction (`config('controlHub.master_api_key')` inexistant). `controlhub_key_type` toujours `'instance'` ; `LinkSeveranceController` non régressé.

## Détail des problèmes

### #1 — 🟠 Corps authentifié non-contrat coercé en désir d'état vide (destructif)

**Sévérité** : 🟠 Important — **Pertinence** : 3
**Fichier(s)** : `app/Http/Controllers/Api/v1/ControlHub/ContractIngestionController.php`

**Constat (review opus)** :
Le contrôleur passait `$request->json()->all()` à `ingest()` sans garde de forme. `ingest()` résout chaque agrégat via `$payload['items'] ?? []` : tout corps décodant en tableau sans les clés attendues devient un « contrat vide » valide. Vérifié empiriquement : `POST {}` authentifié → `200 {success:true, contract_created:true, mutated:true}`, 1 contrat actif créé, `ControlHubContractChanged` dispatché → les deux listeners synchrones réconcilient vers un état **vide** (prune des groupes imposés, re-provisioning à vide) et, après une rupture 32.1, un `{}` **recrée un contrat actif** = ré-établissement silencieux du lien rompu. Le défaut n'est pas la sémantique désir-d'état (un contrat *explicitement* vide « efface tout » est légitime) mais **l'absence de distinction entre « corps illisible/non-contrat » et « contrat vide »**.

**Évaluation orchestrateur** :
Confirmé par lecture du code. `schema_version` étant **optionnelle** (rétro-compat 28.2 : absente ⇒ version courante), la garde ne peut pas l'exiger ; le signal distinctif est la **présence d'au moins une clé d'enveloppe reconnue** (`schema_version`, `items`, `labels`, `imposed_groups`, `catalog_apps`). Correctif en scope 39.1 : c'est l'exposition HTTP (introduite par cette story) qui rend le chemin atteignable par l'amont ; NFR-A3 « payload malformé » est dans le périmètre.

**Solution appliquée** :
Garde de frontière HTTP dans le contrôleur (constante `CONTRACT_ENVELOPE_KEYS` + `array_intersect` sur les clés du payload) : un corps sans aucune clé d'enveloppe → **422 `invalid_upstream_contract`** *avant* délégation (zéro écriture, zéro événement). La sémantique pure de `ingest()` n'est **pas** touchée (invariants 28.2/33/golden préservés ; les appelants internes inchangés). Un contrat vide *explicite* (agrégats déclarés vides) reste accepté.

**Action** : corrigé automatiquement.

### #3 — 🟡 200 « contrat persisté » vs « contrat appliqué »

**Sévérité** : 🟡 Mineur (observation cross-story) — **Pertinence** : —
**Fichier(s)** : `ContractIngestionController.php` + listeners `ReconcileImposedWorkstationGroups` / `ProvisionOrderedApplications`

**Constat** : les listeners avalent tout `\Throwable` (bon pour éviter un rollback post-commit), mais l'amont reçoit `200 success` même si la réconciliation a silencieusement échoué (seul un `Log::error` local subsiste). Pré-existant (28.3/31.3).

**Évaluation orchestrateur** : la conformité d'*application* est précisément l'objet du canal ③ (émetteur de conformité `se5-contract-compliance/v1`, Story 39.2) : le 200 de 39.1 doit rester « **contrat reçu/persisté** », l'état `applied|pending|error|overridden` étant remonté hors-bande. Décision cohérente avec l'architecture de l'epic ; aucun changement en 39.1.

**Action** : ignoré (documenté).
