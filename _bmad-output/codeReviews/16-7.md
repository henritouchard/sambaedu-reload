## Détail des problèmes

### #1 — `register_machine_hardware` au mauvais moment

**Sévérité** : 🔴
**Fichier(s)** : `app/Gpo/Services/ApplicationScriptsGenerator.php:139`, `app/Gpo/Services/ApplicationLoggerService.php:71-84`

**Constat initial (Sonnet)** :
Legacy (`applications.inc.php:799-800`) appelle `register_machine_hardware` DANS le bloc `if ($ret == "0")` du `log_application_scripts` (= 2nd appel curl, footer post-exécution). Natif l'appelle dans `resolveInfo` au premier appel (`ret > 0`). Si script échoue, legacy ne persiste pas l'UUID, natif si.

**Avis Opus (pertinence 3)** :
Confirmé. En pratique, sur le 1er appel curl initial, `%UUID%` n'est pas encore résolu côté PowerShell — c'est le startup script qui le récupère via wmic et le renvoie dans le footer `ret=0`. Donc la divergence côté natif s'amorce au 1er appel avec `uuid=''` (no-op), MAIS le footer côté natif ne fait jamais `registerHardware` non plus → **UUID jamais enregistré dans le natif** (vs legacy qui l'enregistre au footer).

**Solutions possibles** :
1. Déplacer `registerHardware` dans `ApplicationLoggerService::logScripts` branche `$ret === 0` (parité stricte legacy)
2. Garder dans `resolveInfo` mais documenter en `@legacy-bug` que c'est une "amélioration" (UUID enregistré dès le startup, pas seulement à la fin)
3. Bonus : aussi déplacer `setOs` dans `logScripts` (parité ligne 780-781 legacy)

**Action** : ⏳ En attente décision user

2. Retirer le `forget('scripts.$id)` + documenter "pas de cache scripts" en tech-debt

### #4 — `local_admin_scripts` Windows logon no-op

**Sévérité** : 🟠
**Fichier(s)** : `app/Gpo/Services/ApplicationScriptsAssembler.php` (localAdminScripts + resolveLocalAdminRight), `app/Gpo/Services/ApplicationScriptsGenerator.php` (resolveAdminFlag)

**Constat initial (Sonnet)** :
Pour `os=windows && action=logon && userprofile !== ''`, le natif retourne script vide. Legacy (`:736-750`) génère `net localgroup administrateurs DOMAIN\user /add` selon `have_right`/`have_delegation`. Élévation locale perdue.

**Avis Opus (pertinence 3)** :
Confirmé. La dette EST tracée dans `tech-debt-gpo.md:114-128` ("Sortie prévue : Story 7.x dédiée OU shim ad hoc"). Pas une "D1 violation silencieuse" : c'est documenté.

**Décision Henri 2026-05-13** : Epic 7 « Délégations & droits » est `done` (cf. `sprint-status.yaml` 7.1/7.2/7.3) — les services Spatie natifs `PermissionService::canOnWorkstationGroup` + permission `computer.elevate` existent déjà. Le câblage est donc faisable sans nouvelle story dédiée → fix post-review.

**Correctif appliqué (2026-05-13)** :

1. `ApplicationScriptsAssembler` : injection optionnelle `PermissionService` + méthode publique `resolveLocalAdminRight(array $info): bool` qui résout :
   - global : `User::hasPermissionTo('computer.elevate')` (parité `have_right(SE_COMPUTER_ADMIN)`)
   - scopé : pour chaque `WorkstationGroup` candidat (via `Workstation::groups` SQL + fallback `WorkstationGroup::whereIn('name', $parcs)` LDAP), test `PermissionService::canOnWorkstationGroup` (parité `have_delegation`).
2. `localAdminScripts` branche `os=windows && userprofile !== ''` :
   - logon + droits → `net localgroup administrateurs "<SAMBA_DOMAIN>\<user>" /add\r\nset admin=1\r\n`
   - logoff inconditionnel → `net localgroup administrateurs "<SAMBA_DOMAIN>\<user>" /delete\r\n`
3. Branche Linux (`else`) câblée aussi : logon avec droits → `/etc/sudoers.d/<user>` + `chmod 0440` ; logoff inconditionnel → `rm -f /etc/sudoers.d/<user>` (parité legacy `:754-765`).
4. `ApplicationScriptsGenerator::resolveAdminFlag()` pose `$info['admin'] = 1` ssi la même résolution réussit (parité legacy `:936`).

**Mapping `SE_COMPUTER_ADMIN` → permission Spatie retenu** : `computer.elevate` (et non `computer.install`). Justification : `SambaPermission::ComputerElevate` est la seule à déclarer `requiresGpoSync() === true` — sa raison d'être est explicitement « admin local Windows ». Le composite legacy contenait `SE_COMPUTER_ELEVATE` (0x400) donc tout user porteur de l'ancien bit composite a aussi ce bit.

**Limite assumée** : mécanisme legacy d'élévation **temporaire** (`set_local_admin_right` + `local_admin_<user>` config param) non porté. Documentée tech-debt restante. Dans la condition cumulée legacy `:742-747`, le gating `get_local_admin_right != 0` retombait toujours sur `have_right || have_delegation` pour décider de l'`/add` — sémantique fonctionnelle principale préservée.

**Tests ajoutés** : `tests/Unit/Gpo/ApplicationScriptsAssemblerTest.php` (8 tests : add/logon global perm, add/logon délégation scopée, no-op sans droits, delete/logoff inconditionnel, sudoers.d Linux, rm sudoers Linux, resolve nil user, resolve cn missing).

**Action** : ✅ Corrigé (câblage Epic 7 natif)
