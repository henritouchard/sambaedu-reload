## Détail des problèmes

### #1 — TOCTOU singleton (SELECT-then-INSERT) non documenté

**Sévérité** : 🟠 — **Pertinence Opus** : 2
**Fichier(s)** : `app/Services/ControlHub/ControlHubContractIngestionService.php` (`resolveActiveContract`)

**Constat initial (review)** : Le pattern `SELECT first() … if null INSERT` n'est pas safe sous concurrence PostgreSQL READ COMMITTED : deux ingestions simultanées avec des `authority_ref` différents peuvent toutes deux voir « aucun contrat actif » et en créer deux. L'unicité `authority_ref` (28.1) protège l'unicité par référence, **pas** l'invariant « ≤ 1 actif ». Conforme à la story (index partiel délibérément différé, Task 3 optionnelle) mais risque non documenté.

**Avis Opus** : Réel ; probabilité faible car controlHub diffuse une réception à la fois par autorité amont. Mitigation cheap = une phrase PHPDoc, sinon `lockForUpdate()`. Pas bloquant.

**Action** : ✅ Corrigé — note PHPDoc ajoutée sur `resolveActiveContract()` documentant l'hypothèse de réception sérialisée et le renvoi vers l'index partiel différé.

### #2 — `received_at`/`link_state` re-positionnés sur mutation

**Sévérité** : 🟠 — **Pertinence Opus** : 1
**Fichier(s)** : `app/Services/ControlHub/ControlHubContractIngestionService.php:137-146`

**Constat initial (review)** : Sur changement d'`authority_ref` seul, `save()` réécrit `link_state = Active` (déjà actif) et `received_at = now()`. Sémantique ambiguë + soupçon de « dirty artificiel » sur `link_state`.

**Avis Opus** : Largement défendable — rafraîchir `received_at` sur mutation est correct. L'affirmation « dirty artificiel sur `link_state` » est **factuellement fausse** : assigner `Active` à un enum déjà `Active` ne marque pas dirty (`originalIsEquivalent`). Seul `received_at` rend le `save()` dirty, ce qui est l'intention. Note 1.

**Action** : ❌ Non corrigé — requalifié quasi faux-positif. La sémantique reste soumise à confirmation utilisateur (Q3), sans correctif de code.

### #6 — Event dispatché DANS la transaction

**Sévérité** : 🟡 — **Pertinence Opus** : 2
**Fichier(s)** : `app/Services/ControlHub/ControlHubContractIngestionService.php`

**Constat initial (review)** : `ControlHubContractChanged::dispatch()` dans le closure `DB::transaction`. Inerte en 28.2 (aucun listener) mais footgun pour 28.3 : un listener synchrone qui jette ferait rollback de l'ingestion validée ; un listener queued pourrait s'exécuter avant le commit.

**Avis Opus** : Réel forward-looking. Fix cheap recommandé **maintenant** : sortir le dispatch hors transaction.

**Action** : ✅ Corrigé — `$result->mutated`/`$result->contractId` capturés dans le closure ; le `dispatch` s'exécute **après** `DB::transaction()` (re-fetch `ControlHubContract::find(contractId)`). Comportement « 1 event sur mutation, 0 sur no-op » identique (tests verts).
