## Détail des problèmes

### #1 — Invariant « au plus une stable » = TOCTOU sous concurrence

**Sévérité** : 🟠
**Fichier(s)** : `app/Services/Agent/Releases/ReleaseCreationService.php` (create/promote), `app/Services/Agent/Releases/ReleaseManifestService.php:47`

**Constat (review opus)** :
L'invariant « au plus une ligne `is_stable = true` » n'est protégé que par le code en transaction, sans contrainte base ni verrou. Deux `create --stable`/`promote` concurrents peuvent produire deux stables ; le fallback `where('is_stable', true)->first()` sert alors une release non déterministe (AC3 affaibli).

**Évaluation orchestrateur** :
Pertinence : 2 — vérifié dans le code : les transactions ne se sérialisent pas entre elles (unset puis insert/set, pas de lock), et le `first()` du fallback n'a aucun `orderBy`. Risque pratique faible (CLI manuelle), mais la garantie revendiquée n'est pas tenue et le correctif minimal est à coût nul.

**Solutions possibles** :
1. `orderByDesc('id')` sur le fallback stable — déterminisme garanti même en cas de double stable (appliqué).
2. `lockForUpdate()` au début des transactions create/promote — sérialisation réelle (question 1).
3. Contrainte partielle PG — écartée par décision n° 5 (parité SQLite des tests).

**Action** : corrigé automatiquement (solution 1) ; solution 2 soumise à l'utilisateur.

### #2 — `version` et `filename` non cross-validés à la création

**Sévérité** : 🟡
**Fichier(s)** : `app/Services/Agent/Releases/ReleaseCreationService.php:64-122`

**Constat (review opus)** :
`create('2.1.2', 'sambaedu-agent-9.9.9.exe', …)` est accepté : version et filename validés indépendamment. Le manifest annoncerait une version divergente du binaire — confusion de reporting de progression par ring (25.2/25.5).

**Évaluation orchestrateur** :
Pertinence : 2 — validation manquante objective : la story décrit `filename` comme `sambaedu-agent-<version>.exe` (forme produite par le build 24.5, `version.go`), aucun cas légitime de dissociation aujourd'hui. Le test `duplicate_version_is_rejected` exploitait d'ailleurs cette faille (filename `2.1.2+r1` pour version `2.1.2`).

**Solutions possibles** :
1. Garde `filename === "sambaedu-agent-{$version}.exe"` → refus `filename_version_mismatch` (appliqué ; CLI inchangée).
2. Dériver le filename de la version et supprimer l'argument — plus invasif (signature CLI), réévaluable en 25.5.

**Action** : corrigé automatiquement (solution 1) + test dédié + ajustement du test `duplicate_version`.
Conséquence : le filename étant désormais strictement dérivé de la version (bijectif), la branche `duplicate_filename` du service est devenue inatteignable — supprimée (la contrainte unique DB reste le filet) ; son test devient un test du mismatch.
