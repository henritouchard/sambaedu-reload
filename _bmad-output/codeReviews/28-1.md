## Détail des problèmes

### #1 — NFR4 : la clé naturelle ne protège pas le cas `instance` (le plus courant)

**Sévérité** : 🔴 Critique
**Fichier(s)** : `database/migrations/2026_06_26_100000_create_controlhub_contract_tables.php` (unique `chc_item_natural_key`) ; `app/Models/ControlHubContractItem.php` ; `database/factories/ControlHubContractItemFactory.php`

**Constat (review)** : la clé naturelle est `(controlhub_contract_id, type, key, target_type, target_label)`. Pour un item ciblant l'instance, `target_label` valait **NULL**. Or en PG **comme** en SQLite, un index UNIQUE traite NULL comme **distinct** → deux items `instance` strictement identiques NE collisionnent PAS et coexistent. Comme le tier instance/Broadcast est le **défaut** du modèle projet ([[project_registry_default_broadcast_override]]), c'est le cas dominant. Ricochet 28.2 : un `INSERT … ON CONFLICT (… target_label)` ne matche jamais les lignes NULL → ré-insertion à chaque heartbeat → accumulation de doublons. La story déclare pourtant la clé naturelle comme « **le seul livrable d'idempotence de 28.1** » — non tenu pour le cas dominant.

**Action** : **Corrigé**. `target_label` passe en **`NOT NULL DEFAULT ''`** (portable PG + SQLite ; `''` = « pas de label / cible instance »). Migration, modèle (`@property string`), factory (`'' ` au défaut) mis à jour. L'ingestion 28.2 devra normaliser `null → ''` (documenté en commentaire migration). Alternatives écartées : index d'expression `COALESCE` (non portable via `$table->unique()`), PG15+ `NULLS NOT DISTINCT` (non portable SQLite).
