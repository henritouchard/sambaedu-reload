## Détail des problèmes

### #1 — Absence de vérification propriété du token

**Sévérité** : 🔴 Critique
**Fichier** : `app/Http/Controllers/PasswordResetExportController.php:46`

**Constat** :
`fetchListing($token)` est appelé sans vérifier que `$payload['operator_id']` correspond à `auth()->id()`. Un utilisateur authentifié avec un token valide (copie d'URL, log proxy) peut télécharger les mots de passe d'un autre opérateur.

**Avis Opus** (pertinence 3) :
Confirmé. Le middleware `signed` protège contre la forge mais PAS contre le partage de token. La vérification est triviale — `operator_id` est déjà dans le payload. Fix : `abort_if($payload['operator_id'] !== auth()->id(), 403)`.

**Action** : corrigé automatiquement.

### #2 — Injection JS via `$this->js()`

**Sévérité** : 🔴 Critique → reclassifié 🟡 Mineur par Opus
**Fichier** : `resources/views/components/organisms/password-reset-modal.blade.php:157`

`$this->js("window.open('{$downloadUrl}', '_blank');")` — concaténation PHP brute dans du JS.

**Avis Opus** (pertinence 1) :

**Action** : corrigé automatiquement via `dispatch('download-file', url: $downloadUrl)`.

### #3 — Test anti-fuite de mot de passe inefficace

**Sévérité** : 🔴 Critique
**Fichier** : `tests/Unit/Services/UserServiceBulkResetTest.php:158`

**Constat** :
(a) `!in_array('SuperSecret-42', $context, true)` ne parcourt pas les valeurs imbriquées ; (b) `assertTrue($result['success'] || !$result['success'])` est une tautologie (toujours vraie). Le test ne détecte pas une fuite réelle du mot de passe dans les logs.

**Avis Opus** (pertinence 3) :
Confirmé et aggravé. `Log::shouldHaveReceived('info')->withArgs(...)` sans contrainte d'appels peut passer même si aucun appel ne matche. Le test ne teste rien.

**Solution** : Capturer les logs via spy, sérialiser en JSON et asserter `assertStringNotContainsString('SuperSecret-42', json_encode($captured))`.

**Action** : corrigé automatiquement.

### #4 — Transaction DB enveloppe les appels LDAP

**Sévérité** : 🟠 Important
**Fichier** : `app/Services/UserService.php:268`

**Constat** :
`DB::beginTransaction()` est ouvert avant la boucle qui appelle `setUserPassword()` (LDAP). La connexion PostgreSQL reste ouverte pendant toute la durée des appels LDAP (100-500ms × N users). Aucun gain transactionnel réel sur les writes AD.

**Avis Opus** (pertinence 2) :
Confirmé. Solution : déplacer `DB::transaction()` uniquement autour de `$sqlUser->save()`, ou retirer complètement (les updates `pwd_reset_at` sont idempotents).

**Action** : ⏳ En attente de décision Henri (question #3).

### #13 — URLs signées exposées dans `wire:snapshot` du bandeau (Opus)

### #14 — Plaintext passwords en heap PHP sans zéroïsation sur happy path (Opus)

**Sévérité** : 🟠 Important
**Fichier** : `app/Services/UserService.php:880`

**Constat** :
`$plaintextPasswords` et `$results[]['new_password']` conservent les mdp en clair en mémoire. Le `catch` tente une zéroïsation mais le happy-path ne le fait jamais. PHP ne garantit pas la zéroïsation des strings (copy-on-write, GC).

**Avis Opus** :
Limitation PHP documentée — `sodium_memzero()` sur les copies si `ext-sodium` dispo, mais résolution complète impossible en PHP pur.

**Action** : ❌ Non corrigé (limitation langagière — documenté dans le code).

### #15 — `json_encode()` sans `JSON_THROW_ON_ERROR` → listing corrompu silencieux (Opus)

**Sévérité** : 🟠 Important
**Fichier** : `app/Services/BulkResetListingService.php:55`

**Constat** :
Si `$payload` contient un char UTF-8 invalide (nom AD cyrillique mal normalisé), `json_encode()` retourne `false`. `Crypt::encrypt(false)` chiffre le littéral `'false'`. `fetchListing()` décrypte `'false'`, `json_decode('false')` = false, `is_array()` échoue → retourne null → 410 Gone permanent. Data loss silencieux.

**Action** : corrigé automatiquement → `json_encode($payload, JSON_THROW_ON_ERROR | JSON_UNESCAPED_UNICODE)`.
