## Détail des problèmes

### #1 — `HubMode` en HKLM vs HKCU
**Sévérité** : 🟡 · **Fichier** : `database/migrations/2026_07_04_100000_seed_capabilities_explorer_lot.php:133`

**Constat (review opus)** : `HubMode` est seedé en HKLM (face Machine D4) alors qu'il est très largement documenté comme clé per-user (HKCU). C'est le candidat le plus susceptible d'être inefficace une fois armé (pas dangereux — juste sans effet). C'est un choix de portée (D4), pas seulement une valeur non vérifiée.

**Action** : ✅ Corrigé. Le protocole lab 36.3.1 (scénario QA) est renforcé : test déterminant de `HubMode` en **HKLM SEUL**, avec instruction explicite de déplacer la clé en HKCU (bascule provider Session, AC4 reste valide) AVANT merge si seul HKCU a de l'effet. La capacité étant `unmanaged`, aucun risque tant que non armée.

### #2 — `is_active=true` vs gate dur `is_active=false`
**Sévérité** : 🟡 · **Fichier** : `...seed_capabilities_explorer_lot.php:189`

**Constat (review opus)** : les 4 capacités sont seedées `is_active=true` avec des clés non vérifiées ; le précédent `photo_viewer_restored` (35.5) utilisait `is_active=false` comme gate dur. Si `migrate` atteignait /vm avant le gate (ex. déclenché par la story sœur 36.1), les capacités deviendraient armables avec des clés non validées.

**Décision orchestrateur** : 🚫 Conservé `is_active=true`. C'est le patron DOMINANT du projet pour un seed opt-in (lots CD95, registry_list) : la sûreté vient de `default_value='unmanaged'` (rien n'est émis à l'agent tant qu'un override de parc ne l'arme pas délibérément) + du gate-migrate. Le `is_active=false` de 35.5 était l'exception d'une limitation de **parseur** (`name=""`), pas de clés non vérifiées — non transposable. Aucune clé du lot n'est destructive une fois armée. Rationale ajouté en commentaire dans la migration.

### #3 — `created_at` dans le bloc UPDATE
**Sévérité** : 🟡 · **Fichier** : `...seed_capabilities_explorer_lot.php:192`

**Constat** : `updateOrInsert` réécrit `created_at` au rejeu de `up()`. Imperfection d'idempotence réelle mais **héritée à l'identique du patron CD95/ISO**, invisible au test.

**Action** : 🚫 Ignoré. Corriger ici seul créerait une divergence avec le patron prescrit sur tout le projet. À traiter globalement si jamais, hors story.

### #4 — Anti-collision intra-capacité
**Sévérité** : 🟡 · **Fichier** : `tests/Feature/Migrations/CapabilitiesSchemaAndSeedTest.php:1564`

**Constat (review opus)** : la garde `array_unique($lotCapabilities)` attrape deux capacités différentes partageant une identité, mais collapse un doublon d'identité `{hive|path|name}` au sein d'une même capacité (absent de ce lot, mais non couvert).

**Action** : ✅ Corrigé. Ajout d'une assertion sur les occurrences BRUTES (`array_count_values`) : aucune capacité du lot ne porte deux fois la même identité. Verrouille les futurs lots. Tests : 41/41 (834 assertions).
