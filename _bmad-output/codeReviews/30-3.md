## Détail des problèmes

### P1 + M1 — Robustesse du listener et de la levée de verrou

**Sévérité** : 🟠
**Fichier(s)** : `app/Listeners/ReconcileImposedWorkstationGroups.php`, `app/Services/ControlHub/ImposedWorkstationGroupReconciler.php` (`releaseDeImposedGroups`)

**Constat initial (review)** :
`releaseDeImposedGroups()` itère sans try/catch par groupe (asymétrie avec la boucle principale protégée). Un `save()` qui échoue remonte jusqu'à `ingest()`.

**Avis Opus** (pertinence 3) :
Vérifié : `ControlHubContractChanged` est dispatché **hors transaction, après commit** (`ControlHubContractIngestionService::ingest()` l.148-150), et le listener est **synchrone sans try/catch**. Donc toute exception de `reconcile()` (release, mais aussi `Log`, contention DB) provoque un **HTTP 500 alors que l'ingestion est déjà committée**. Aggravant : une ré-ingestion identique étant un no-op idempotent, **aucun event n'est re-dispatché** → la réconciliation échouée n'est jamais rejouée automatiquement. M1 généralise P1 : le vrai défaut est l'absence de garde dans le listener.

**Action** : corrigé automatiquement — try/catch + `Log::error` dans `handle()` (la réconciliation ne doit JAMAIS faire échouer une ingestion committée) ET try/catch par groupe dans `releaseDeImposedGroups()` (symétrie avec la boucle principale).

### P3 + P5 — Exit code de la commande & race check-then-act

**Sévérité** : 🟠 / 🟡
**Fichier(s)** : `app/Console/Commands/ReconcileImposedWorkstationGroups.php`, `app/Services/ControlHub/ImposedWorkstationGroupReconciler.php`

**Constat initial (review)** :
P3 : la commande retourne toujours `SUCCESS` même si `errors != []` → un orchestrateur ops ne détecte pas l'échec partiel. P5 : `findByName→createGroup` non atomique → fausse erreur en concurrence (event + commande).

**Avis Opus** (P3 pertinence 2, P5 pertinence 1) :
Doublon réel **impossible** (index `UNIQUE` sur `name` l.74 du schéma unifié + `validateGroupData()`). Pire cas P5 = une entrée `errors[]` bénigne. **Interaction** : corriger P3 (exit FAILURE sur `errors`) transformerait cette erreur de course bénigne en échec ops → il faut traiter P5 conjointement.

**Action** : corrigé automatiquement, couplé — dans le chemin de création, capturer spécifiquement `InvalidArgumentException` / violation d'unicité et re-vérifier l'existence (si le groupe existe désormais → compter `confirmed`, pas `errors`). La commande retourne alors `FAILURE` uniquement sur de vraies erreurs.
