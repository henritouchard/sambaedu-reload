## Détail des problèmes

### #1 — PHPDoc classe : mention `@can('modify-capability')` côté Blade stale

**Sévérité** : 🟡 (sonnet : 🟠 — opus rééquilibre : aucun `@can` n'existe, grep négatif)
**Fichier(s)** : `app/Policies/CapabilityPolicy.php` (intro de classe)

**Constat initial (review sonnet)** : la phrase d'intro (héritée de 29.2) présente `@can('modify-capability', $cap)`
comme consommable côté Blade. Avant 29.8 ce `@can` reflétait droit+verrou ; après, il ne reflète
QUE le verrou. Un futur dev copiant ce pattern créerait une régression UX (bouton visible sans le droit).

**Avis Opus** : vrai mais surévalué par sonnet. La phrase parle de l'enforcement du *verrou* en double
(`@can` ET `Gate::authorize`), ce qui reste exact après 29.8. Aucun `@can` n'existe (grep négatif), et le
bloc 29.8 corrigeait déjà le cadrage plus bas. Sévérité réelle = mineure. Pertinence 2/3.

**Action** : ✅ Corrigé automatiquement — ajout d'un avertissement explicite à l'intro : `@can('modify-capability')`
ne reflète QUE le verrou amont depuis 29.8 ; le contrôle de droit doit être porté par la surface appelante.

### #2 — Cas invité `$user = null` → `true`, non documenté

**Sévérité** : 🟡 (sonnet : 🟠)
**Fichier(s)** : `app/Policies/CapabilityPolicy.php` (PHPDoc `modify()`)

**Constat initial (review sonnet)** : signature nullable → Laravel appelle `modify(null, …)` pour un invité.
Avant 29.8 : `hasPermission(null,…)` → false (invité refusé au niveau policy). Après : `! isCapabilityLocked()`
→ `true` sur capacité non verrouillée. Changement de comportement silencieux, non documenté/testé.

**Avis Opus** : base factuelle correcte (vérifiée : `ChecksPermissions::hasPermission(null,…)` renvoyait bien false).
MAIS non atteignable : `guardCustomize()` fait `auth()->check()`, `guardAdmin()` passe par `Gate::allows('server.admin')`
(false pour invité). C'est la même migration intentionnelle que l'AC#7. Volet **doc** légitime ; un test guest
dédié = over-engineering léger (déjà couvert par l'AC#7). Pertinence 2/3.

**Action** : ✅ Corrigé automatiquement (volet doc) — phrase PHPDoc explicitant le cas invité (`true` voulu, la surface
garde l'authentification en amont). Test guest dédié **non ajouté** (redondant avec AC#7).

### #3 — `actAsNonAdmin()` : stubs Mockery `can()` inertes

**Sévérité** : 🟡
**Fichier(s)** : `tests/Feature/Livewire/Admin/ParcDefaultsUpstreamLockTest.php`

**Constat initial (review sonnet)** : `$user->shouldReceive('can')…` est du code mort : `guardAdmin()` lit
`Gate::allows('server.admin')`, jamais `$user->can()`. Le 403 vient de l'absence de `Gate::before` accordant
`server.admin`. Les stubs donnent une fausse impression de contrôle de l'outcome.

**Avis Opus** : confirmé en profondeur (le before-hook Spatie appelle `checkPermissionTo`, absent du mock d'interface
→ null → Gate false sans passer par `can()`). Stubs inertes mais inoffensifs. Pertinence 2/3.

**Action** : ✅ Corrigé automatiquement — commentaire explicitant que les stubs `can()` sont inertes et que le 403
provient de l'absence de before-hook accordant `server.admin`.

### #4 — Test verrou amont (délégué positif-seul) non discriminant

**Sévérité** : 🟡
**Fichier(s)** : `tests/Feature/Livewire/Parc/CapabilitiesTabCustomizeScopingTest.php::positive_delegate_is_still_blocked_by_upstream_lock`

raison, le test passerait quand même — prouve « 0 écriture » mais pas « le verrou a mordu » (AC#4).

un contrat amont »)` + `assertSet('showOverrideModal', false)` : le test prouve désormais que c'est bien
`authorizeUpstream` qui refuse.
