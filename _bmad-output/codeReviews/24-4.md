## Détail des problèmes

### #1 — UUID SMBIOS hors try/catch : une panne WMI musèle le rapport

**Sévérité** : 🟠
**Fichier(s)** : `agent/windows/SambaEduAgent.ps1:1069`

**Constat (review opus)** :
`$uuid = [string](Get-CimInstance -ClassName Win32_ComputerSystemProduct).UUID` est dans `Invoke-AgentCycle`, hors de tout try/catch local, sous `$ErrorActionPreference='Stop'` + `Set-StrictMode -Version Latest`. Provider CIM dégradé → exception terminante → tout le bloc rapport (collecte drops + POST /report) est sauté alors que la collecte d'état a réussi. « Agent muet » sur une classe de panne WMI réelle en parc — exactement ce que l'AC4/NFR veut éviter. `Build-Report` accepte déjà un UUID vide (`[AllowEmptyString()]`).

**Évaluation orchestrateur** :
Pertinence : 3 — vérifié lignes 49-50 (StrictMode Latest + EAP Stop) et 1040-1086 : tous les autres appels risqués du cycle sont protégés individuellement, celui-ci est le seul orphelin. Le catch de `Start-AgentLoop` rattrape mais avec `outcome='backoff'` et zéro rapport ce cycle. Fix 5 lignes, zéro risque, sur le chemin de la démo.

**Solutions possibles** :
1. try/catch local → fallback `$uuid = ''` + log WARNING, le rapport part (retenu)
2. Déplacer l'appel dans `Build-Report` avec gestion interne

**Action** : corrigé automatiquement (solution 1).

### #2 — `kind = 'identity'` forgeable côté signal posté

**Sévérité** : 🟡
**Fichier(s)** : `app/Models/OverlaySignal.php` (kind string libre), `agent/windows/handlers/Overlay.ps1:115`, `app/Services/Agent/Providers/OverlayStateProvider.php:95-97`

**Constat (review opus)** :
La colonne `overlay_signals.kind` est une string libre. Un signal posté avec `kind='identity'` est traité par `Build-OverlayDocument` comme bloc identité ; le vrai identity synthétique (prepend, premier) gagne, le faux est sauté → le signal disparaît de l'overlay sans erreur ni trace. Impact borné (poster un signal = accès privilégié).

**Évaluation orchestrateur** :
Pertinence : 2 — mécanisme confirmé dans le code (prepend ligne 97 du provider, garde `if ($null -eq $identity)` du handler). Réel mais l'action dépend d'un choix : valider à l'insertion (touche le POC hors story), coercer au provider, ou documenter. Pas de solution unique non ambiguë.

**Solutions possibles** :
1. Reclassement `identity`→`notice` dans `OverlayService::postSignal()` (pattern de validation défensive existant — le message reste visible) (retenu)
2. Coercition dans `OverlayStateProvider::signalCandidates`
3. Documenter le comportement (MVP, accès posting déjà privilégié)

**Action** : corrigé sur arbitrage Henri (solution 1) — constante `KIND_RESERVED_IDENTITY` + reclassement dans `postSignal()` + le provider référence la constante + test `post_signal_reserved_identity_kind_reclassified_as_notice` (OverlayApiV1Test : 18 passed).

### #4 — `[bool](& $handler.Test ...)` fragile au pipeline pollué

**Sévérité** : 🟡
**Fichier(s)** : `agent/shared/ConvergenceEngine.ps1:207`

**Constat (review opus)** :
Si un futur handler `Test` (Epic 27) émet un objet parasite dans le pipeline avant son `return`, le résultat est un array ≥2 éléments et `[bool]` lève (« Cannot convert System.Object[] to Boolean ») → l'item bascule en `error` au lieu de son vrai verdict. Les deux handlers actuels sont propres.

**Évaluation orchestrateur** :
Pertinence : 2 — exact en PS 5.1 (cast explicite `[bool]` d'un array multi-éléments lève). L'échec serait contenu en `error` par le try/catch par item (pas de faux verdict), mais c'est LE point de dispatch générique de tous les handlers à venir et le fix est neutre pour les handlers actuels.

**Solutions possibles** :
1. `$isCompliant = [bool]((@(& $handler.Test $typeItems))[-1])` — ne retenir que le dernier objet émis (retenu)
2. Exiger `| Out-Null` par convention de handler (doc seulement, pas de filet)

**Action** : corrigé automatiquement (solution 1, avec commentaire de contrat handler).

### #5 — TOCTOU `is_file()` → `response()->file()`
