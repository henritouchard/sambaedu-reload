## Tension de conception centrale — TRANCHÉE (design sain)

Le chemin exe **complet** n'est pas dans le payload (préserve AC7) ; l'agent le **re-résout sur le poste** via App Paths
(HKCU/HKLM) puis PATH. **Verdict Opus : design sain, pas un gap fonctionnel.** Le chemin runtime est propre au poste
(archi/langue/version) — le mettre dans le contrat serveur le rendrait faux pour la moitié du parc. Le serveur n'a besoin
que du **basename** pour fabriquer `Applications\<exe>`, et l'agent reste le dernier rempart (abstention D-Henri n°5).

**Seule dette : sémantique.** Le commentaire de migration affirme que le chemin **COMPLET** est « nécessaire à
l'auto-enregistrement (AC6) » — **factuellement faux** : l'agent ne consomme jamais cette colonne, il redécouvre le chemin
lui-même. `applications.executable` devrait être documenté comme « basename suffit, chemin complet ni transmis ni utilisé ».
→ Corrigé en **C8** (commentaire/doc, pas de changement de code).

## Détail des problèmes

### #1 — Visionneuse de photos native incorrecte + natives absentes de Win11

**Sévérité** : 🟠 (1a, rétrogradé de 🔴 par Opus) / 🟡 (1b) — **Pertinence Opus : 2**
**Fichier(s)** : `database/seeders/NativeApplicationSeeder.php`

**Constat initial (Sonnet)** : Visionneuse seedée avec `executable=%SystemRoot%\System32\rundll32.exe` → basename
`rundll32.exe` → générique `"rundll32.exe" "%1"` qui n'ouvre pas une image (manque `shell32.dll,ImageView_Fullscreen`).
`WindowsPhotoViewer` désactivé depuis Win10 1607 / absent Win11 ; WordPad retiré en Win11 24H2. La convention
`source=native` = « toujours applicable » est fausse sur Win11.

**Avis Opus** : Confirme le fond mais sépare deux griefs d'inégale valeur. **(a) `rundll32.exe` est réellement faux** —
vrai défaut de **donnée seedée**, mono-ligne. **(b) WordPad/Photo Viewer absents de Win11** = affirmation factuelle
correcte mais **hors modèle** : le filet D-Henri n°5 (agent s'abstient si ProgId absent) gère exactement ce cas ; c'est
de la **curation produit**, pas un bug de code. Sévérité « critique » surcotée.

**Action** : (a) **corrigé** — retrait de la Visionneuse du seed + commentaire de règle de curation (C1). (b) **tranché
Henri (Q1) = RETIRER** — WordPad aussi retiré du seed (supprimé de Win11 24H2). Catalogue natif = Bloc-notes + Paint.

### #2 — Générique d'une native affiché « applicable » au lieu de « best-effort »

**Sévérité** : 🟠 — **Pertinence Opus : 2**
**Fichier(s)** : `app/Services/Agent/Resolvers/AssociationResolver.php:88-93`,
`resources/views/pages/parc/groups/_partials/associations-tab.blade.php:119`

**Constat initial (Sonnet)** : quand une native ne déclare pas l'extension, le resolver fabrique
`Applications\notepad.exe` avec `source=native` ; l'UI calcule `$available=$a->isNative()`=true → « applicable », alors
que c'est un générique à auto-enregistrer (AC6). Contredit le piège n°7 (native = « présent »).

**Avis Opus** : Confirmé et bien vu. L'AC5 dit littéralement « générique → best-effort » et l'UI ne le matérialise pas
pour le cas natif-générique → faux positif de prédiction. Filet de sécurité aval existe (l'asso ne casse pas), mais l'UI
**sur-promet**. Mitigation : traiter `generic === true` comme « best-effort » indépendamment de `source`.

**Action** : **corrigé** (C2) — détection du générique (`progid` commence par `Applications\`) → badge « best-effort »
distinct, indépendant de `source`.

### #3 — Collision/écrasement de `source` sur ligne partagée inter-parcs (cross-source)

**Sévérité** : 🟡 (rétrogradé de 🟠 par Opus) — **Pertinence Opus : 2**
**Fichier(s)** : `app/Models/FileAssociation.php:179-184`, `app/Services/Agent/Resolvers/AssociationResolver.php:210`

**Constat initial (Sonnet)** : `catalogKey` slugifie le `\` → `catalogKey('.txt','Applications\notepad.exe')` =
`txt_applications_notepad_exe` quelle que soit la source. Si native-générique et WPKG-générique convergent sur le même
basename pour la même extension, `updateOrCreate` écrase `source`/`wpkg_package` pour tous les parcs partageant la ligne.

**Avis Opus** : Confirmé arithmétiquement, mais portée étroite : (1) exige une collision de basename entre native et WPKG
sur une extension qu'aucune ne déclare richement ; (2) le payload aval reste identique (`{identifier, progid, type}`) —
seuls le statut prédictif et `wpkg_package` divergent ; (3) c'est l'invariant catalogue-partagé assumé en 27.3bis.

**Action** : **documenté** (pas de correction). Dette : ajouter un test de l'upsert cross-source + documenter que la clé
ne discrimine pas la source. Scénario étroit, non bloquant.

### #6 — Vecteur hash générique auto-référentiel + commentaire trompeur

**Sévérité** : 🟡 — **Pertinence Opus : 1**
**Fichier(s)** : `agent/shared/handler_associations_test.go:9-16, 52`

**Constat initial (Sonnet)** : le hash `5q6eG+3TpdI=` est calculé par le code Go testé lui-même, pas par une référence
indépendante — vecteur de non-régression interne, pas preuve inter-implémentation.

**Avis Opus** : Exact, mais le commentaire d'en-tête prétend « référence Python indépendante » pour **toutes** les lignes

**Action** : **corrigé** (C7) — commentaire rectifié (distinction réf indépendante vs non-régression interne + renvoi à

### #7 — Pas d'avertissement si l'extension est déjà associée sur le parc

### #M1 — Recomposition cross-parc réactive `is_active` (kill-switch global) — *manqué par Sonnet*

**Sévérité** : 🟡 — **identifié par Opus**
**Fichier(s)** : `app/Services/Agent/Resolvers/AssociationResolver.php:219`

**Constat (Opus)** : `updateOrCreate` force `'is_active' => true` sur update. `is_active=false` est le kill-switch global

**Action** : **corrigé** (C5) — `is_active` posé à `true` uniquement à la création, jamais réécrit sur ligne existante.
