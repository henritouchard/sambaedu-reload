## Détail

### #1 — 🟠 Preuve de précédence incomplète — Pertinence 2 — Corrigé
Les tests DB ne prouvaient la précédence que **config vide**. Par lecture du code, la résolution est if/else strict (aucune fusion possible) — pas de bug réel — mais une régression future réintroduisant un `array_merge` ne serait pas détectée.
**Fix** : test `db_precedence_wins_over_a_conflicting_non_empty_config` — config PLEINE (clés/iss du setUp, ≠ DB) + `ControlHubConnection` active + JWT signé avec la paire CONFIG (accepté sans DB) → **rejeté** car le verifier ne connaît que la clé DB (key-map à 1 entrée, aucune fusion).

### #2 — 🟠 `aud` par défaut = UUID aléatoire si env non figé — Pertinence 2 — Non corrigé (prérequis rollout)
Le comportement est **correct et fail-closed** (rejette, ne bypass pas). Le risque est **opérationnel** (provisioning). Ajouter un garde `doctor`/artisan est une story d'infra à part entière (hors périmètre 39.3, cf. dette provisioning `SE4FS_INSTANCE_ID` déjà connue). **Décision** : ne pas modifier le code (le fail-closed est le bon comportement) ; **remonter comme prérequis de déploiement à Henri** (synthèse epic). Déjà documenté en docblock de `expectedAud()`.

### #3 — 🟡 Bascule DB→config silencieuse — Pertinence 1 — Suivi
Seul un re-handshake complet omettant `idp_federated` réécrit les colonnes à `null` (le heartbeat/renew ne les touche pas) → scénario rare, non automatique. Ajouter un log de source + WARNING sur changement toucherait le chemin de sécurité `verify()` pour un gain d'observabilité 🟡 ; jugé disproportionné en correction de review. **Tracé comme suivi** (candidat à une story d'observabilité si le besoin émerge).

### #4 — 🟡 `empty()` sur `hasFederatedIdp()` — Pertinence 2 — Corrigé
`!empty($this->idp_kid)` traiterait la chaîne `"0"` comme vide → repli silencieux config alors que la colonne porte une valeur.
**Fix** : comparaison stricte `!== null && !== ''` sur les 3 colonnes. Portillon de toute la précédence DB>config → fail-closed net.

### #5 — 🟡 Commentaire obsolète — Pertinence 2 — Corrigé
`config/federated_auth.php` disait encore « Fallback dynamique sur `sambaedu.se4fs_name` ». **Fix** : commentaire mis à jour → `controlHub.se4fs.instance_id` (Story 39.3).

### #6 — 🟡 Double `current()` par `verify()` — Pertinence 1 — Suivi
`expectedIss()` et `buildKeyMap()` appellent chacun `ControlHubConnection::current()` (2 requêtes/login fédéré). Refactor « résoudre 1× dans verify() » = risque sur un chemin de sécurité pour un gain perf 🟡. **Non corrigé** (candidat suivi avec #3, même refactor).
