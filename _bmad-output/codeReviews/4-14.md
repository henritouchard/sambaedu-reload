## Détail des problèmes

### #1 — `resolveBareName` non déterministe (+ M3 cohérence du nom nu)

**Sévérité** : 🟠 — **Fichier(s)** : `app/Actions/Groups/MergeLegacyUserGroups.php:239-250`

**Constat initial (review sonnet)** : le `get()` (l.71) n'a pas d'`ORDER BY` ; `resolveBareName` prend la portion nue de la **première ligne préfixée rencontrée**. Sur une base à casse divergente (`Classe_3A` + `Equipe_3a`), le nom nu final est non déterministe en PostgreSQL (ordre physique non garanti) ; la contrainte `UNIQUE name` étant case-sensitive en PG, un sync ultérieur peut tenter un `create` d'un doublon.

**Avis Opus** : pertinence **2**. Vérifié : risque réel mais étroit (suppose une divergence de casse anormale dans les CN AD d'une même classe). **Manqué par sonnet et regroupé ici (M3)** : le service dérive le nom nu via `stripClasseLikePrefix` (`UserGroupService:889`) = `substr($name, strlen($prefix))` sur `['Classe_','Equipe_','PP_']`, **byte-identique** à la migration *à condition de stripper depuis le même CN canonique*. La divergence M3 se réduit donc exactement à ce problème.

**Action** : ✅ Corrigé. `resolveBareName` (1) renvoie le `name` de la ligne nue si présente (= survivante D1), (2) sinon strippe depuis le CN le plus prioritaire (`Classe_` > `Equipe_` > `PP_`), déterministe quel que soit l'ordre SQL et aligné sur `stripClasseLikePrefix`.

### #2 — `PP_` orphelin seul non flaggé

**Sévérité** : 🟠 — **Fichier(s)** : `app/Actions/Groups/MergeLegacyUserGroups.php:285-313`

**Constat initial** : un `PP_<X>` isolé passe par `renameLonelyPrefixedRow`, renommé `X` type `classe`, mais ses membres ne reçoivent pas `is_head_teacher=true`.

**Avis Opus** : pertinence **1**. Cas quasi-théorique (un `PP_` sans classe associée n'existe pas dans un AD legacy sambaedu) ; et le 1er `syncFromAd` post-migration reposerait le flag. Mitigé mais peu coûteux à fermer.

**Action** : ✅ Corrigé. Dans `renameLonelyPrefixedRow`, si le préfixe est `PP_`, les membres de la ligne reçoivent `is_head_teacher=true` (et `head_teachers_flagged` est incrémenté).

### #3 — AC1 non testé

**Sévérité** : 🟠 — **Fichier(s)** : `tests/Feature/Migrations/MergeLegacyUserGroupsMigrationTest.php`

**Constat initial** : aucun test ne charge la migration réelle ; les tables de test sont montées avec `is_head_teacher` déjà présente. Le rétro-remplissage `false` et `down()` ne sont pas exercés.

**Avis Opus** : pertinence **2**. Le rétro-remplissage est garanti par le moteur SQL, mais AC1 est nommé et la migration porte une logique non triviale (ordre colonne→fusion, gardes `hasColumn`).

**Action** : ✅ Corrigé. Test `it_real_migration_adds_column_retrofills_false_and_down_drops_it` : table sans la colonne → `up()` ajoute + rétro-remplit `false` sur une arête préexistante → `down()` retire.

### M1 — Fusion data hors transaction (manqué par sonnet)

**Sévérité** : 🟠 — **Fichier(s)** : `app/Actions/Groups/MergeLegacyUserGroups.php`, `database/migrations/2026_06_25_120000_*`

**Avis Opus** : la fusion par base fait jusqu'à 4 écritures séquentielles hors transaction explicite. Un échec PG à mi-parcours laisse une base partiellement fusionnée (pivots reportés, redondantes non supprimées) — re-run non garanti idempotent. Exécution réelle = geste manuel PG post-merge (D5) → fenêtre de risque réelle.

**Action** : ✅ Corrigé. Chaque base est traitée dans sa propre `DB::transaction(...)` : atomicité par base, les bases déjà fusionnées restent intactes, aucune base laissée à mi-chemin.

Les tables de test montées à la main n'ont pas la FK → simple écart de fidélité test/prod, pas de perte de membre (les membres sont reportés sur la survivante AVANT suppression). Documenté, non corrigé.
