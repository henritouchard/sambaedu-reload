## Détail des problèmes

### #1 + #7 — Bypass `overrides_locked` / `is_active` dans `saveOverride()`

**Sévérité** : 🟠 Important
**Fichier(s)** : `resources/views/pages/parc/groups/_partials/capabilities-tab.blade.php` (`saveOverride()`, computed `editingCapability()`)

**Constat initial (review Sonnet)** : `overrides_locked` n'est contrôlé que dans `openAdd()` et la
computed `addableCapabilities()` (front). `editingCapabilityId`/`isEditing` sont des propriétés
publiques Livewire (hydratées depuis le client) ; `saveOverride()` charge la capacité via la computed
`editingCapability` (`Capability::find()` brut, sans filtre) puis upsert `capability_assignments`.
Un client peut `$wire.set('editingCapabilityId', <id_gelée>)` + `$wire.call('saveOverride')`.

**Avis Opus** : **Confirmé par preuve** (deux probes jetables) — override écrit (a) sur capacité
**gelée**, (b) sur capacité **inactive**. Pertinence **3**. Nuance : le composant entier est gaté
`app.customize` → pas une élévation de privilège, mais une **violation d'invariant métier** (le gel
n'est pas opposable) + override inerte sur capacité inactive. Le garde ne pouvait pas vivre seulement
côté front. `#7` (is_active) est le jumeau, même garde.

**Solution appliquée** : garde serveur dans `saveOverride()` — recharger la capacité avec
`->where('is_active', true)` ; refuser un **nouvel** override sur une capacité gelée, en dérivant
« nouvel override » de l'**existence en base** (`capability_assignments`), PAS du flag client
`isEditing` (lui aussi mutable). Une capacité gelée déjà overridée reste éditable (re-convergence) ;
une capacité gelée sans override ne peut pas en recevoir. 2 tests ajoutés (gelée+nouveau refusé via
wire:call direct ; inactive refusée).

### #2 — On-only override `off` = no-op silencieux

**Sévérité** : 🟡 Mineur (UX) — **design, pas bug**
**Fichier(s)** : `database/migrations/2026_06_18_100300_seed_capabilities_iso_lot.php`, `capabilities-tab.blade.php`

**Constat initial (review Sonnet)** : 4 capacités on-only exposent `options=[on,off]` ; un `off`
saisi est validé, persisté, mais ignoré à la compilation (le Broadcast `on` gagne) — sans feedback.

**Avis Opus** : Pertinence **2**, **mais re-qualifié : ce n'est pas à corriger côté compilation**
(le test `on_only_map_emits_nothing_when_effective_value_is_off` verrouille ce comportement = D5,
piège n°5). Le vrai problème est le **seed/UI** qui propose `off`.

**Décision Henri (2026-06-18)** : « si on peut mettre *on*, on doit pouvoir mettre *off* » → la racine
est la `spec` **on-only**, pas l'UI. Fix appliqué : les 4 capacités dont un état « off » a un sens
registre réel deviennent **symétriques** — `off` réécrit la valeur qui réactive la fonctionnalité
(`DisableWindowsConsumerFeatures`/`DisableSoftLanding`→0, NetCache `No*`→0 & `Enabled`→1,
`TurnOffWindowsCopilot`→0, OneDrive `IsPinnedToNameSpaceTree`→1). **`windows_updates_managed`** reste
la **vraie exception on-only** (un « off » du bundle = retirer ~34 clés = verbe `delete`, hors MVP
piège n°6) → son option « off » trompeuse est **retirée** (`options=[on]` « Géré »). 2 tests de seed
ajoutés (symétrie ; WU managed-only).

**Action** : ✅ corrigé (seed + tests).

### #4 — `typedValue` : `null` en spec → 0 (DWORD) silencieux

**Sévérité** : 🟡 Mineur (défensif)
**Fichier(s)** : `app/Services/Agent/Providers/AbstractCapabilityStateProvider.php` (`typedValue()`)

**Constat initial (review Sonnet)** : une `spec` portant `value:null` produirait un DWORD `0`
(EnableLUA `0` = UAC OFF) silencieusement.

**Avis Opus** : Pertinence **1.5**. **Aucune clé du lot seedé n'a `value:null`** → robustesse
défensive pour seeds futurs, pas un défaut du livrable.

**Action** : **non corrigé** — risque théorique. Si Henri veut durcir, lever une exception sur `null`
résolu pour un type numérique (au lieu de `0` silencieux). Noté pour 27.13 (nouveaux mécanismes).

### #8 — `array_is_list([]) === true` → MULTI_SZ vide (trouvé par Opus)

**Sévérité** : 🟡 Mineur
**Fichier(s)** : `app/Services/Agent/Providers/AbstractCapabilityStateProvider.php` (interpréteur), `docs/agent/state-providers.md`

**Constat (Opus)** : `array_is_list([]) === true` → une `spec` future portant `value:[]` avec
`type=REG_MULTI_SZ` serait **émise** (MULTI_SZ vide), pas « cesser de gérer ». Le piège n°5 ne couvre
pas ce coin. Aucune clé du lot ne le déclenche aujourd'hui.

**Solution appliquée** : note dans `state-providers.md` — un littéral liste vide `[]` = clé gérée à
vide ; pour « cesser de gérer », utiliser une map sans la valeur effective (jamais `[]`).
