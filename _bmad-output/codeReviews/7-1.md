## Détail des problèmes

### #1 — Gate serveur manquante sur `addMachines` / `removeMachine` / `deleteGroup`

**Sévérité** : 🔴 Critique
**Fichier(s)** : `resources/views/pages/parc/groups/[id]/index.blade.php:143-172, 1084-1100`

**Constat initial (review)** :
Aucune de ces 3 méthodes Livewire n'appelle `Gate::allows()` / `authorize()`. Seul `loadGroup()` teste `Gate::allows('view', $this->group)` à l'entrée. Un user avec uniquement `computer.view` scopé passe la porte, et peut ensuite appeler ces méthodes via un Livewire event forgé (devtools).

**Avis Opus** :
Pertinence 3. Confirmé au mot près. Le service `WorkstationGroupService::deleteGroup / bulkAddMachinesToGroup / removeMachineFromGroup` ne vérifie rien non plus. Scénario d'exploitation : un délégué qui outrepasse son périmètre — exactement ce que l'AC3 interdit. Les policies `update-workstationGroup` et `delete-workstationGroup` existent déjà dans `WorkstationGroupPolicy.php:73-84`, il suffit de les câbler.

**Solutions possibles** :
1. Ajouter `Gate::authorize('delete-workstationGroup', $this->group)` sur `deleteGroup()`, et `Gate::authorize('update-workstationGroup', $this->group)` sur `addMachines()` / `removeMachine()`.

**Action** : corrigé automatiquement.

### #4 — Absence de transaction grant + audit, échec swallowed

**Sévérité** : 🟠 Important
**Fichier(s)** : `app/Services/PermissionService.php:113-165, 174-215, 225-265` + `app/Services/DelegationHistoryService.php:71-84`

**Constat initial (review)** :
Pas de `DB::transaction()` englobant. `DelegationHistoryService::log()` catch `Throwable`, log `error`, retourne `null`. L'appelant `PermissionService` ne teste pas le retour null. L'AC5 dit "l'échec audit ne doit pas silencieusement laisser passer" — contradictoire avec l'implémentation best-effort assumée.

**Avis Opus** :
Pertinence 2. Le choix design (audit best-effort) est cohérent avec "un grant réussi ne doit pas être rollback par un audit KO". Une transaction ferait l'inverse (rollback). **Vrai trou** : quand `log()` retourne null, rien ne remonte côté UI (l'AC5 mentionnait "toast admin").

**Solutions possibles** :
1. **(A)** Transaction stricte : `DB::transaction()` + rethrow dans `log()`. Change la sémantique (grant KO si audit KO).
2. **(B)** Best-effort + alerte : détecter retour null, émettre `Log::warning` + toast warning côté Livewire. Mettre à jour l'AC5 pour refléter ce choix.

**Action** : en attente décision utilisateur (§Questions).

### #5 — `applyDelegations` / `applyRoles` / `applyPermissions` sans `user.delegate`

**Sévérité** : 🔴 Critique
**Fichier(s)** : `resources/views/pages/users/_partials/rights-drawer.blade.php:289-377`, `routes/web.php:50`

**Constat initial (review)** :
AC1 spécifie "admin SER avec `user.delegate`". Les 3 méthodes Livewire n'ont aucun guard serveur. Route `/rights-management` = middleware `sambaedu.auth` seulement, pas `sambaedu.admin`.

**Avis Opus** :
Pertinence 3. **Escalade de privilège complète** — le plus grave du lot, sous-évalué par Sonnet en "Important". Tout user authentifié peut forger `Livewire.dispatch(...)` et s'auto-accorder `SambaRole::SuperAdmin` via `applyRoles()`, ou toutes les perms sur toutes les salles via `applyDelegations()`. La permission `user.delegate` existe dans l'enum mais n'est **jamais** testée en code hors conversion bitmask.

**Solutions possibles** :
1. Middleware `can:user.assign.right` (ou dédié `user.delegate`) sur la route `/app/rights-management`.
2. `abort_unless(Gate::allows('user.assign.right'), 403)` au début de `open()`, `applyRoles()`, `applyPermissions()`, `applyDelegations()`.
3. Enrober boutons dans `users-table.blade.php` / `dropdownUserActions.blade.php` avec `@can`.

**Action** : corrigé automatiquement.

### #A — `ensureEloquentUser()` crée user fantôme sans check AD

**Sévérité** : 🔴 Critique
**Fichier(s)** : `resources/views/pages/users/_partials/rights-drawer.blade.php:387-401`

**Constat initial (second avis Opus)** :
`ensureEloquentUser()` crée un `EloquentUser` minimal (`login`, `role='autre'`, `is_active=true`) sans vérifier que le login existe dans l'AD. Un admin peut injecter n'importe quel login dans `selectedUsers` → création d'un user fantôme en DB SQL. Impact aggravé par l'absence de guard du #5 (avant correction #5, n'importe qui exploitait ce vecteur).

**Avis Opus** :
Pertinence 3. Vecteur immédiat pré-correction #5. Post-correction #5, seul un admin peut le déclencher, réduit la sévérité mais reste une dette : création d'enregistrements DB orphelins.

**Solutions possibles** :
1. Vérifier l'existence du login dans l'AD avant `EloquentUser::create()` — si absent, skip + toast warning.
2. Ou requérir que le login vienne d'une recherche AD validée en amont (plus gros refactor).

**Action** : corrigé automatiquement (check AD minimum).
