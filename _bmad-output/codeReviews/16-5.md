### #2 — `doToggleDisabled`/`Enforced` : pas de rollback

**Sévérité** : 🟠
**Fichier(s)** : `resources/views/pages/app/gpo/[guid]/links/index.blade.php`

**Constat initial (review)** :
```php
$this->gpoService->removeLink($ouDn, $this->guid);
$this->gpoService->setLink($ouDn, $this->guid, enforce: ..., disable: $newDisabled);
```
Si `removeLink` réussit puis `setLink` échoue (timeout, ACLs), le lien est définitivement supprimé. Toast erreur affiché mais état AD régressé. `loadAll()` n'est PAS rappelé après catch → UI désynchronisée.

**Avis Opus** :
Pertinence 3/3 — risque réel en prod. Soit ajouter try/catch local avec re-tente `setLink` avec flags initiaux, soit appeler `loadAll()` dans tous les cas.

**Solutions possibles** :
1. Try/catch local avec rollback re-setLink avec flags d'origine (pattern `reorderLinks`).
2. Appeler `loadAll()` même en cas d'erreur dans `confirmPendingAction`.

**Action** : ✅ Corrigé automatiquement — combinaison des 2 (rollback + refresh systématique).

### #3 — Heuristique idempotence `'object class violation'`

**Sévérité** : 🟠
**Fichier(s)** : `app/Gpo/Services/GpoService.php`

**Constat initial (review)** :
`looksLikeIdempotentLinkError` matche `'object class violation'` (erreur LDAP générique de schéma, pas un signe de lien déjà existant). Idem `'no such'` qui matche `'no such attribute'` — vrais échecs traités comme succès idempotents.

**Avis Opus** :
Pertinence 2/3 — risque pratique faible (regex amont filtre), mais code défensivement faux. Recommandation : retirer `'object class violation'`, conserver seulement `'already'` / `'gplink already'` pour le link, et restreindre l'unlink à `'no such gp link'`.

**Solutions possibles** :
1. Retirer `'object class violation'` + restreindre les patterns.
2. Documenter en TD-16.5-4 la fragilité résiduelle.

**Action** : ✅ Corrigé automatiquement (patterns restreints) + TD-16.5-4 ajoutée.

### #4 — Comptage postes : sous-OU + wildcards SQL

**Sévérité** : 🟠
**Fichier(s)** : `resources/views/pages/app/gpo/[guid]/links/index.blade.php`, `resources/views/pages/app/gpo/[guid]/index.blade.php`

**Constat initial (review)** :
- `ad_dn ILIKE '%,<OU_DN>'` matche les postes des sous-OUs (faux positifs scope)
- Si `$dn` contient `%` ou `_`, wildcards SQL non échappés → matches erratiques

**Avis Opus** :
Pertinence 3/3 sur wildcards (vrai bug défensif) / 2/3 sur sous-OU (sémantique débattable — peut être considéré comme correct vu héritage GPO).

**Solutions possibles** :
1. Wildcards : `str_replace(['%', '_'], ['\\%', '\\_'], $dn)` avant ILIKE.
2. Sous-OU : documenter explicitement dans TD-16.5-2 OU restreindre via regex DN (coûteux).

**Action** : ✅ Corrigé automatiquement (wildcards échappés) + TD-16.5-2 enrichie (scope sous-OU documenté). Question Henri ouverte pour confirmer le scope voulu.
