## Détail des problèmes

### #1 — `canForceReevaluation` non `#[Locked]` (élévation privilège Livewire)

**Sévérité** : 🔴 Critique
**Fichier(s)** : `resources/views/pages/wpkg/deployments/[workstation]/index.blade.php:38,51,88`

**Constat initial (review)** : La propriété publique `$canForceReevaluation` est évaluée une seule fois dans `mount()` et sérialisée en clair dans l'état Livewire. La méthode `forceReevaluation()` re-lit la propriété sérialisée au lieu de re-vérifier `Gate::allows()`. En Livewire v3, les propriétés publiques non `#[Locked]` peuvent être modifiées via wire protocol forgé.

**Avis Opus (pertinence 3)** : Confirmé ligne 38 : `public bool $canForceReevaluation = false;` sans `#[Locked]`. Ligne 88 dans `forceReevaluation()` : `if (! $this->canForceReevaluation)` — la garde lit la propriété publique. Mitigant : l'event final `WorkstationManualReevaluationRequested` ne porte pas de droit user, donc l'impact reste limité à régénération INI (pas de RCE, pas de rotation secret). Reste sérieux pour un produit avec compliance.

**Solutions possibles** :
1. (Simple) `#[Locked] public bool $canForceReevaluation;` — pattern déjà utilisé dans `pages/users/[login]/index.blade.php:25`.
2. (Robuste) Supprimer la propriété et appeler `Gate::allows('wpkg.assign')` directement dans `forceReevaluation()`.
3. (Défense en profondeur — recommandé) Combiner les deux : `#[Locked]` + double-check `auth()->user()?->can('wpkg.assign')` dans `forceReevaluation()`.

**Action** : ✅ corrigé automatiquement (option 3).

### #12 — `WpkgDashboardQueryService::profileAggregates()` jointure `orOn` + `where` (potentiel over-count)

**Sévérité** : 🟠 Important
**Fichier(s)** : `app/Wpkg/Deployment/Services/WpkgDashboardQueryService.php:186-193`

**Constat (manqué Sonnet, repéré second avis Opus)** : Dans la jointure `workstations w`, le `$join->on(function ($q): void { $q->on('w.id', '=', 'apw.workstation_id')->orOn('w.id', '=', 'wgw_p.workstation_id'); })` combine ensuite `->where('w.status', '=', 'active')->whereNull('w.archived_at')`. Selon la grammar Laravel, `orOn` peut sortir la condition `where` du status (parens manquantes selon precedence). Risque : postes `archived` comptabilisés dans certains profils.

**Impact** : KPI faussé sur les agrégats par profil (over-count).

**Solutions possibles** :
1. Wrapper la condition status/archived dans un `->where(function ($q) { ... })` explicite.
2. Utiliser un UNION de deux jointures (workstation_ids ∪ group_ids) plus lisible.

**Action** : ⏳ à corriger automatiquement après vérification SQL générée + test rapide d'over-count.
