## Détail des problèmes

### #1 — Rotation multi-kid non réalisable par simple `.env`

**Sévérité** : 🟠 Important
**Fichier(s)** : `handoff-federated-login-controlhub.md` §4 ; `config/federated_auth.php:71-75`

**Constat initial (review sonnet)** :
Le doc §4 affirme la rotation multi-kid « sans coupure » comme faisable, mais la config ne construit la map `jwt.keys` qu'avec une seule paire d'env. Provisionner deux kids exige d'éditer `config/federated_auth.php`.

**Avis Opus** : pertinence **3**, plus grave que décrit. Le bloc `keys` (l.71-75) est structurellement **mono-entrée**. Le doc transforme une intention d'archi (M1 future) en capacité livrée, à trois endroits dont deux induisent directement l'intégrateur en erreur (table §4 + point « les deux clés valides dans la map »). C'est le seul point susceptible de **faire échouer une rotation en prod**. **Must-fix.**

**Solution appliquée** : §4 reformulée — la rotation multi-kid est **prévue mais nécessite au MVP une édition de `config/federated_auth.php`** (la map `jwt.keys` est mono-entrée via `.env`), pas un simple changement de variable. Note explicite ajoutée.

**Action** : corrigé automatiquement.

### #M1 — `active_kid` tu / rôle du `kid` à clarifier

**Sévérité** : 🟠 Important
**Fichier(s)** : `handoff-federated-login-controlhub.md` §4, §2.1 ; `config/federated_auth.php:64-66`

**Constat (manqué par Sonnet, relevé par Opus)** :
La config expose `jwt.active_kid` (informatif). Le commentaire de config est explicite : « le verifier accepte tout kid présent dans `keys` » — donc le `kid` du header sélectionne la clé par **présence dans la map**, sans devoir égaler `active_kid`. Le doc ne le disait pas, ce qui renforçait la confusion sur la rotation (#1).

**Solution appliquée** : §4 précise qu'`active_kid` est **informatif** et que la sélection de clé se fait par **présence du `kid` dans `keys`**.

**Action** : corrigé automatiquement.

### #2 — Cible de redirection : `intended()`

**Sévérité** : 🟡 Mineur
**Fichier(s)** : `handoff-federated-login-controlhub.md` §1, §3 ; `FederatedLoginController.php:132`

**Constat (sonnet)** : le code fait `redirect()->intended(route('app.dashboard'))` ; `app.dashboard` n'est que le fallback.

**Avis Opus** : pertinence **1**. Le 302 est correct ; sans URL `intended` pré-mémorisée (cas nominal d'un POST cross-site fédéré), la cible EST `app.dashboard`. Détail interne SE5 sans impact sur ce que controlHub produit. Nice-to-have.

**Solution appliquée** : §1 et §3 précisent « (ou l'URL `intended` si une était mémorisée) ».

**Action** : corrigé automatiquement.

### #3 — Atomicité de la consommation du `jti`

**Sévérité** : 🟡 Mineur
**Fichier(s)** : `handoff-federated-login-controlhub.md` §1 ; `FederatedLoginController.php:89-112`

**Constat (sonnet)** : `consumeOnce` est dans le même `DB::transaction()` que le provisioning ; un rejeu rollbacke tout.

**Avis Opus** : pertinence **1**. L'ordre décrit (« en dernier, après provisioning ») est vrai ; seule l'atomicité n'était pas dite. Bon comportement à documenter (protège l'idempotence du retry légitime). Nice-to-have.

**Solution appliquée** : §1 précise que provisioning + consommation `jti` sont **dans une même transaction** (un rejeu rollbacke le provisioning, le `jti` n'est pas brûlé → retry légitime possible).

**Action** : corrigé automatiquement.
