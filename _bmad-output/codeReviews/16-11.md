## Détail des problèmes

### #1 — BOOTSTRAP_TOKEN jamais transmis au script de migration complet

**Sévérité** : 🔴 Critique
**Fichier(s)** : `resources/views/auth/v1/bootstrap-fragment-cmd.blade.php`, `bootstrap-fragment-sh.blade.php`, `bootstrap-cmd.blade.php`, `bootstrap-sh.blade.php`

**Constat initial (sonnet)** :
Le fragment télécharge et exécute le script complet (`bootstrap.cmd` / `bootstrap.sh`). Le script complet utilise `X-Bootstrap-Token: $env:BOOTSTRAP_TOKEN` (Win) ou `${BOOTSTRAP_TOKEN:-}` (Linux). Or, le fragment ne définit/exporte pas BOOTSTRAP_TOKEN. Conséquence : 100% des enrolls réels échoueront 401 `bootstrap_token.missing`.

**Avis Opus** : Pertinence 3 — confirmé après lecture. Aucun mécanisme caché ne pose la variable. Le legacy `applications.php` ne le pose pas dans l'env du process appelant.

**Solutions possibles** :
1. Le fragment récupère un token md5 frais avant d'invoquer le script complet (`set BOOTSTRAP_TOKEN=<id-md5>` via curl à `applications.php?uuid=…&os=…` qui pose le contexte et renvoie le token dans la réponse).
2. Le middleware `InjectBootstrapFragment` injecte directement le token via une substitution Blade (il a accès au contexte APCu).
3. Documenter explicitement comme gap Phase 3+ et adapter les smoke tests QA.

**Action** : ✅ Corrigé Q1.b (2026-05-18) — option fallback retenue : le middleware `mintBootstrapToken($uuid)` génère un md5 frais et pose `apcu_store('apps.<token>', ['uuid' => $uuid, ...], 1800)`. Le placeholder `###_BOOTSTRAP_TOKEN_###` dans les templates Blade est substitué juste avant injection. Le fragment fait `set "BOOTSTRAP_TOKEN=<token>"` (Win) ou `export BOOTSTRAP_TOKEN="<token>"` (Linux) avant le curl du script complet. 3 tests ajoutés.

### #2 — Refresh schedulé (schtasks / systemd) n'envoie pas le `refresh_token` en body

**Sévérité** : 🔴 Critique
**Fichier(s)** : `resources/views/auth/v1/bootstrap-cmd.blade.php:82-87`, `bootstrap-sh.blade.php:121-131`

**Constat initial (sonnet)** :
Tâche planifiée fait POST `/refresh` sans body. `EnsureRefreshToken:52` rejette 400 `refresh.missing`. Les postes migrés perdront leurs JWT à expiration (10h access / 30j refresh).

**Avis Opus** : Pertinence 3 — confirmé. Le middleware lit `refresh_token` depuis le body JSON, regex 64 hex.

**Solutions possibles** :

2. Endpoint serveur dédié servant ce script (cohérent avec `bootstrap.{cmd,sh}`).

**Action** : ✅ Corrigé Q1.c (2026-05-18) — option 1 retenue (script inline déposé par le bootstrap, pas de nouveau controller). Les scripts refresh locaux POST `/refresh` avec body JSON `{"refresh_token": ...}`, parsent la réponse, ré-écrivent tokens (DPAPI Protect Win / écriture atomique auth.json Linux). 4 tests Feature ajoutés.

### #3 — UUID case-sensitivity Windows uppercase vs APCu lowercase

**Sévérité** : 🟠 Important
**Fichier(s)** : `app/Auth/V1/Services/LegacyBootstrapTokenValidator.php:177`, `app/Auth/V1/Http/Middleware/RequireBootstrapToken.php:108-122`

**Solutions possibles** :
1. Normaliser `strtolower($candidate)` dans `extractDeclaredUuid` ET `payloadMatchesUuid`.
2. Ajouter test `isvalid_with_uppercase_declared_uuid_against_lowercase_context_matches`.

**Action** : ✅ Corrigé automatiquement.

### Opus-#A — Le `uuid` n'est JAMAIS posé dans le contexte APCu legacy

**Sévérité** : 🔴 Critique BLOQUANT
**Fichier(s)** : `app/Gpo/Services/ApplicationScriptsGenerator.php:193-231`

**Avis Opus (finding original)** :
Lecture du code Story 16.7 : l'`$info` POSÉ en APCu via `$this->contextWriter->write($id, $info, 1800)` (ligne 225) ne contient PAS la clé `uuid`. Ligne 230 `$info['uuid'] = $uuid` est ajouté **APRÈS** le write — donc l'enrichissement n'est que dans la valeur retournée à l'appelant, pas dans le cache APCu. Même comportement en cas de cache hit.

Le cadrage SM D-Q4 affirme « tous les payloads `apps.$id` posés par `ApcuAppContextWriter` portent `uuid` » — **factuellement faux**. La docstring `ApcuAppContextWriter:35` liste `uuid` comme **passthrough**, mais il faudrait encore que le caller le passe ; or `ApplicationScriptsGenerator` ne le fait pas.

**Conséquence** : si #1 est corrigé (token transmis), le validator 16.11 entrera dans `payloadMatchesUuid`, ne trouvera pas la clé `uuid`, retournera `false` → 401 `bootstrap_token.invalid` (ou `uuid_mismatch` selon le path). **100% des enrolls 16.11 échouent même après fix #1**.

**Solutions possibles** :
1. Modifier `ApplicationScriptsGenerator:193-225` pour mettre `'uuid' => $uuid` dans `$info` AVANT `contextWriter->write()`. Coût : 1 ligne. Vérifier que `AppContext::fromApcuArray` (Story 4.8) ne casse pas.
2. Escalader D-Q4 fail-closed — accepter le mode dégradé (sans uuid check). Court-circuite Q4 mitigation.
3. Extraire l'uuid d'une autre source (lookup `workstations` Eloquent par hostname).

**Action** : ✅ Corrigé Q1.a (2026-05-18) — option 1 retenue. `$info['uuid'] = $uuid` posé AVANT `$this->contextWriter->write()`. Le path cache hit ré-écrit le payload en APCu si `uuid` manque (migration douce). Docstring `ApcuAppContextWriter` mise à jour. `AppContext::fromApcuArray` non impacté (la clé `uuid` n'est pas dans le set strict mais dans `raw[]` passthrough — ne casse rien côté lecteur Story 4.8). Aucune modification de test 16-7 nécessaire.
