## Questions en attente

> Questions nécessitant une réponse de l'utilisateur avant de pouvoir avancer.

1. **Périmètre des délégués sur création/réattachement (renvoi #9 → #11)** — un délégué scopé sur `salle_a` peut-il *créer* une imprimante et la rattacher à `salle_b` (où il n'a aucune délégation) ? La policy `manage($user, null)` retourne `server.admin` global, donc **de facto** la création est admin-only ; mais le `updatePrinter` permet à un délégué d'éditer une imprimante de `salle_a` et de la **réattacher** à `salle_b` (faille réelle). Faut-il bloquer les réattachements hors-scope ou les autoriser pour faciliter la délégation transversale ?
2. **Filtre admin "Toutes" : orphans visibles ou non ? (#6)** — actuellement les orphans sont absentes du filtre `all` côté admin (visibles uniquement dans le filtre dédié `orphans`). Comportement intentionnel mais le label "Toutes" est trompeur. Renommer "Présentes dans CUPS" ou inclure orphans dans `all` avec badge ?
3. **Politique de log sur split-brain transactionnel (#5)** — quand CUPS commit puis SER échoue puis rollback CUPS rate, l'imprimante reste orpheline dans CUPS. Faut-il logger en niveau `ERROR` (alerte ops) ou laisser en `WARNING` (audit silencieux) ? Aujourd'hui c'est warning, et `printers:sync` réconciliera.

## Détail des problèmes

### #1 — Fuite `$e->getMessage()` dans toast catch large

**Sévérité** : 🟠
**Fichier(s)** : `resources/views/pages/parc/_partials/printers-tab.blade.php:340`

**Constat initial (sonnet)** :
Dans le catch `\Throwable` de `addPrinter()`, `$this->toastError('Erreur lors de l\'ajout : ' . $e->getMessage())` peut exposer `SQLSTATE[23000]: Integrity constraint violation: 1062 Duplicate entry 'imp_x' for key 'PRIMARY'` ou autres détails internes DB.

**Avis Opus** : pertinence **2**. Risque infosec moindre (contexte authentifié admin/délégué) mais AC5 dit explicitement "aucune StackTrace ne fuite vers l'UI". Les autres `toastError` (lignes 319, 454, 482, 514) utilisent `$e->firstStderrLine()` (CUPS contrôlé) ou message d'`InvalidArgumentException` (contrôlé). Seul le 340 est concerné.

**Solutions possibles** :
1. Toast générique `'Une erreur interne est survenue. Consultez les logs.'` + `Log::error($e)` pour traçabilité.
2. Distinguer `\InvalidArgumentException` (message safe) vs `\Throwable` générique (message masqué).

**Action recommandée** : Option 1.

### #2 — N+1 sur `getJobsCount()` dans `listPrinters()`

**Sévérité** : 🟠
**Fichier(s)** : `app/Services/Print/CupsPrinterService.php:121`

**Constat initial (sonnet)** :
`foreach ($names as $name => $uri) { ... 'jobs_count' => $this->getJobsCount($name) }` exécute 1 `lpstat -o <name>` par imprimante. Pour 20 imprimantes = 22 forks shell. Estimation D10 « < 200 ms pour 50 imprimantes » incompatible (~50 ms × 50 = 2.5s minimum).

**Avis Opus** : pertinence **3** confirmée. 2 + N executions de `proc_open`. Sur parc 50 imprimantes = 52 forks par chargement de page. `lpstat -o` (sans argument) liste **tous** les jobs en attente toutes imprimantes confondues — un seul fork. Format : `<printer>-<jobid>  <user>  <size>  <date>` → `array_count_values` sur `preg_match('/^([^-]+)-/', $line, $m)`.

**Solutions possibles** :
1. Refactorer `listPrinters()` pour appeler `lpstat -o` une seule fois et grouper côté PHP.
2. Rendre `jobs_count` paresseux (chargé à la demande via une action Livewire séparée).

**Action recommandée** : Option 1.

### #3 — `URI_REGEX` accepte `socket://` sans port

**Sévérité** : 🟠
**Fichier(s)** : `app/Services/Print/CupsPrinterService.php:39`

**Constat initial (sonnet)** :
`URI_REGEX = '#^(socket|ipp|ipps|lpd|http|https)://[^\s\'"`$;|&<>\\\\]+$#'` accepte `socket://192.168.1.10` (sans port obligatoire pour socket://) → erreur lpadmin tardive.

**Avis Opus** : pertinence **2**. Pas un risque sécu (escapeshellarg + sudo whitelist couvrent). Risque UX : erreur tardive côté CUPS au lieu de validation Livewire claire.

**Solutions possibles** :
1. `parse_url()` post-regex pour valider host non-vide + port présent pour `socket://`.
2. Ajouter ces payloads dans `maliciousUriPayloads` data-provider pour cataloguer.

**Action recommandée** : Option 1 + ajouter test Unit dans `maliciousUriPayloads`.

### #5 — Test `cups-ok-ser-fail` rollback manquant

**Sévérité** : 🟠
**Fichier(s)** : `resources/views/pages/parc/_partials/printers-tab.blade.php:286-342` + tests Feature absents

**Constat initial (sonnet)** :
Le test `test_add_printer_rolls_back_when_cups_fails` couvre le cas inverse (CUPS échoue d'abord). Le scénario réel du rollback best-effort (CUPS commit → SER fail → rollback CUPS via `deletePrinter`) n'est pas testé. La story phase 7.1 prévoyait `test_add_printer_rolls_back_cups_on_ser_failure` qui n'a pas été implémenté.

**Avis Opus** : pertinence **3** confirmée. Le rollback peut lui-même échouer (Samba reload race, lpadmin verrou) — pas de re-tentative, pas de queue de réconciliation. La fenêtre de drift est documentée comme acceptable mais la **vérification automatique** est manquante.

**Solutions possibles** :
1. Ajouter test Feature `test_add_printer_rolls_back_cups_on_ser_failure` qui mock le `Printer::create` pour throw, vérifie que `CupsPrinterService::deletePrinter` est appelé en cleanup.
2. Tester aussi le cas où le rollback CUPS rate (vérifier qu'un `Log::warning` structuré est émis pour réconciliation par `printers:sync`).

**Action recommandée** : Option 1 + 2.

### #11 — `updatePrinter` permet réattachement cross-scope (faille de sécurité réelle)

**Sévérité** : 🟠
**Fichier(s)** : `resources/views/pages/parc/_partials/printers-tab.blade.php:444-451`

**Constat (Opus, manqué par sonnet localisation)** :
`Gate::authorize('manage-printer', $printer)` valide les rattachements **existants** de l'imprimante, mais pas les **nouveaux** `editWorkstationGroupIds` envoyés par le SFC. Un délégué scopé sur `salle_a` peut éditer une imprimante rattachée à `salle_a` et `sync()` les pivots vers `salle_b` (où il n'a aucun droit).

**Solutions possibles** :
1. Avant le `sync()` du pivot, intersecter `editWorkstationGroupIds` avec `getAuthorizedWorkstationGroups($user)->pluck('id')` ; rejeter les IDs hors scope (soit 403, soit silencieusement filtrés avec toast warning).
2. Bloquer entièrement la modification du rattachement pour les délégués (admin-only sur ce champ).

**Action recommandée** : **Décision produit Henri** (cf. Question 1). Par défaut option 1 (intersection).
**Test** à ajouter : `delegated_user_cannot_reattach_printer_to_unauthorized_group` dans `PrinterPolicyDelegationTest.php` ou `PrintersTabTest.php`.

### #12 — CUPS down + fail-soft → sync marque tout orphan en cascade

**Sévérité** : 🔴 **CRITIQUE**
**Fichier(s)** : `app/Console/Commands/PrintersSyncCommand.php:42` + `app/Services/Print/CupsPrinterService.php:84-93`

**Constat (Opus, manqué par sonnet)** :
Si CUPS daemon est down au moment du cron 03:30, `CupsPrinterService::listPrinters()` retourne `[]` (fail-soft documenté) au lieu de throw. La commande `printers:sync` voit alors "0 imprimantes CUPS" et **marque toutes les imprimantes SER non-orphan comme orphan** (`->update(['orphan' => true])`).

**Cascade utilisateur** :
- Au reboot CUPS, la commande suivante les restaurera (`orphan = false`)
- **Entre-temps** : le scope `forUser` masque les orphans → **les délégués voient liste vide pour leur parc** pendant la fenêtre.
- Si le sync planifié 03:30 tombe pendant une maintenance Samba/CUPS, les utilisateurs arrivent au bureau le matin avec leurs imprimantes "disparues" jusqu'à la sync suivante.

**Solutions possibles** :
1. Ajouter `CupsPrinterService::isHealthy()` (test `lpstat -r` ou `systemctl is-active cups`) ; si KO → `PrintersSyncCommand` skip + log error + alerte.
2. Distinguer `listPrinters()` "vide réel" vs "CUPS down" (exposer le returnCode du `lpstat -s` ou throw `CupsDaemonDownException`).
3. Test : mock `listPrinters` qui throw au lieu de `[]`, vérifier qu'aucune row n'est marquée orphan.

**Action recommandée** : **Décision produit Henri** (cf. Question 3 mais aussi décision technique). Option 2 (distinction explicite) est la plus propre. Test obligatoire.

### #14 — `LC_ALL=C` partiel sur commandes mutantes

**Sévérité** : 🟡

**Constat (Opus, manqué par sonnet)** :
Tous les `lpstat`/`lpinfo` sont préfixés `LC_ALL=C` ✓ (cohérent avec parsing). Mais `lpadmin` (lignes 215/252/283), `cupsenable` (298), `cupsdisable` (312) ne le sont pas. **Solutions possibles** :
1. Préfixer toutes les exec par `LC_ALL=C` pour stabilité.
2. Centraliser dans `RealCommandRunner` un préfixe systématique.

**Action recommandée** : Option 2 (DRY).
