## Détail des problèmes

### #1 — `createFromTemplate()` ignore `$result->warnings` (AC2 non honoré)

**Sévérité** : 🟠 — **Pertinence Opus** : 2/3
**Fichier(s)** : `resources/views/pages/shares/index.blade.php` (`createFromTemplate`)

**Constat initial (review Sonnet)** :
Le `TemplateMaterializationResult` porte `$warnings` (peuplé par `NetworkShareValidator::warnings($share)`), mais l'UI ne l'utilise jamais. AC2 demande explicitement le surfaçage des warnings non bloquants (WG-montage-seul) en `toastWarning`. De plus le chemin de succès se termine par `session()->flash('toast', …)` + redirect : un `toastWarning()` ajouté après dispatch serait perdu, donc le fix passe par le flash.

**Avis Opus** : Réel manquement au contrat AC2, mais **inerte en pratique** — aucune des 4 recettes seedées n'assigne de WG, donc `warnings()` retourne toujours `[]`. Le service les calcule correctement ; c'est l'UI qui les jette. Fix trivial : injecter `$result->warnings` dans le `session()->flash('toast', …)` avant le redirect (l'analyse de Sonnet sur le redirect est juste).

**Action** : ✅ **Corrigé automatiquement.** Les warnings non vides sont annexés au message flashé et basculent le toast en statut `warning` (titre « Répertoire créé (avec avertissements) »). Honore le contrat AC2 et défend les recettes futures, sans risque architectural (reprise exacte du chemin flash existant de 34.2 `deleteShare`).

### #2 — Cardinalité des rôles validée côté service seulement + trou de couverture

**Sévérité** : 🟡 — **Pertinence Opus** : 2/3
**Fichier(s)** : `resources/views/pages/shares/index.blade.php` (`templateRules`), `tests/Feature/Livewire/Shares/SharesFromTemplateTest.php`

**Constat initial (review Sonnet)** :
`templateRules()` ne porte aucune règle Livewire field-level sur `roleSelections`. Une cible requise manquante (ex. `user_to_user` sans `user_b`) remonte en `toastError` générique via `InvalidArgumentException` de `buildAssignmentPlan`, pas en erreur de champ. **Sûr** (rien créé, refus AVANT transaction) mais UX dégradée, et aucun test Feature ne couvre ce cas (seul le niveau service l'était).

**Avis Opus** : Confirmé, sûr, UX dégradée. Le trou de couverture est le point actionnable.

**Action** : ✅ **Corrigé (test + acté).** Ajout du test Feature `missing_required_target_surfaces_toast_error_and_creates_nothing` (cible requise absente → `toastMagic` dispatché, 0 share + 0 pivot créés). La validation field-level Livewire dynamique par rôle est laissée de côté (couplage avec la recette DB, valeur UX marginale vs le toast explicite déjà présent) — la sécurité et la non-création sont prouvées.

### #3 — Requêtes DB redondantes par render

**Sévérité** : 🟡 — **Pertinence Opus** : 1/3
**Fichier(s)** : `resources/views/pages/shares/index.blade.php` (bloc Blade `@php`)

**Constat initial (review Sonnet)** :
`selectedTemplate()` appelée ~3× et `roleCandidates()` ~2× par render (appels imbriqués `templatePreview()` → `roleCandidates()` → `selectedTemplate()`). Chaque appel = requête `WHERE key = ?`. Reco : propriétés `#[Computed]` Volt pour cache par-request.

**Avis Opus** : Confirmé, **impact nul** (table de 4 lignes indexée sur `key`, `roleCandidates` plafonné à 100). Du polish.

**Action** : ❌ **Non corrigé.** Pertinence 1/3, impact runtime nul. La refonte en `#[Computed]` touche la structure du composant Volt (réactivité `wire:model.live`) pour un gain négligeable — laissée de côté pour éviter un risque disproportionné. Note d'amélioration possible si la page évolue.

### #4 — `'letter' => $this->templateLetter` au lieu de `$validated[...]`

**Sévérité** : 🟡 — **Pertinence Opus** : 1/3
**Fichier(s)** : `resources/views/pages/shares/index.blade.php` (`createFromTemplate`)

**Constat initial (review Sonnet)** :
Inconsistance stylistique : `name`/`directory_name`/`label` viennent de `$validated[...]`, mais `letter` de la propriété brute `$this->templateLetter`. Fonctionnellement identique (la validation ne transforme pas la valeur), aucun scénario d'échec.

**Avis Opus** : Confirmé, purement stylistique.

**Action** : ✅ **Corrigé automatiquement.** `'letter' => $validated['templateLetter'] ?? null` (cohérence post-validation avec les autres champs).

### M-1 — Unicité `directory_name` non pré-checkée dans le service _(trouvé par Opus, manqué par Sonnet)_

**Sévérité** : 🟡
**Fichier(s)** : `app/Services/Filesystem/DirectoryTemplateService.php` (`materialize`)

**Constat (Opus)** :
Le service valide format + lettre réservée mais PAS l'unicité de `directory_name` (contrainte présente seulement en DB). En chemin UI c'est couvert par la règle `unique:network_shares,directory_name`. Mais un appel **direct** à `materialize()` (future commande/API) avec un nom déjà pris lève une `QueryException` brute **dans** la transaction (→ rollback, donc pas d'écriture partielle, **sûr**) au lieu de l'`InvalidArgumentException` documentée dans le PHPDoc.

**Action** : ✅ **Corrigé automatiquement.** Pré-check explicite `NetworkShare::where('directory_name', …)->exists()` dans la validation amont du service → `InvalidArgumentException` avec message clair, cohérent avec le contrat PHPDoc et le chemin UI. Tout appelant (UI + direct) obtient désormais le même comportement.

### M-2 — Seeder non-pruning → recettes orphelines _(trouvé par Opus, manqué par Sonnet)_

**Sévérité** : 🟡
**Fichier(s)** : `database/seeders/DirectoryTemplateSeeder.php`

**Constat (Opus)** :
`updateOrCreate` sur `key` ne supprime jamais. Si une recette est retirée de `templates()` dans une version future, sa ligne DB persiste et apparaîtrait encore dans le sélecteur UI (`DirectoryTemplate::all()` sans filtre). Aucun impact pour les 4 recettes figées actuelles.

**Action** : ✅ **Corrigé (test garde-fou).** Ajout du test `db_contains_only_the_canonical_keys_after_seed` qui épingle l'ensemble EXACT des clés en DB après seed — casse si le catalogue dérive. Le **pruning runtime** (`whereNotIn(...)->delete()`) est volontairement **écarté** : il entrerait en conflit avec une future édition d'admin (option C, 34.x) où des recettes custom ne doivent pas être supprimées au re-seed. Le garde-fou par test couvre le risque sans changer le comportement.

### M-3 — Cap 100 candidats + zéro scoping étab (dette 34.2 amplifiée) _(trouvé par Opus, manqué par Sonnet)_

**Sévérité** : 🟡
**Fichier(s)** : `resources/views/pages/shares/index.blade.php` (`roleCandidates`), `app/Services/Filesystem/DirectoryTemplateService.php` (`assertTargetValid`)

**Constat (Opus)** :
Dans un étab fédéré (75 étab), (a) une cible au-delà des 100 premiers alphabétiques est inselectionnable via l'UI ; (b) toute cible visible — y compris cross-établissement — passe la validation serveur (existence seule). C'est la dette 34.2 (Q3 + piège #10), **explicitement documentée** dans le Dev Agent Record. Le multi-select `destinataires` (`direction_to_all`, cardinalité `many`) **amplifie mécaniquement** la surface de grant cross-maille/cross-étab d'un seul geste.

**Action** : ❌ **Non corrigé.** Dette architecturale assumée, héritée de 34.2 (les pickers SQL ne sont pas scopés par établissement car l'AD est banni du chemin SQL — pas de scope étab homogène en SQL). Sa résolution = expansion d'appartenance/scope étab, à rebours du pure-lecture — renvoyée à 34.x avec la fermeture de la collision cross-maille (limitation 34.2 M-A). NOMMÉE, non aggravée structurellement.

## Invariants critiques vérifiés (par les deux reviewers)

- **Socle figé INTOUCHÉ** : `git diff --staged --name-only` ne contient AUCUN fichier de : `NetworkShareService`, `NetworkShareValidator`, `NetworkSharePolicy`, `DrivesStateProvider`, `StateCompiler`, `ShareService`, `agent/**`, `contract-v1`, golden `state.v1.json`, `FROZEN_STATE_HASH`. Pas de bump version agent. Confirmé après corrections.
- **WG-montage-seul (defense-in-depth)** : `respectsMountOnlyInvariant()` appelé en tête de `buildAssignmentPlan()` + `in_array($maille, ALLOWED_ROLE_MAILLES)` par rôle AVANT écriture. Une recette corrompue (maille WG) → `InvalidArgumentException`, jamais de montage-seul masqué. Tests `no_seeded_recipe_grants_a_workstation_group` + `every_recipe_respects_the_mount_only_invariant`.
- **Transaction + collision** : `assertNoLetterCollision($share->fresh())` appelé AVANT commit (audience peuplée via requête DB directe `audienceKeys`, pas de faux négatif) ; collision → rollback complet (0 ligne, testé). Patron `addAssignment` 34.2 fidèlement reproduit.
- **`provision()` hors transaction** : appelé APRÈS commit ; échec = fail-soft (share committé sans dossier + toast), cohérent avec `createShare` 34.2, éditable ensuite.
- **Injection de type impossible** : `assignable_type` vient du `maille` de la recette DB, jamais du payload Livewire ; `roleSelections` ne fournit que des IDs, clés inconnues ignorées.
- **Cohérence `group_type`** : `assertTargetValid` refuse un `UserGroup` du mauvais type (test `group_type_mismatch_is_refused`) → pas de mauvais groupe Unix mappé silencieusement.
- **Zéro AD / LdapRecord / APCu** : aucun import/appel. Postgres-only (NFR7).
