## Détail des problèmes

### #1 — 🟡 Le test UPDATE ne prouve pas le rafraîchissement de `updated_at`

**Fichier** : `tests/Feature/Livewire/Parc/CapabilitiesOverrideAuditTest.php` (`re_editing_an_override_preserves_original_created_at`)

**Constat initial (review)** :
Seul `created_at` était figé dans le passé (`subDays(3)`). `updated_at` conservait sa valeur d'INSERT (= `now()` du test, donc « aujourd'hui »). L'assertion `updated_at > frozenDate(-3j)` était **trivialement vraie même si la branche UPDATE oubliait `'updated_at' => now()'`** — l'AC#1 (« `updated_at` rafraîchi ») n'était donc pas réellement gardé.

**Action** : **Corrigé automatiquement.** `updated_at` est désormais figé à `subDays(2)` (date distincte de `created_at`), et l'assertion vérifie que la ré-édition l'a fait **avancer** au-delà de cette valeur figée (`assertGreaterThan($frozenUpdatedAt, …)`). L'AC#1 est maintenant réellement prouvé.

### #2 — 🟡 Le test INSERT n'asserte pas `updated_at`

**Fichier** : `tests/Feature/Livewire/Parc/CapabilitiesOverrideAuditTest.php` (`inserting_a_new_override_sets_created_at`)

**Constat initial (review)** :
L'AC#2 exige « la ligne est créée avec `created_at` **ET** `updated_at` posés ». Le test n'assertait que `created_at` non nul.

**Action** : **Corrigé automatiquement.** Ajout de `assertNotNull($row->updated_at, …)`.

### #3 — 🟡 Occurrence sœur du même anti-pattern : `queue_task_runs`

**Fichier** : `app/Providers/AppServiceProvider.php:260-273` (handler `Queue::before`)

**Constat initial (review)** :
Le même défaut exact existe ailleurs — `updateOrInsert('queue_task_runs', ['task_uuid'=>…], [… 'created_at' => now()])` pose `created_at` dans les VALEURS. Sur un `task_uuid` déjà présent (retry / re-dispatch), `before` ré-écrase le `created_at` d'origine. Les handlers `after`/`failing` (L.289/315) n'écrivent pas `created_at` → risque circonscrit. `sync_cursors` (UserSyncService:438) est sain.

**Note de scope** : strictement **hors périmètre** de 29.7 (table/domaine différents) — le scope de la story est correctement borné.

**Action** : **Tracé en backlog (story 29-9-ne-pas-ecraser-created-at-queue-task-runs)**, même fix closure iso-29.7. Pas inclus dans 29.7.

### #4 — 🟡 Fragilité `assertSame` chaîne `created_at` (driver-dépendant)

**Fichier** : `tests/Feature/Livewire/Parc/CapabilitiesOverrideAuditTest.php` (`assertSame($frozenDate, $row->created_at)`)

**Constat initial (review)** :
L'égalité compare une chaîne `Y-m-d H:i:s` à la valeur relue brute par le query builder. Robuste en SQLite (cible HÔTE imposée), mais se romprait sur un autre driver (Postgres : microsecondes/`+00`).

**Action** : **Différé.** Faible priorité, tests HÔTE sqlite-only par règle projet ([[project_phpunit_test_env_host_vs_vm]]). Aucun flake réel ici.

### #5 — 🟡 TOCTOU `$hasExistingOverride` (hors tx) vs `$exists` interne

**Fichier** : `resources/views/pages/parc/groups/_partials/capabilities-tab.blade.php:291-347`

**Constat initial (review)** :
`$hasExistingOverride` (lu avant la transaction, pilote l'action d'audit) et le `$exists` recalculé dans `updateOrInsert` sont deux lectures indépendantes pouvant diverger sous concurrence. Effet **bénin** (`created_at` cohérent dans tous les cas), pré-existant, non aggravé fonctionnellement.

**Action** : **Différé (aucune action).** Fenêtre étroite, issue bénigne ; unifier serait du gold-plating (cf. footgun `value` nullable déjà acté en 29.5 #5).
