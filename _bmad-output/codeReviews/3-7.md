### #2 — Pattern catchall `^ipxe/action/` peut intercepter le clonage UDP legacy (hors-scope D3)

**Sévérité** : 🟠
**Fichier(s)** : `config/sambaedu.php:96`

**Constat** :

```php
'^ipxe/action/' => 'gone:action iPXE inconnue ou format invalide - utiliser /ipxe/action/{action} valide',
```

Le legacy `sambaedu/ipxe/clonage.php` et `sambaedu/ipxe/action.php` orchestrent le workflow stateful UDP-multicast (HORS-SCOPE 3.7 selon D3). Ces fichiers utilisent `action.php?action=xyz` (path `ipxe/action.php` — NE matche PAS `^ipxe/action/` car pas de `/` après `action`). 

OK le pattern est en réalité bien restreint (`^ipxe/action/` exige le slash final). Mais le test `it_returns_404_for_action_with_invalid_format` montre que `POST /ipxe/action/RESCUECD` (uppercase, format invalide) tombait en 404 Laravel avant — maintenant en 410 (catchall). Si un poste très ancien terrain (non-mis-à-jour via 16.11) hardcode une URL `POST /ipxe/action/clonezilla_live` mais avec un parseur firmware bogué qui ajoute un suffixe trailing (ex: `/ipxe/action/clonezilla_live/` ou `/ipxe/action/clonezilla_live;jsessionid=...`), la route Laravel ne matche plus → catchall → 410.

Avant 3.7, ce poste aurait été proxié vers le legacy via `direct_legacy_routes ^/ipxe/`. Maintenant, il est bloqué silencieusement → boot KO.

**Pourquoi c'est un problème** :

Régression réelle pour postes terrain qui n'ont pas migré leur firmware iPXE ou qui ont des URL hardcodées avec format non-canonique. La couche `^ipxe/action/` est trop large car elle PRÉCÈDE `direct_legacy_routes` dans l'ordre de check du catchall (block d'abord, proxy ensuite ligne 61 vs ligne 90). Le legacy n'est plus consultable du tout pour ces chemins.

**Solutions possibles** :

1. Restreindre le pattern à `^ipxe/action/[A-Z]` (matche seulement les actions qui ont des caractères invalides définis — uppercase, etc.) → moins de faux positifs.
2. Ajouter dans `allowed_legacy_routes` un pattern de bypass pour `action.php` (legacy `sambaedu/ipxe/action.php` direct route) → mais le pattern actuel `^ipxe/action/` ne capture pas `action.php` donc déjà OK.
3. Accepter le comportement (D10 = cleanup strict Epic 3) et documenter dans Section 16 que les postes terrain doivent être à jour 16.11 pour ne plus appeler les anciens chemins.

**Action recommandée** : Décision Henri requise — Q-H1 question ouverte.

**Correction appliquée (2026-05-22)** : Décision Henri = garder pattern strict (D10 cleanup propre). (1) Commentaire détaillé ajouté `config/sambaedu.php:96` au-dessus de `'^ipxe/action/'` expliquant les conséquences (postes terrain doivent être à jour 16.11) ; (2) docs QA Section 16 — paragraphe « Compat postes legacy » + smoke commands pour valider le comportement avant prod.

**Sévérité** : 🟠
**Fichier(s)** :
- `app/Ipxe/Services/IpxeService.php:789-802` (lit `config('ipxe.se4fs_url')`)
- `app/Ipxe/Services/IpxeActionResolver.php:323-336` (lit `config('ipxe.actions.server_base_url')`)

**Constat** :

Deux méthodes privées `resolveServerBaseUrl(Request $request): string` coexistent dans le namespace `App\Ipxe\Services\` avec :

`IpxeService::resolveServerBaseUrl` :
```php
$configured = (string) config('ipxe.se4fs_url', '');
```

`IpxeActionResolver::resolveServerBaseUrl` (nouveau 3.7) :
```php
$configured = (string) config('ipxe.actions.server_base_url', '');
```

Si Henri définit `IPXE_SE4FS_URL=http://proxy.lan` dans `.env`, le menu maintenance utilisera cette URL, MAIS les actions gparted/hdt/memtest IGNORERONT cette config (clé différente). Comportement incohérent silencieux.

**Pourquoi c'est un problème** :

1. **Bug latent** : si Henri configure un override en prod (proxy LAN custom), il aura des chemins kernel cassés sur gparted/hdt/memtest.
2. **DRY violation** : 2 implémentations à maintenir.
3. **Dette technique** : 8 endroits dans `IpxeService` appellent `$this->resolveServerBaseUrl($request)` → 9e endroit (resolver) avec config divergente.

**Solutions possibles** :

1. Unifier sur une seule clé `ipxe.se4fs_url` ; faire `IpxeActionResolver` lire la même config (= 1 seule implémentation).
2. Extraire la méthode dans un trait/service partagé (`ServerBaseUrlResolver`).
3. Documenter explicitement le choix de 2 clés distinctes (si volontaire — improbable).

**Action recommandée** : Solution 1 — auto-applicable. Unifier sur `ipxe.se4fs_url` et supprimer `ipxe.actions.server_base_url`.

**Correction appliquée (2026-05-22)** : `IpxeActionResolver::resolveServerBaseUrl()` lit désormais `ipxe.se4fs_url` (clé canonique, partagée avec `IpxeService` + `IpxeEnrollmentOrchestrator`). ### #10 — `it_ensures_no_user_variable_in_action_kernel_lines` est un faux positif (regex inefficace pour Blade)

**Sévérité** : 🟠
**Fichier(s)** : `tests/Architecture/IpxeNamespaceTest.php:1209-1241`

**Constat** :

Le test arch D12 vise à empêcher l'injection iPXE en interdisant `{{ $mac }}`, `{{ $uuid }}`, `{{ $workstationName }}`, `{{ $ip }}` dans les lignes `kernel `/`initrd ` des templates 3.7.

Le regex utilisé :
```php
$userVarPattern = '/\$\s*(mac|uuid|workstationName|ip)\b/i';
```

Test sur une vraie ligne `kernel {{ $mac }} foo` :
- `{{ $mac }}` contient `$ mac` après préfixe `$` → matche ? Test direct nécessaire.

Mais la sigil Blade est `{{ $mac }}` — le `$` est PRÉCÉDÉ par `{{` (deux braces + espace). La regex `\$\s*(mac...)` matche bien `$mac` (l'espace après `$` est optionnel via `\s*`). Donc en théorie le regex matche aussi `{{ $mac }}`.

Vérification : `preg_match('/\$\s*(mac|uuid|workstationName|ip)\b/i', '{{ $mac }}')` → matche.

**OK, le test fonctionne**, mais le concept reste fragile :

- Le test passe car les 6 templates 3.7 n'ont AUCUNE de ces variables dans kernel/initrd. ✓
- MAIS la check est uniquement lexicale (string parsing). Si un futur dev utilise `{{ Str::of($mac)->lower() }}` ou `@php $foo = $mac; @endphp` puis `{{ $foo }}`, le test ne détecterait pas l'injection.
- De plus, le regex match `\$\s*ip` qui matche aussi `$ipxe`, `$ipQuery`, etc. → faux positifs potentiels en cas de variable Blade `$ipv6` etc.

Plus subtil encore — `$workstationName` est lu via `\bworkstationName\b`, mais Blade peut aussi avoir une variable nommée `workstation_name` (snake_case). Le test ne couvre que les noms exacts.

**Pourquoi c'est un problème** :

Faux sens de sécurité. Le test est correct pour empêcher la régression évidente, mais ne couvre PAS toutes les voies d'injection. Documentation D6 dans story.md devrait clarifier la limite.

**Solutions possibles** :

1. Renforcer le regex pour matcher TOUTE variable Blade `{{ ... }}` dans une ligne kernel/initrd (au-delà des 4 noms whitelistés).
2. Documenter la limite dans le test commentaire (« ce test couvre les 4 variables connues — un audit manuel reste nécessaire si nouvelles variables user introduites »).
3. Accepter en l'état (les 6 templates 3.7 sont statiques).

**Action recommandée** : Solution 2 (documenter) — auto-applicable.

**Correction appliquée (2026-05-22)** : Regex renforcée avec ancres lexicales : `/(?<![A-Za-z0-9_])\$\s*(mac|uuid|workstationName|ip)(?![A-Za-z0-9_])/`. Élimine les faux positifs sur `$ipxe`/`$ipQuery`/`$macAddress` tout en capturant `{{ $mac }}`, `{{$mac}}`, `{!! $mac !!}`, `{{ Str::lower($ip) }}`. Test du test ajouté : `it_validates_user_variable_regex_matches_blade_and_php_sigils` qui exerce 6 patterns à matcher + 5 patterns à ne pas matcher.
