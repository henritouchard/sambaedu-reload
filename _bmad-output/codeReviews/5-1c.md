## Détail des problèmes

### #1 — `openOverrideModal` fait `toastAccessDenied` au lieu de `abort(403)`

**Sévérité** : 🟠 Important
**Fichier(s)** : `resources/views/pages/users/groups/[id]/_partials/group-quota-section.blade.php:118-123`

**Constat initial (review)** :
L'AC4 demande explicitement `abort(403)` pour les 2 méthodes (`openOverrideModal` ET `applyOverride`). Le code fait `toastAccessDenied + return` pour `openOverrideModal` et `abort(403)` pour `applyOverride`. Le test AC13#5 ne couvre que `applyOverride`. Le pattern 5.1b post-review (`quota-section.blade.php:289-292, :323`) fait pareil — donc dérogation cohérente projet, mais textuellement non conforme à l'AC.

**Avis Opus** : Pertinence 1/3.
`openOverrideModal()` n'a aucun side-effect serveur (state UI uniquement) — un payload forgé pré-remplit un dialog conditionné par `@can('server.admin')` ligne 361, donc invisible. La vraie barrière (`applyOverride`) fait bien `abort(403)`. Cohérence avec 5.1b post-review pèse lourd. Pattern toast vs abort sur méthode "ouvrir UI" est défendable UX (un abort 403 sur clic bouton casse la page entière).

**Solutions possibles** :
1. Documenter la dérogation dans Dev Notes — la spec doit s'aligner sur le pattern 5.1b post-review, pas l'inverse.
2. Aligner les 2 composants (group-quota + quota-section) sur `abort(403)` → invasif sur 5.1b livré.
3. Hybride : `toastAccessDenied` pour `openOverrideModal` (ouverture UI) + `abort(403)` pour `applyOverride` (mutation), ce qui est l'état actuel — formaliser comme convention projet.

**Action** : ⏳ En attente — question Henri (option 1 ou 3 recommandée).

### #4 — Test AC13#19 idempotence toast tautologique

**Sévérité** : 🟡 Mineur
**Fichier(s)** : `tests/Feature/LoginOverQuotaToastTest.php:245-260`

**Constat initial (review)** :
Le test invoque `listener->handle()` une seule fois mais affirme "la 2ème requête ne re-fire pas". Pas de 2ème invocation = pas de couverture défensive réelle.

**Avis Opus** : Pertinence 2/3.
Le constat est juste. Tester `handle()×2` ne prouverait que l'absence de dédoublonnage du listener (qui n'en a pas et n'en a pas besoin — l'idempotence vient de l'event Login). Le bon test serait HTTP intégration sur 2 requêtes successives → lourd. Alternative pragmatique : `handle()×2 + expectToastMagicWarning(2)` documente la dépendance au framework.

**Solutions possibles** :
1. Renommer en `test_listener_does_not_self_deduplicate_and_relies_on_login_event_uniqueness` + ajouter 2ème `handle()` → asserter 2 toasts.
2. Test d'intégration HTTP (2 requêtes successives, asserter 1 seul toast côté session).
3. Garder en l'état avec un commentaire explicite sur la dépendance event Login.

**Action** : ⏳ En attente — question Henri (option 1 recommandée).
