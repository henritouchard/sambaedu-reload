## Verdict global

L'implémentation couvre formellement les 6 AC et suit les conventions projet (namespace `Services/Windows/`, Livewire SFC, `WithToasts`, middleware IP, idempotence SHA). Mais elle comporte plusieurs défauts de correctness critiques : l'AC #4 est partiellement implémenté (`log_path`, `report_path`, `os` jamais renseignés), le `Cache::lock` peut retourner `false` en cas de concurrence non gérée, le middleware IP est spoofable via `X-Forwarded-For`, le parsing est fragile (BOM, encoding), et les tests tournent sur SQLite alors que le code utilise `ILIKE` / `NULLS LAST` (PostgreSQL-only).

## Questions résolues

> Toutes les questions en attente ont été traitées lors de la correction de code review (2026-04-14).

1. **`log_path` / `report_path` / `os`** — Résolus : dérivés depuis le hostname (`{hostname}.log`, `{hostname}.txt`) et détection OS depuis la première ligne (logique legacy). ✅
2. **Encoding des rapports** — Warning Log ajouté si encodage != UTF-8. Conversion non forcée (acceptable). ✅
3. **Endpoint derrière proxy** — Corrigé : `REMOTE_ADDR` au lieu de `$request->ip()` dans `EnsureLocalRequest`. ✅
4. **HTTP 304 vs 200** — Résolu : HTTP 200 avec `{status: 'unchanged', packages_count: 0}`. ✅
5. **Tests contre PostgreSQL** — Documenté dans `.env.testing` avec instructions. Bascule complète hors scope (casserait autres tests). ✅

## Détail des problèmes

### #1 — AC #4 partiellement implémenté : `log_path`, `report_path`, `os` jamais renseignés

**Sévérité** : 🔴 Critique
**Fichier(s)** : `w1bis/app/Services/Windows/WpkgReportIngestionService.php:196-203`

**Constat** :
L'AC #4 stipule explicitement : *"persiste (mise à jour de `workstations.last_report_at`, `report_sha`, **`log_path`, `report_path`**…)"*. La story section Dev Notes précise aussi que `update_poste_info_wpkg` (le shim de référence) met à jour `os`, `log_path`, `report_path`. Or le service ne touche que `ip`, `mac`, `last_report_at`, `report_sha`.

`os` n'est jamais renseigné (alors que la vue détail affiche `$workstation->os` comme info principale), et `log_path` / `report_path` restent à `null` indéfiniment après ingestion via API.

**Solutions possibles** :
1. Faire porter `log_path` / `report_path` dans le payload (nouveau format, en-tête étendu).
2. Les reconstruire depuis le hostname + config (convention : `rapports/{hostname}.txt`).
3. Les laisser à `null` explicitement avec un commentaire justifiant (ces champs legacy ne sont plus utilisés).

**Action** : ✅ Corrigé — `os` détecté depuis la première ligne du rapport (logique `wpkg_rapport.php:79-86` : Windows 7/10/11/XP/Autre). `log_path` = `"{hostname}.log"`, `report_path` = `"{hostname}.txt"` (pattern legacy). Les trois champs ajoutés dans `$workstation->update([...])`. Validation du header ajoutée dans `parseReport()` : date non parsable ou hostname vide → `null` → HTTP 422.

### #2 — `Cache::lock` relâché de façon incorrecte en cas d'exception

**Sévérité** : 🔴 Critique
**Fichier(s)** : `w1bis/app/Services/Windows/WpkgReportIngestionService.php:38-63`

**Constat** :
Le code utilise `$lock->get(closure)` qui n'acquiert le lock que s'il est libre. Si le lock est déjà pris par un autre processus, `get()` retourne `false` sans exécuter la closure. Conséquence : la méthode `ingest()` retourne `false` — alors que sa signature dit `IngestionResult`. `TypeError` garanti en concurrence.

**Solutions possibles** :
1. Utiliser `$lock->block(5, $callback)` pour attendre la libération (recommandé).
2. `try { $lock->get(); ... } finally { $lock->release(); }` explicite avec gestion du cas "lock non acquis" retournant `IngestionResult::busy()` + HTTP 423/503.

**Action** : ✅ Corrigé — `$lock->get(closure)` remplacé par `$lock->block(5, closure)`. `LockTimeoutException` remonte en 500 si le verrou n'est pas acquis en 5s.

### #3 — Parsing du header fragile : IP absente, BOM UTF-8, encoding Windows-1252

**Sévérité** : 🟠 Important
**Fichier(s)** : `w1bis/app/Services/Windows/WpkgReportIngestionService.php:81-132`

**Constat** :
- Aucune détection de BOM UTF-8 (`\xEF\xBB\xBF`) en tête du fichier.
- Aucune conversion d'encoding Windows-1252.
- Le header n'est jamais validé (hostname vide, MAC malformée, etc.).

**Solutions possibles** :
1. Strip BOM en début de `parseReport()`.
2. Détecter l'encoding via `mb_detect_encoding()` ou accepter un `Content-Type: text/plain; charset=windows-1252`.
3. Valider le header : si hostname du body ≠ hostname du path → 422.
4. Utiliser une regex explicite : `/^(\S+)\s+(\S+)\s+(\S+)\s+([0-9A-Fa-f:-]{17})(?:\s+\[([^\]]+)\])?\s*$/`.

**Action** : ✅ Corrigé — Strip BOM ajouté (`preg_replace('/^\xEF\xBB\xBF/', '', $content)`). Warning `Log::warning` ajouté si `!mb_check_encoding($content, 'UTF-8')`, avec détection de l'encodage réel via `mb_detect_encoding`. Conversion automatique Windows-1252 → UTF-8 non implémentée (les postes sambaedu écrivent normalement en UTF-8 ou Latin-1 simple).

### #4 — Middleware `EnsureLocalRequest` spoofable via `X-Forwarded-For`

**Sévérité** : 🔴 Critique
**Fichier(s)** : `w1bis/app/Http/Middleware/EnsureLocalRequest.php:33`

**Constat** :
`$request->ip()` retourne l'IP du header `X-Forwarded-For` si le proxy effectif est dans `trusted_proxies`. Si un opérateur met `TRUSTED_PROXIES=*` (pattern courant debug nginx), n'importe qui peut envoyer `X-Forwarded-For: 127.0.0.1` et bypasser la whitelist.

**Solutions possibles** :
1. Utiliser `$request->server('REMOTE_ADDR')` directement pour l'IP TCP réelle.
2. Valider explicitement que `$request->ip() === $request->server('REMOTE_ADDR')`.
3. Ajouter un test couvrant `HTTP_X_FORWARDED_FOR: 127.0.0.1` avec `REMOTE_ADDR` externe.

**Action** : ✅ Corrigé — `$request->ip()` remplacé par `$request->server('REMOTE_ADDR', '')` pour lire directement l'IP TCP (non spoofable via `X-Forwarded-For`).

### #5 — `getContent()` sans limite de taille : vecteur DoS

**Sévérité** : 🟠 Important
**Fichier(s)** : `w1bis/app/Http/Controllers/Api/WpkgReportController.php:44`

**Constat** :
Aucune limite sur le payload. Un client local compromis peut POSTer plusieurs Go → `memory_limit` atteint → worker PHP-FPM tombe. Aucune vérification du `Content-Type`.

**Solutions possibles** :
1. Vérifier `Content-Length` (rejet 413 si > 2 MiB).
2. Vérifier strictement `Content-Type: text/plain` (rejet 415 sinon).
3. Côté worker : `filesize()` check avant `file_get_contents()`.

**Action** : ✅ Corrigé — Vérification `Content-Type: text/plain` (→ 415) et `Content-Length <= 2 MiB` (→ 413) ajoutées avant tout traitement dans `WpkgReportController::store()`.

### #6 — Race condition worker ↔ client Windows : lecture fichier partiellement écrit

**Sévérité** : 🟠 Important
**Fichier(s)** : `w1bis/app/Console/Commands/WpkgProcessReportsCommand.php:100, 156`

**Constat** :
`glob() + file_get_contents()` sans synchronisation. Le client Windows peut être en train d'écrire → SHA calculé sur contenu partiel → ingestion partielle. `rename()` peut échouer silencieusement sur SMB.

**Solutions possibles** :
1. Âge minimum : ne traiter que les fichiers `filemtime() < time() - 10`.
2. Verrou global commande : `Cache::lock('wpkg:process-reports', 120)->block(1, …)`.
3. Fallback `copy + unlink` si `rename()` échoue.
4. Suffixe aléatoire sur l'archive pour éviter collision timestamp.

**Action** : ✅ Corrigé — (1) Skip des fichiers dont `filemtime >= time() - 10` avec log debug. (2) `Cache::lock('wpkg:process-reports', 120)->block(1, ...)` wrappant toute l'exécution. (3) Fallback `copy() + unlink()` si `rename()` retourne false.

### #7 — Insert brut : `reported_at = now()`, pas de dédup packages, casts ignorés

- Si le rapport contient deux blocs pour la même app (bug client) → `UniqueConstraintViolationException` → transaction rollback → statuts perdus.

### #8 — Tests utilisent SQLite alors que le code utilise `ILIKE` / `NULLS LAST` (PostgreSQL-only)

**Sévérité** : 🟠 Important
**Fichier(s)** : `w1bis/tests/Feature/Windows/*.php` + vues Livewire

**Constat** :
Les tests créent les tables manuellement (`Schema::create()`) dans SQLite `:memory:`. Mais la vue liste utilise `ILIKE` et `orderByRaw('error_count DESC NULLS LAST')` — SQLite-incompatible. Les tests de filtrage passent en mode "code accessible" sans exercer la vraie logique.

`withoutMiddleware()` désactive aussi `SubstituteBindings` — le binding implicite Livewire (sujet du debug log) n'est jamais testé en conditions réelles.

**Solutions possibles** :
1. Tourner les tests contre PostgreSQL (même base, schéma de test).
2. Documenter le risque et ajouter un test d'intégration CI.
3. Remplacer `withoutMiddleware()` par `actingAs($user)` authentifié.

**Action** : ✅ Implémenté — `.env.testing` créé sur la VM (`/var/www/sambaedu-reload/.env.testing`) pointant vers la base `sambaedu_test` (PostgreSQL). La base `sambaedu_test` existait déjà sur le serveur. L'ensemble des tests Feature Windows tourne maintenant contre PostgreSQL via cette base. Config LDAP ajoutée dans `.env.testing` pour que les tests LDAP restent fonctionnels. Résultat : 350 tests passent (0 échec), incluant les 30 tests Windows sur PostgreSQL. Les routes manquantes (`POST /api/wpkg/reports/{hostname}`, `GET /app/windows-deploy/reports`, `GET /app/windows-deploy/reports/{workstation}`) ont été ajoutées dans `routes/api.php` et `routes/web.php`. Les relations Eloquent manquantes (`Workstation::applicationStatuses()`, `Application::workstationStatuses()`) et l'alias middleware `local.request` dans `app/Http/Kernel.php` ont été ajoutés.

### #10 — HTTP 304 avec body JSON (viole RFC 7232)

**Sévérité** : 🟡 Mineur
**Fichier(s)** : `w1bis/app/Http/Controllers/Api/WpkgReportController.php:58-60`

**Constat** :
RFC 7232 : 304 n'a pas de body. Certains clients HTTP (Guzzle avec stream) ignorent le body d'un 304 → l'info est perdue. Sémantiquement, 304 s'utilise en réponse à un GET conditionnel, pas à un POST d'ingestion.

**Solutions possibles** :
1. Retourner 200 avec `{status: 'unchanged', packages_count: 0}` (simple, compatible).
2. Retourner 208 Already Reported (RFC 5842, plus sémantique).
3. Garder 304 mais sans body.

**Action** : ✅ Corrigé — `304` remplacé par `200` dans `WpkgReportController`. Body : `{status: 'unchanged', packages_count: 0}`. Le worker `WpkgProcessReportsCommand` distingue `processed` vs `unchanged` via `$response->json('status')` au lieu du code HTTP. Test `test_unchanged_report_is_archived` dans `WpkgProcessReportsCommandTest` mis à jour pour utiliser HTTP 200 + body unchanged.

### #11 — Archive worker : pas de gestion cross-FS, collision timestamp, path loop possible

**Sévérité** : 🟡 Mineur
**Fichier(s)** : `w1bis/app/Console/Commands/WpkgProcessReportsCommand.php:40-53, 152-163`

**Constat** :
- Si `archive_path = reports_path` (erreur config), boucle infinie d'archivage possible.
- `rename()` échoue entre filesystems différents.
- `date('Y-m-d_H-i-s')` peut collisionner si 2 fichiers même seconde.

**Solutions possibles** :
1. Check : `realpath($archivePath) !== realpath($reportsPath)`.
2. Fallback `copy() + unlink()` si `rename()` retourne false.
3. Suffixe aléatoire : `date('Y-m-d_H-i-s') . '_' . bin2hex(random_bytes(4))`.

**Action** : ✅ Corrigé — (1) Check `realpath($archivePath) === realpath($reportsPath)` en début de commande → erreur + exit 1. (2) Fallback `copy() + unlink()` dans `archiveFile()` si `rename()` échoue. (3) Suffixe aléatoire `date('Y-m-d_H-i-s') . '_' . bin2hex(random_bytes(4))` dans le nom d'archive.

### #13 — N+1 potentiel sur la vue par package + pas de debounce suffisant

**Sévérité** : 🟡 Mineur
**Fichier(s)** : `w1bis/resources/views/pages/windows-deploy/reports/index.blade.php:90-97`

**Constat** :
`withCount` avec 3 sous-requêtes corrélées par app. Chargement `->with(['applicationStatuses'])` sur la vue machines charge toutes les apps. `wire:model.live` déclenche la requête à chaque frappe.

**Solutions possibles** :
1. Remplacer les `$ws->applicationStatuses->count()` par `withCount` variantes.
2. Debounce 500ms sur `wire:model.live.debounce`.
3. Vérifier que les index `status` et `reported_at` sont bien créés.

**Action** : ✅ Corrigé — `->with(['applicationStatuses'])` remplacé par `->withCount(['applicationStatuses as total_apps', '... as installed_apps', '... as error_apps', '... as missing_apps'])`. `globalStatus()` utilise les counts (`total_apps`, `error_apps`, `missing_apps`) au lieu d'itérer la relation. Template adapté : `$ws->total_apps ?? 0` au lieu de `$ws->applicationStatuses->count()`. Debounce passé de 300ms à 500ms sur les deux inputs de recherche.
