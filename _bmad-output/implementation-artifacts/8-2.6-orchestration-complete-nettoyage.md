# Story 8.2.6 : Orchestration complète + nettoyage

Status: done

## Story

As a **responsable de collège**,
I want que l'ajout d'applications depuis le dépôt exécute le flow complet de bout en bout,
So que les packages WPKG sont correctement installés et servis aux postes Windows.

## Acceptance Criteria

1. **Flow E2E depuis l'UI** — Given je sélectionne des applications dans le tab Dépôt et clique "Ajouter au catalogue", When le flow s'exécute, Then chaque app passe par : download XML → vérif hash → multi-download → post-traitement → mise à jour base → régénération `packages.xml`.

2. **Fichiers aux bons chemins** — Given l'installation est terminée, When je vérifie le filesystem, Then les fichiers sont aux chemins définis par `<download saveto="...">` dans `/var/sambaedu/unattended/install/`.

3. **packages.xml correct** — Given l'installation est terminée, When le `packages.xml` local est régénéré, Then il contient les packages installés (triés, sans noeuds SambaEdu) et est servi aux clients WPKG.

4. **Erreur avec feedback** — Given une erreur survient pendant l'installation, When l'erreur est catchée, Then le toast affiche un message explicite, And `Application.status` = `Error`, And `InstallationLog.status` = `Failed` avec le message d'erreur.

5. **Code mort supprimé** — Given le nouveau flow est en place, When je cherche l'ancien code mono-fichier, Then `downloadPackageXml()` et `getAppStoragePath()` n'existent plus dans `AppStoreService` (attention : `removeDirectory()` est encore utilisée par `uninstallApplication()` — à vérifier avant suppression).

6. **Nettoyage tmp2/** — Given une installation réussit, When les fichiers post-téléchargement sont déplacés vers leur chemin final, Then le répertoire `tmp2/` est purgé des fichiers résiduels liés à cette installation (XML recipe + éventuels fichiers intermédiaires). En cas d'échec, les fichiers `tmp2/` sont conservés pour diagnostic.

7. **installed_at et installed_version mis à jour** — Given l'installation réussit, When `finalizeInstallation()` est exécutée, Then `Application.installed_at = now()` et `Application.installed_version = $application->version` sont persistés en base.

### `finalizeInstallation()` — analyse complète

```php
// Lignes 227-238 dans AppStoreService
private function finalizeInstallation(Application $application, string $xmlPath): void
{
    $application->update([
        'status' => ApplicationStatus::Installed,
        'installed_version' => $application->version,
        'installed_at' => now(),
        'local_xml_path' => $xmlPath,  // ← ATTENTION : c'est le chemin tmp2/ temporaire !
    ]);

    $this->updateLocalPackagesXml();  // délègue à PackagesXmlService::regenerate()
}
```

**Problème identifié** : `$xmlPath` passé à `local_xml_path` est le chemin dans `tmp2/` (format : `{storagePath}/wpkg/tmp2/{app_id}_{date}_{uniqid}.xml`). Après la Tâche 2 (nettoyage `tmp2/`), ce fichier sera supprimé. Options :
- Option A : Stocker le XML dans `Application.xml` (colonnes texte) et mettre `local_xml_path = null` (le fichier tmp est éphémère par nature)
- Option B : Conserver le XML recipe dans un répertoire permanent (ex: `{storagePath}/wpkg/recipes/{app_id}.xml`) au lieu de `tmp2/`
- **Option recommandée A** : `local_xml_path` est une trace de debug — le contenu est déjà dans `Application.xml`. Après nettoyage `tmp2/`, mettre `local_xml_path = null` ou le supprimer du update dans `finalizeInstallation()`.

Note : Le stockage de `Application.xml` (ligne 140) se fait AVANT le nettoyage `tmp2/`, donc le contenu XML est sauvegardé en base avant la suppression du fichier temporaire.

### Nettoyage `tmp2/` — où placer le code

Le `$xmlPath` est créé dans `downloadXmlRecipe()` et passé de méthode en méthode. La suppression doit avoir lieu après le bloc try complet, dans la section succès de `installApplication()` :

```php
// Dans installApplication(), après le bloc try success
// ... (après finalizeInstallation)
@unlink($xmlPath);  // Nettoyage du XML recipe temporaire
Log::debug('[AppStore] XML recipe temporaire nettoyé', ['path' => $xmlPath]);
```

**Important** : ne pas placer dans le bloc `catch` — les fichiers `tmp2/` doivent persister en cas d'erreur pour le diagnostic.

### Colonnes `installer_*` du modèle `Application`

Les colonnes `installer_url`, `installer_sha256`, `installer_filename`, `installer_size`, `local_installer_path` existent encore dans le modèle `Application` et la migration. Ces colonnes sont du **legacy mono-fichier** jamais supprimé. La spec originale mentionnait leur nettoyage en 8.2.6.

**Décision** : Ne pas supprimer les colonnes dans cette story (risque de migration destructive). Les laisser nullable — elles seront ignorées. Ajouter une note `todos` dans le sprint-status si nécessaire.
