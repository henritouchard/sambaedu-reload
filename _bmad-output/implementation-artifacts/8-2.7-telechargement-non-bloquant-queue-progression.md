# Story 8.2.7 : Téléchargement non-bloquant au catalogue — installation WPKG en queue + progression Livewire

Status: ready-for-dev
Depends on: 8.2.6 (done)

## Story

As a **responsable de collège**,
I want que l'ajout d'applications WPKG au catalogue s'exécute en tâche de fond (queue) plutôt que dans la requête web,
So que je puisse continuer à naviguer pendant les téléchargements, en lancer plusieurs en parallèle, et suivre leur progression en temps réel.

## Contexte

Aujourd'hui, ajouter un package WPKG au catalogue est **bloquant**. Le bouton « Ajouter au catalogue » appelle `installFromDepot()` qui **boucle dans la requête Livewire** sur les apps sélectionnées et exécute `AppStoreService::installApplication()` de façon synchrone (`resources/views/pages/parc-settings/_partials/depot-tab.blade.php:191-231`). Chaque installation télécharge le XML recipe + N fichiers (timeout 300 s/fichier) ; pendant tout ce temps `isInstalling = true` gèle l'UI et la navigation.

L'infrastructure pour passer à l'asynchrone est **déjà en place** — cette story branche le tuyau sans rien réinventer :

- `installApplication(DepotApplication, string $initiatedBy = 'system')` est déjà idempotent (`Application::firstOrCreate`) et écrit déjà tout le cycle de vie dans un `InstallationLog` (`status`, `progress` 0-100, `downloaded_bytes`, `message`, `started_at`, `completed_at`). Il suffit de l'**encapsuler dans un Job** et de le **dispatcher** au lieu de l'appeler en ligne.
- Les tables `jobs`, `failed_jobs`, `job_batches` **existent déjà** (`database/migrations/2026_01_30_000000_create_unified_schema.php:333-401`). `QUEUE_CONNECTION=database` est configuré en prod (`.env` + `.env.example`).
- Trois **workers de queue systemd sont déjà déployés et auto-gérés** par `scripts/update.sh:497` (enable + restart à chaque update), tournant en `www-admin` (uid 599, condition pour écrire `storage/wpkg/`) :
  - `laravel-queue-worker.service` → `queue:work database` (queue `default`)
  - `laravel-queue-general.service` → `queue:work database --queue=default,high,low`
  - `laravel-queue-sync.service` → `queue:work database --queue=sync`
- Le pattern « dispatch d'un job long + suivi par polling Livewire » existe déjà à l'identique : `resources/views/pages/admin/ipxe/iso-windows/index.blade.php` (dispatch `DownloadWindowsIsoJob`, card « en cours » avec `wire:poll.60s` conditionnel). C'est la référence à répliquer.

> **Décision de file** : on cible la queue **`default`** (déjà servie par DEUX workers : `laravel-queue-worker` + `laravel-queue-general`). Le parallélisme effectif = nombre de workers actifs sur cette file (≥ 2 sur la VM actuelle), **PAS** automatique au-delà : un worker traite un job à la fois. Aucune nouvelle action OPS n'est requise pour `default`. Dev Notes documente l'alternative file dédiée `wpkg` et son coût (édition d'un `.service`).

## Acceptance Criteria

1. **Dispatch non-bloquant** — *Given* je sélectionne N applications dans le tab Dépôt et clique « Ajouter au catalogue », *When* `installFromDepot()` s'exécute, *Then* un `InstallApplicationJob` est **dispatché par app** (N dispatches) et la méthode rend la main immédiatement **sans** exécuter l'installation en ligne, *And* aucune attente synchrone ne gèle la requête.

2. **InstallationLog créé à l'état initial** — *Given* le dispatch a lieu, *When* je consulte la base juste après, *Then* il existe un `InstallationLog` par app avec `status = Pending`, `progress = 0`, `started_at = now()`, `initiated_by` = login de l'utilisateur courant (pas `'system'`), `application_id` renseigné. La création du log + du modèle `Application` (état `Downloading`) se fait **dans le dispatch** (UI) ou **au début du Job** — au choix, mais le log doit exister pour que le polling l'affiche.

3. **Navigation libre pendant l'installation** — *Given* des installations sont en cours, *When* je change de filtre / page / onglet dans le tab Dépôt, *Then* l'UI répond normalement (plus de blocage `isInstalling` qui désactive durablement l'interface). Le toast de confirmation indique « N installation(s) lancée(s) en arrière-plan », pas « N application(s) ajoutée(s) ».

4. **Exécution effective par le worker** — *Given* un `InstallApplicationJob` est en file, *When* le worker `queue:work` le traite, *Then* il exécute exactement le flow existant `AppStoreService::installApplication($depotApp, $initiatedBy)` (download XML → vérif hash → multi-download → post-traitement → finalisation → régénération `packages.xml`), *And* l'`Application` finit à `Installed`, *And* l'`InstallationLog` finit à `Success` avec `progress = 100` et `completed_at` renseigné.

5. **Plusieurs téléchargements simultanés** — *Given* je sélectionne plusieurs apps, *When* je clique « Ajouter au catalogue », *Then* chaque app a son propre Job indépendant sur la file `default` ; l'échec d'un Job ne fait **pas** échouer les autres (isolation par job, pas de boucle partagée).

6. **Progression affichée (polling)** — *Given* au moins une installation est non-terminale (`status ∉ {Success, Failed}`), *When* la page est affichée, *Then* un panneau de progression liste les installations actives de l'utilisateur courant avec, par ligne : nom de l'app, `status->label()`, barre de progression (`progress` %), et `message`. Le panneau se rafraîchit via `wire:poll` **conditionnel** (actif seulement s'il reste une installation non-terminale, comme `iso-windows`). Quand tout est terminal, le polling s'arrête.

7. **Gestion d'échec robuste** — *Given* une installation échoue (URL invalide, hash mismatch, move KO), *When* le Job lève une exception, *Then* l'`InstallationLog.status = Failed` avec le message d'erreur (déjà géré par le `catch` de `installApplication()`), *And* l'`Application.status = Error`, *And* le Job définit `$tries`, `backoff` et une méthode `failed()` qui marque le log `Failed` si `handle()` n'a pas pu le faire (garde-fou idempotent — ne pas écraser un log déjà terminal). L'échec n'interrompt pas les autres jobs.

8. **Régénération packages.xml sérialisée** — *Given* plusieurs jobs se terminent quasi-simultanément, *When* chacun appelle `updateLocalPackagesXml()` (→ `PackagesXmlService::regenerate()`), *Then* la régénération est protégée d'une écriture concurrente corrompue. L'écriture est **déjà atomique** (write `.tmp` + `rename`, `PackagesXmlService.php:70-74`) ; ajouter en plus un `Cache::lock` court autour de `regenerate()` (ou de l'appel dans le Job) pour sérialiser les régénérations concurrentes et éviter une lecture `Application::installed()` incohérente. Documenter le choix.

9. **Tests** — *Given* la suite de tests, *When* je l'exécute, *Then* :
   - un test prouve que `installFromDepot()` **dispatche** le Job (via `Queue::fake()` + `Queue::assertPushed(InstallApplicationJob::class, N)`) et **n'exécute pas** l'installation en synchrone (l'`Application` ne passe pas à `Installed`, aucun HTTP n'est tapé) ;
   - un test prouve que `InstallApplicationJob::handle()` appelle `AppStoreService::installApplication()` avec le bon `DepotApplication` et le bon `initiated_by` ;
   - le flow E2E existant `tests/Feature/Services/AppStore/AppStoreInstallFlowTest.php` (qui appelle `installApplication()` **directement**) reste **vert sans modification** (non-régression) ;
   - le test du composant Livewire vérifie le toast « lancée(s) en arrière-plan » et l'`initiated_by` du log.

### Le flow `installApplication()` est complet et NE DOIT PAS être réécrit

`AppStoreService::installApplication()` (`app/Services/AppStore/AppStoreService.php:80-192`) fait déjà tout, dans un `try/catch` qui gère l'échec (log `Failed` + app `Error`, ligne 175-191). Cette story **n'y touche pas** (sauf éventuellement la sérialisation `packages.xml`, Tâche 2). Le Job est une fine enveloppe : `find` + délégation. **Anti-pattern à éviter** : dupliquer la logique d'installation dans le Job.

### Pourquoi passer l'id et non le modèle au Job

`SerializesModels` rechargerait `DepotApplication` à l'exécution, mais une row stale ou un `firstOrCreate`/sync entre-temps rendent l'id plus sûr. Cf. `DownloadWindowsIsoJob` qui prend `public readonly int $downloadId`. Pattern projet confirmé.

### Gabarit Job (référence `app/Jobs/ApplyQuotaJob.php`)

```php
class InstallApplicationJob implements ShouldQueue
{
    use Dispatchable, InteractsWithQueue, Queueable, SerializesModels;

    public int $tries = 3;
    public int $backoff = 30;

    public function __construct(
        public readonly int $depotApplicationId,
        public readonly string $initiatedBy,
    ) {
        $this->onQueue('default'); // servie par laravel-queue-worker + laravel-queue-general
    }

    public function handle(AppStoreService $appStoreService): void
    {
        $depotApp = DepotApplication::find($this->depotApplicationId);
        if ($depotApp === null) {
            Log::warning('[AppStore] InstallApplicationJob: DepotApplication introuvable', ['id' => $this->depotApplicationId]);
            return;
        }
        $appStoreService->installApplication($depotApp, $this->initiatedBy);
    }

    public function failed(?Throwable $e): void { /* garde-fou idempotent — guard isTerminal() */ }
}
```

> **`$timeout` du Job** : un package peut avoir N fichiers à 300 s chacun (`WPKG_DOWNLOAD_TIMEOUT`). Le `retry_after` de la connexion `database` vaut **90 s** (`config/queue.php`). Si `handle()` dépasse 90 s, le job pourrait être re-pris par un autre worker (double exécution). Définir `public int $timeout` cohérent (ex. somme des timeouts + marge, cf. `DownloadWindowsIsoJob::$timeout`) ET noter que `retry_after` < `timeout` est un risque de double-pickup. **Mitigation** : `firstOrCreate` rend l'install idempotente ; le `WithoutOverlapping` (Tâche 1 optionnel) ou un `timeout` < `retry_after` évite le doublon. **Trancher** : soit augmenter `retry_after` (config, hors VM → cache config), soit `WithoutOverlapping` par app, soit accepter l'idempotence comme garde-fou. Recommandation : `WithoutOverlapping` keyé sur `app_id` (simple, sans toucher la config prod).

### File de queue : `default` déjà servie par 2 workers

`scripts/config/laravel-queue-worker.service` (`--queue` implicite `default`) + `scripts/config/laravel-queue-general.service` (`--queue=default,high,low`) traitent tous deux `default`. Donc dispatcher sur `default` = parallélisme ≥ 2 **sans aucune action OPS**. `update.sh:497` enable+restart ces workers automatiquement. **Parallélisme ≠ illimité** : 2 jobs WPKG max en vol simultané sur la VM actuelle (un par worker), les suivants attendent.

> File dédiée `wpkg` (alternative documentée, NON retenue par défaut) : isolerait les téléchargements lourds des jobs courts (AdSync, quotas). Coût : éditer `--queue=...` de `laravel-queue-general.service` **ou** créer `laravel-queue-wpkg.service` + l'ajouter à `update.sh`. Tout est dans le repo (déployé par update.sh) — faisable côté code, mais inutile pour le MVP. **Ne pas configurer la VM depuis le dev.**

## Recommandation Modèle Dev

**Recommandation : `opus`**

Bien que la logique métier d'installation soit déjà écrite et ne soit pas à réimplémenter, cette story est **plus subtile qu'un simple câblage** :

- **Sémantique de queue à raisonner correctement** : interaction `$tries`/`backoff`/`$timeout` vs `retry_after=90s` de la connexion `database` (risque de double-pickup sur un job long), choix `WithoutOverlapping` vs idempotence `firstOrCreate`, file servie par plusieurs workers. Une erreur ici produit des installations dupliquées ou des jobs perdus — silencieux et difficile à diagnostiquer.
- **Concurrence** : sérialisation de `packages.xml` sous charge parallèle, garde-fou `failed()` idempotent qui ne doit pas écraser un log déjà terminal.
- **Piège de test non-évident** : `QUEUE_CONNECTION=sync` en test rend `dispatch()` synchrone — sans `Queue::fake()`, le test « non-bloquant » téléchargerait réellement et passerait pour de mauvaises raisons. Distinguer dispatch-fake / handle-réel / non-régression E2E demande de la rigueur.
- **Décisions à trancher** (log créé en UI vs dans le Job ; file `default` vs `wpkg`) avec impacts UX et OPS.

Le risque n'est pas le volume de code (faible) mais la **justesse des choix de concurrence et de test**, où un modèle moins capable produirait un résultat qui « marche en surface » mais double-exécute ou teste à côté. D'où `opus`.
